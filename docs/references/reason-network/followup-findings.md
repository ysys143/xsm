# 후속 실행과 설계 반영

2026-10-24. 초기의 600초 분석과 선택 함수 20개를 전체 완료로 취급했던 판정을 정정하고, 두 Ghidra 프로젝트를 시간 제한 없이 끝까지 분석했다. CLI 배포물의 실제 모듈을 격리 실행하고 공개 엔진의 E2E 7종을 추가 수행했다. 이 문서의 통과 수는 관찰 조건의 충족이며 제품 무결함 판정이 아니다.

## 원본 배포 모듈의 워커 시험

[실행기](probe_cli_worker.py)와 [격리 actor](probe_worker_actor.mjs)는 수정하지 않은 CLI 0.2.557 ask-worker 모듈을 실행한다. 자식 CLI·모델 결과·전송 계층은 가짜 구현이다. 저널 파일은 실제로 쓰고 별도 프로세스를 종료·재시작했다. 유료 API와 실제 모델 호출은 없었다. [15개 관측 결과](worker-probes.json).

| 확인한 경로 | 실제 관측 | xsm 제안 |
|---|---|---|
| 문맥과 실행 순서 | 같은 발신자 자식 재사용·직렬 처리, 다른 발신자는 별도 자식·병렬 처리 | ADR-0016: 문맥 공유 단위를 명시하고 독립 검토 문맥과 구분 |
| 임시 ask 주소 | 같은 사람의 서로 다른 임시 ask 주소가 한 문맥으로 합쳐짐 | 주소 변화와 업무 변화가 같은지 별도 판단 |
| 하네스 차이 | Claude는 strict MCP·훅 비활성화, Codex는 요청별 exec이고 resume 없음 | ADR-0023: 같은 serve 주소의 후속 문맥을 하네스별로 검증 |
| 6명이 모두 작업 중인 풀의 일곱 번째 발신자 | 새 자식을 넣은 직후 유휴 회수 대상으로 선택. 실제 ask 시작은 6건, 회신은 7건이며 한 회신은 워커가 실행 중이 아니라는 오류 | ADR-0016: 수락 전에 실행 용량 확보, 대기 또는 명시적 과부하 결과. 실행하지 않은 일을 일반 답으로 성공 처리하지 않음 |
| 수신 확인 직전 종료 | 요청은 먼저 저널에 남으며 재시작 뒤 회수 | ADR-0018: 먼저 보관하고 확인 |
| 답 송신 직전 종료 | 생성된 답은 이미 저장. 재시작 뒤 모델 실행 없이 답만 재송신 | ADR-0018: 회신 장애와 과제 재실행 분리 |
| 회신 세 번 실패 | 답이 남고 다음 프로세스에서 새 작업 없이 재송신 | 결과 보존과 재전송 ID·수명 계약 필요 |
| 업무 부작용 후 답 저장 전 종료 | 재시작 때 요청 재실행. 가짜 업무 부작용이 두 번 발생 | at-least-once 경계. 부작용별 멱등 키·조정 필요 |

일곱 실제 LLM 세션을 실행한 결과가 아니다. 과부하 관측은 배포 모듈의 제어 흐름과 가짜 자식의 관측이며 전체 CLI 배선·모델 동작과 구분한다. 저널 경로의 좋은 점을 수용하되 풀 한도 6이나 발신자 단위 문맥 공유를 xsm 기본값으로 옮기지 않는다.

## 인증 완료와 요청 결속

바이너리에서 device-sign-in의 실제 구현 모듈도 추출했다. 얇은 재수출 모듈을 구현으로 오해하지 않고, 의존하는 구현의 바이트 구간과 SHA를 [추가 추출 기록](cli-additional-extraction.json)에 남겼다. [actor](probe_auth_actor.mjs)는 이 모듈을 수정하지 않고 실행한다. HTTP·자격 저장 helper·프로세스 존재 확인은 가짜이며, 파일·lock은 격리 폴더에서 실제로 처리한다. 사용자 자격 증명이나 계정 서버는 접근하지 않았다. [12개 관측 결과](auth-probes.json).

exclusive lock, 살아 있는 소유자와 만료·죽은 소유자의 구분, 다른 소유자의 lock 보존, 정상 완료·명시적 거부·만료, pending 삭제 및 다른 clientId 로그인 감지를 확인했다. 사용자가 재명령해도 진행 중 흐름을 이어받는 설계는 xsm의 연결 의도 보존에 참고할 만하다.

다만 finisher가 token 응답을 기다리는 동안 pending 파일을 **다른 유효 pairingId**의 파일로 바꾸면, 이전 응답의 자격을 저장하면서 새 pending은 남기는 경로가 재현됐다. 응답 전 반복 검사에서는 pairingId를 보지만 저장 직전 검사는 파일 존재와 기존 credential의 clientId만 본다. 실제 여러 CLI가 lock·종료 절차를 거쳐 이 교체 조건에 도달하는지는 검증하지 않았다. 이를 실제 계정 탈취나 서버 검증 우회로 판정하지 않는다.

ADR-0015·0020·0023에는 답을 받은 시점과 적용 직전의 원 요청·대상·세대 일치를 요구한다. 서명·로그인 성공이나 lock 존재가 현재 요청과의 일치를 대신할 수 없다.

SDK의 실제 ReasonApi 구현도 정적으로 대조했다. 조직의 agent-network 조회·생성·회전, network/teams 등록, relay 작업 claim·완료·회신은 `/v3` HTTP 경로다. P2P 메시지 전송과 계정·호스팅 relay 경로는 다른 데이터 경로다. 이 클라이언트 분석으로 서버의 접근 검사나 저장·전달 보장을 입증하지 않는다.

## 알림 영수증과 E2E 실패

[알림 실행기](probe_notify.py)는 OS 명령을 파일 장벽에서 기다리게 한 뒤 실패시키는 가짜 알림만 사용한다. 공개 0.12.11 debug 엔진과 공식 배포 0.12.10 모두에서 각각 [4개](notify-probes.json)·[4개](notify-baseline-probes.json) 관찰 조건을 충족했다. 실제 사용자 알림은 0회다.

엔진은 OS 명령이 끝나기 전에 `popped up`을 반환한다. 명령이 나중에 exit 1이면 실패는 데몬 로그에만 남고 발신자별 1분 제한도 소모된다. 따라서 OS 호출 완료나 사람이 보았다는 증거로 쓸 수 없다. ADR-0020은 요청 접수·OS 호출 성공·사람 확인을 구별하고 실패한 호출의 재시도 정책을 검사한다.

공개 E2E는 실행 suite **7개**와 공통 도우미 `proofs.py` 1개다. 8개 실행 suite라는 이전 표현을 정정한다. [전체 기록](e2e-results.json).

| suite | 처음 실행 | 후속 대조 |
|---|---:|---|
| hooks | 63/63 | 합성 하네스의 훅·수신·자료 교환 |
| codex_busy | 35/35 | 가짜 Codex의 작업 중 전달·큐 경로 |
| two_machines | 129/130 | 수정하지 않고 재실행해도 129/130. 알림 로그 검사 1건 실패 유지 |
| names | 33/36 | 잘못 선택한 구버전 0.10.8 때문에 가입이 실패하고 2건이 연쇄 실패. 의도한 0.12.6으로 36/36 |
| mixed_versions | 23/23 | 이 suite는 0.10.8과의 호환 경로를 별도로 다룸 |
| regional_relays | 14/14 | 지역 릴레이 목록·선택 경로 |
| guided | 9/9 | 가짜 대화형 입력의 안내 경로 |

처음 실행은 306 통과·4 실패다. names 시험체를 바로잡은 각 suite의 후속 결과는 **309 통과·1 실패**다. 두 실행을 합쳐 독립된 620개 사례로 세지 않는다.

two_machines의 실패에서는 영수증 뒤 `shown()`이 0.5초 기다렸어도 로그가 비어 있었다. 두 번의 실행 모두 종료 후 해당 파일에는 기대한 발신자·세션·본문이 있었다. 비동기 명령의 종료를 기다리지 않는 소스와 위 장벽 시험에 부합하는 타이밍 문제다. 원 시험을 수정해 통과로 만들지 않았다. 제품이 표현한 성공 단계가 실제 관측보다 앞서는 문제는 별도로 ADR에 반영한다.

모든 머신·홈·모델은 한 물리 호스트의 합성 시험체다. iroh 연결은 실제로 사용했지만 물리 원격·다른 NAT·모든 릴레이 장애·실제 모델의 이해까지 입증한 것은 아니다. 가짜 브라우저·알림과 격리 상태를 사용했고 실제 사용자 세션의 환경 표식을 제거했다.

## 증거의 종착점

[잔여 의문](residual-unknowns.json)은 20개 항목 각각에 조사 결과와 남은 경계를 기록한다. 기존 xsm 연결 승인 수집 실패와 일반 Codex 전달 실패를 후속 합성 시험의 성공으로 덮지 않는다. 새 물리 머신, 실제 승인 UI 경쟁, 하네스의 실제 공유 MCP 배치는 여전히 미검증이다. 수행 주체는 조사 코디네이터이며 확인 일자는 2026-10-24다. 해당 경로를 다시 평가할 때는 원 표본을 유지하고 허가된 시험 환경에서 ADR의 대응 수용 검사를 실행한다. 이 항목의 향후 생략을 사용자가 승인한 것으로 기록하지 않는다.

두 Ghidra 프로젝트의 자동 분석·사후 목록 추출·저장은 모두 exit 0이고 시간 초과 플래그는 false다. [실행 메타데이터](full-native-analysis.json). 이는 native 함수 의미 전수 검증이나 비공개 서버 복원을 뜻하지 않는다. xsm 제품 코드를 바꾸지 않고, 관찰 결과를 9개 Proposed ADR에 반영했다.
