# 조직 구성과 권장 개발 운영 모델

XSM은 에이전트 세션들이 서로를 찾아 대화하고, 공동 상태를 남기고, 일을 이어받게 하는 중립적인 통신 기반이다.
조직의 역할·관계·의사결정 방식은 사용자가 자연어로 정하고, 참여하는 에이전트들이 그 규칙에 따라 협업한다.

규모가 크고 장기간 병렬로 진행하는 개발 작업에는 **강한 모델의 팀장과 수평적인 워커들로 구성된 조직을 강력히 권고한다.**
팀장은 계획과 진도를 관리하고, 워커들은 역할을 나눠 실행하며, 큰 작업은 여러 팀으로 나눠 필요한 정보를 공유한다.
이 문서는 사람이 팀을 구성할 때와 에이전트가 자신의 역할을 이해할 때 함께 참조하는 운영 가이드다.

## 1. 조직은 자연어로 구성한다

사용자는 누가 계획을 유지하는지, 누가 무엇을 맡는지, 어떤 결정을 함께 내리는지, 누구에게 보고하는지를 말로 지정한다.
에이전트들은 이 지시를 작업 요청과 공유 상태에 반영한다. 업무 역할마다 별도의 제품 기능이나 고정된 계층을 만들 필요는 없다.

팀장 중심 조직 외에도 동등한 구성원들이 토론하는 의회형, 서로의 결과를 검토하는 동료 조직, 독립 팀들의 느슨한 연합을
구성할 수 있다. 합의·표결 같은 절차를 지정했다면 참여자들이 그 절차를 수행하고 결과를 기록한다. XSM이 자연어 규칙을
해석해 합의나 표결을 자동 집행하는 것은 아니다.

조직 구성의 자유와 개발 작업에 대한 권장 방식은 함께 성립한다. 별도의 조직을 지정하면 그 규칙을 따르되,
장기적인 계획 유지와 병렬 실행을 함께 요구하는 개발에서는 아래의 팀장·워커 구성을 우선 권장한다.

## 2. 통신 범위·조직·생성 관계를 구분한다

| 개념 | 의미 |
|---|---|
| 프로젝트(`project`) | 폴더와 그 안의 세션들을 묶는 통신 범위 |
| 팀(`team`) | 함께 목표를 수행하는 세션들의 구성원 목록과 팀 보드 |
| 업무 역할 | 팀장·주력 워커·보조 워커 등 자연어로 정한 책임과 협업 관계 |
| 생성 관계 | 어떤 세션이나 외부 도구가 어떤 워커를 띄웠는지에 관한 관계 |
| 모델·런타임 | 각 참여자의 작업에 사용할 모델과 그 모델을 실행하는 환경 |

한 프로젝트 안에 여러 팀이 있을 수 있고, 한 세션이 여러 팀에 속할 수도 있다. 팀은 프로젝트나 머신 경계를 넘을 수 있다.
세션을 생성한 부모가 업무상 상급자일 필요는 없으며, 작업을 요청받았다고 생성 깊이가 늘어나지도 않는다.

자연어로 역할을 부여하는 것과 제품의 구성원·`lead`·생성자 관계를 등록하는 것은 구분한다. 역할 지시만으로 팀 가입이나
통신 권한이 자동으로 설정되지는 않는다. XSM의 `lead`는 구성원 관리와 사용자 승인 창구에 관련된 자리이며,
모든 조직에서 최종 업무 결정권자를 뜻하지는 않는다. 권장 개발 조직에서는 업무상 팀장과 이 자리를 맞추면 운영이 명확해진다.
생성자에게 연결된 승인 전달 경로도 별도로 유지되므로, 역할 이름을 바꾼 것만으로 그 경로가 바뀌지는 않는다.

## 3. 권장 개발 조직: 팀장과 수평적인 워커

여러 작업을 동시에 진행하고, 중간 결과에 따라 계획을 조정하며, 세션이 바뀌어도 방향을 유지해야 하는 개발에서는
팀장 한 명이 전체 목표와 계획을 책임지고 여러 워커가 실행을 나눈다.

| 역할 | 권장 모델 배치 | 책임 |
|---|---|---|
| 팀장 | fable/astra급 | 목표·완료 기준·계획 유지, 작업 배정, 진도 관리, 판단 조율, 결과 통합, 사용자 보고 |
| 주력 워커 | opus/sol급 | 비교적 넓은 구현·분석·검증 과제 수행, 관련 워커와의 협업, 결과와 막힘 보고 |
| 보조 워커 | haiku max/luna max급 | 범위가 명확한 조사·검사·반복 작업 등을 맡아 실행 지원 |

모델명은 이 가이드의 역할별 권장 배치다. XSM이 이 표에 따라 모델을 자동 선택하거나 현재 워커 기본값을 변경하지는 않는다.
실행할 때는 사용할 런타임의 모델과 추론 설정을 확인해 지정한다.

주력과 보조는 업무 역할이다. 모두 팀장 아래 같은 생성 깊이에 두고, 과제에 맞춰 역할과 협업 상대를 지정할 수 있다.
주력 워커가 보조 워커에게 직접 요청하고 결과를 받아도 된다. 보조 워커는 여러 명을 붙일 수 있으며,
각각의 담당 범위와 결과를 받을 상대를 분명히 한다.

강한 팀장 모델을 두는 목적은 작업 전체의 계획과 판단을 오래 유지하는 데 있다. 그 일관성은 모델의 대화 문맥에만 맡기지
않고 목표·현행 결정·담당·진행 상태를 팀 보드에 남겨 뒷받침한다. 팀장이나 워커가 교체되어도 기록을 읽고 이어갈 수 있어야 한다.

## 4. 역할별 행동

### 팀장

팀장은 시작할 때 목표, 완료 기준, 주요 제약과 작업 간 의존성을 정리하고 일을 나눈다. 각 과제에는 담당자, 필요한 입력,
기대 산출물, 완료 판단 방법과 보고 대상을 명시한다. 주력·보조 역할과 직접 협업할 상대도 함께 알려 준다.

진행 중에는 완료·진행·막힘을 구분해 파악한다. 답을 기다리는 동안 진행할 수 있는 다른 일을 이어가고,
워커가 멈췄거나 기존 계획의 전제가 바뀌면 원인을 확인해 배정과 계획을 조정한다. 한 워커의 답변만으로 전체 완료를 판단하지
않고, 합의한 완료 기준에 따라 결과를 통합한다. 결과·남은 일·사용자의 판단이 필요한 사항을 묶어서 보고한다.

모든 대화를 팀장이 중계할 필요는 없다. 워커 사이의 세부 협의는 직접 진행하게 하되, 공동 결정·담당·우선순위에 영향을 주는
변경은 팀장이 파악하고 현행 계획에 반영한다. 사용자는 어느 워커에게든 직접 지시할 수 있으며, 팀장은 그 지시로 생긴 변경도
계획과 조율한다.

### 주력 워커

주력 워커는 맡은 과제를 이해하고 필요한 팀 보드 항목과 산출물을 읽은 뒤 실행한다. 배정된 범위 안에서 직접 판단하고,
검증한 결과와 남은 문제를 보고한다. 다른 워커의 정보나 도움이 필요하면 상대에게 구체적으로 요청한다.

보조 워커에게 요청할 때는 과제의 배경, 입력, 범위, 기대 결과와 보고 대상을 전달한다. 받은 결과를 자신의 과제에 통합하고
확인할 책임도 진다. 이미 다른 일을 맡은 워커를 사용하려면 현재 배정과 여유를 확인하고, 우선순위나 담당을 바꿔야 하면
팀장에게 조율을 요청한다.

작업 중 발견한 팀 공통의 전제 변경이나 다른 작업과의 충돌은 조기에 알린다. 단순한 도움 요청과 과제 범위·담당·일정의 변경을
구분하고, 전체 계획에 영향을 주는 변경은 팀장과 조율한다.

### 보조 워커

보조 워커는 정해진 범위의 과제를 수행하고 요청자에게 결과를 돌려준다. 관측한 사실, 수행한 검사와 그 결과,
해결하지 못한 문제를 구분해 보고한다. 범위 밖에서 발견한 내용은 요청자에게 알리고, 추가 과제는 기존 배정과 조율한다.

보조 역할이라는 이유로 다른 워커와 대화할 수 없는 것은 아니다. 필요한 상대와 직접 협의할 수 있으며,
수행 중인 과제의 책임자와 보고 흐름을 유지한다.

## 5. 일회성 서브에이전트와 지속적인 워커

한 번의 요청과 결과로 끝나는 작은 작업에는 하네스의 서브에이전트를 활용할 수 있다. 해당 호출을 맡긴 에이전트가
결과를 회수하고 통합한다. 모든 서브에이전트를 별도의 XSM 구성원으로 등록할 필요는 없다.

문맥을 유지하면서 여러 차례 협의하거나, 독립적인 진행 상태와 주소를 가지고 병렬 작업을 이어갈 상대는 지속적인 워커로 둔다.
팀장이 처음부터 여러 보조 워커를 같은 깊이에 두고, 주력 워커에게 필요한 협업 상대를 지정할 수 있다.

워커가 다시 워커를 만드는 생성 계층을 계속 늘리면 요청 배경의 전달, 결과 회수, 담당과 진행 상태의 추적에 드는 소통 비용이
커진다. 이 가이드는 얕은 생성 계층과 수평적인 역할 배정을 권장하며, 그보다 깊은 재귀 위임은 권장하지 않는다.

XSM이 생성하는 워커는 팀장을 깊이 0, 그 아래 워커들을 깊이 1로 세면 이 수평 구성에 해당한다.
`max_depth`의 기본값 1은 이러한 구성과 맞는다. 하네스 내부 서브에이전트와 Orca 같은 외부 도구가 생성하는 워커의 한도는
각 실행 환경이 관리하며, XSM의 생성 깊이 제한과 동일하게 취급하지 않는다.

## 6. DM·보드·보고의 역할

| 상황 | 사용하는 경로 |
|---|---|
| 일을 요청하거나 질문하고 결과를 회신한다 | 해당 세션 또는 선택한 수신자에게 DM |
| 팀 전체에 유효한 계획·결정·담당·진행을 남긴다 | 팀 보드 |
| 전체 진행과 사용자의 판단이 필요한 사항을 전달한다 | 팀장이 사용자에게 보고 |
| 세션이 맡은 역할과 작업 맥락을 다른 세션으로 넘긴다 | 기록을 정리한 뒤 XSM 인수인계 절차 |

보드는 현행 공동 상태이고, DM은 행동과 응답을 요청하는 경로다. 같은 상태를 두 곳에 중복 관리하지 않는다.
변경된 결정에 따라 누군가 행동해야 하면 DM에서 관련 보드 항목을 가리키고 구체적인 요청을 전달한다.

진행 보고에는 무엇을 끝냈는지, 어떤 근거로 확인했는지, 무엇이 남았는지, 누구의 응답이나 판단이 필요한지를 담는다.
단순한 전달 확인이나 답변 수신을 과제 완료와 구분한다. 합의한 완료 기준에 필요한 검사를 수행하고,
미실행·실패·미해결 사항을 실제 결과와 함께 남긴다.

## 7. 복수 팀의 느슨한 협업

큰 작업을 동시에 관리할 때는 목표나 책임 영역별로 팀을 나눈다. 각 팀은 자신의 팀장·워커·보드를 가지고 독립적으로 진행한다.
각 팀장이 자기 팀의 계획을 유지하므로, 모든 세부 작업을 한 팀장의 대화 문맥에 모을 필요가 줄어든다.

팀 사이에는 공통 결정, 인터페이스와 의존성의 변경, 다른 팀에 영향을 주는 제약, 인계할 결과처럼 필요한 정보를 공유한다.
보통 팀장끼리 조율하되 담당 워커들이 직접 협의할 수 있다. 협의 결과 중 각 팀의 계획에 영향을 주는 내용은 해당 팀의
보드에 반영한다. 모든 팀에 같은 진행 보고를 반복해서 보내지는 않는다.

팀장들만 함께 참여하는 별도의 조율 팀을 둘 수도 있다. 예를 들어 API·저장소·UI 팀의 팀장들이 각각 자기 작업 팀과
조율 팀에 함께 속한다. 조율 팀의 다중 수신 DM은 팀장 간 소통 채널이 되고, 그 팀의 보드에는 팀 간 합의와 의존성을 남긴다.
각 팀장은 합의에 따른 자기 팀의 담당·계획 변경을 작업 팀 보드에 반영하고 원래 합의 항목을 가리킨다.

| 팀 | 구성원 | 공유하는 상태 |
|---|---|---|
| API 팀 | API 팀장과 해당 워커들 | API 개발의 계획·담당·진행 |
| 저장소 팀 | 저장소 팀장과 해당 워커들 | 저장소 개발의 계획·담당·진행 |
| UI 팀 | UI 팀장과 해당 워커들 | UI 개발의 계획·담당·진행 |
| 조율 팀 | 위 세 팀의 팀장들 | 공통 인터페이스·팀 간 의존성·통합 시점 |

조율 팀의 팀장들은 동등하게 협의할 수 있다. 이 관계는 같은 세션들의 다중 소속으로 구성하며, 별도의 상위 지휘자나
추가 생성 깊이를 요구하지 않는다. 팀은 독립적인 실행 단위로 유지하면서 필요한 조율 관계를 겹쳐 둘 수 있다.

정보는 통신이 허용된 상대에게 DM으로 전달하고, 필요한 보드 항목이나 산출물을 가리킨다. 여러 팀이 있다는 이유만으로
상대 팀의 모든 상태를 읽거나 모두에게 메시지를 보낼 권한이 자동으로 생기지는 않는다.

## 8. 자연어로 관계를 지정하는 예

### 권장 개발 팀 구성

> 이번 작업은 장기적으로 병렬 진행할 개발 과제다. 너는 팀장을 맡아 목표·완료 기준·계획과 진도를 관리해라.
> 팀장 모델은 fable/astra급으로, 주력 워커 A와 B는 opus/sol급으로 구성한다. 보조 워커 C와 D는
> haiku max/luna max급으로 두고 모두 같은 생성 깊이에 배치한다. A는 구현, B는 검토와 통합 검증,
> C는 관련 코드 조사, D는 범위가 명확한 반복 검사를 맡는다. A와 B는 C·D에게 직접 협업을 요청해도 된다.
> 요청마다 결과를 받을 상대를 지정하고, 기존 배정이나 우선순위가 충돌하면 팀장과 조율해라.
> 현행 계획·결정·담당·진행은 팀 보드에 유지하고, 전체 결과는 팀장이 통합해 보고해라.

### 워커에게 역할 전달

> 너는 이 팀의 주력 워커 A다. 맡은 범위는 캐시 계층 구현이고, 완료 기준은 합의한 동작과 관련 검사 통과다.
> 보조 워커 C에게 기존 구현 조사를 요청할 수 있다. C의 결과를 검토하고 네 작업에 통합해라.
> 구현 세부 사항은 직접 판단하되 공용 인터페이스나 다른 워커의 담당을 바꿔야 하면 팀장과 조율해라.
> 진행과 막힘, 완료 결과는 팀장에게 보고해라.

### 독립적인 여러 팀

> API 팀과 저장소 팀은 각자의 팀장과 보드로 독립적으로 진행해라. API 계약과 데이터 모델 변경처럼 서로에게 영향을 주는
> 사항은 담당 워커끼리 협의하고 각 팀장에게 알려라. 합의한 변경은 각 팀의 보드에 반영하고,
> 충돌하는 우선순위와 해결되지 않은 쟁점은 팀장들이 조율해라. 두 팀장은 자기 팀과 함께 별도의 조율 팀에도 참여해라.
> 조율 팀에서는 동등하게 협의하고 팀 간 합의·의존성·통합 시점을 보드에 남겨라. 각 팀장은 그 합의를 가리켜
> 자기 팀의 계획을 갱신해라.

### 수평적 의회형 조직

> 세 세션은 동등한 구성원으로서 설계안을 검토한다. 제안과 근거는 팀 보드에 남기고, 구체적인 질문과 반론은 DM으로 교환해라.
> 세 구성원 모두가 동의한 안을 합의로 기록하고, 합의되지 않으면 쟁점과 각 입장을 사용자에게 보고해라.
> 제품의 구성원 관리나 승인 처리를 맡은 세션이 있다는 이유로 그 세션에 설계상의 최종 결정권을 부여하지 않는다.

이 예문들은 조직과 역할을 설명하는 지시다. 실제 모델 선택·세션 생성·팀 등록·사용자 승인에는 각각의 도구와 절차를 따른다.

## 9. 적용 범위와 관련 안내

이 문서는 조직을 구성하고 운영하는 공통 지침이다. 작성만으로 기존 세션에 역할을 주입하거나,
설치된 스킬·워커 기본 모델·깊이 설정을 변경하지 않는다. 에이전트가 참여할 때에는 선택한 조직과 자신의 역할을 전달해야 한다.

업무 지시와 사용자 승인은 구분한다. 팀장이나 동료의 요청은 기존에 허용된 범위에서 일을 진행하는 근거이며,
사용자에게 받아야 하는 승인을 대신하지 않는다. 팀장 중심 조직에서는 필요한 사용자 판단을 팀장이 취합한다.
다른 조직에서는 그 창구를 명시하고, 실제 승인 전달과 기록은 제품의 절차에 맞춘다.
