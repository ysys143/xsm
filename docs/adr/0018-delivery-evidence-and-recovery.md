# ADR-0018: 전달 증거와 메시지 복구를 같은 수명 계약으로 관리한다

- 상태: Proposed
- 관련 목표: G2, G3, G4
- 작성일: 2026-10-24
- 비교 근거: [Reason 비교 노트](../references/reason.md)
- 기존 결정 효력: 이 문서는 아직 Accepted ADR을 대체하지 않는다.

## 질문

전송 요청·저장·문맥 인계·회신·과제 결과를 혼동하지 않으면서 취소·중단·재시작·오프라인을 어떻게 복구할 것인가?

## 맥락

Reason은 SQLite 우편함·outbox, 명시적 Delivered 확인, 전달 중 중복 노출 억제와 확인 기한, 대기 취소, 재접속 후 재등록을 구현한다. [store.rs](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/store.rs), [mail.rs](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/daemon/mail.rs), [client.rs](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/client.rs).

그러나 일반 Codex 표본에서는 실제 queue 실행 전에 등록된 것 같은 문구를 반환했고 나중에 실패했다. 내부 read_at도 모델의 이해를 증명하지 않는다. 이 설계는 배울 복구 경로와 고쳐서 받아들일 상태 표현을 함께 제공한다.

요청과 답을 먼저 기록한 뒤 확인하고 재송신하는 저널 방식도 비교했다. 메시지 중복 제거나 저장된 답의 재사용이 업무 부작용의 exactly-once를 보장하지는 않는다.

xsm에는 이미 [ledger](../../xsm/ledger.py)의 queued·unknown·수신 영수증·outcome, [send](../../xsm/send.py)의 동일 ID 재전송, [receive](../../xsm/receive.py)의 ID·발신자·본문 대조, [remote](../../xsm/remote.py)의 확인 불명 조정이 있다. outbox.py는 승인 전 보관이며 Reason의 원격 전송 outbox와 의미가 다르다. 수신함 조회와 훅의 기록 시점도 대조해야 한다.

## 선택지

| 안 | 방식 | 이점 | 비용·위험 |
|---|---|---|---|
| A | 기존 상태·복구 기능을 개별 경로에서 유지 | 변경이 작음 | 경로마다 증거와 대기 의미가 달라질 수 있음 |
| B | 상태 증거·확인·재전송·수명 계약을 통일하고 기존 저장소 위에 구현 | 진단과 복구가 일관됨 | 상태 전이·원자성·이전 레코드 해석 필요 |
| C | Reason의 SQLite·데몬 구조를 통째로 채택 | 한 저장소에서 트랜잭션 가능 | 기존 파일 기반 경로·0003·마이그레이션 비용 변화 |

## 제안 계약

B를 제안한다. SQLite 채택은 별도 근거가 필요하며 이 문서가 저장소 변경을 확정하지 않는다.

- 상태는 무엇이 관측됐는지를 나타낸다. 최소한 발신 의도 보관, 전송 시도, 원격 저장, 런타임 인계 확인, 보류/거부, 확인 불명을 구분한다. 기존 status를 바꿀 때는 호환 매핑과 원 증거를 보존한다.
- native queue 성공 전에 queued-into-runtime을 확정하지 않는다. 정적 능력과 이번 시도의 관측 결과를 분리하고 실패 시 수신 능력 하향과 회수 경로를 함께 표시한다.
- 수신 확인은 모델이 이해·실행·성공했다는 뜻이 아니다. 답과 task outcome은 별도 축이며, 작업 성공 보고와 독립 검증도 다르다.
- 먼저 보관하고 확인한다. 문맥 인계 중인 메시지는 같은 경로의 동시 조회에서 중복 노출을 억제하고, 확인이 없으면 다시 회수 가능하게 한다. 중복 처리에 대한 의미는 at-least-once이며 업무 부작용의 exactly-once를 약속하지 않는다.
- 대기 취소·클라이언트 종료는 미독 삭제나 상대 과제 취소가 아니다. 대기 중 push 억제가 풀려야 하며, 결과를 못 넘긴 메시지는 다시 회수할 수 있어야 한다.
- 재시도는 원 ID·발신 신원·대상 신원·전체 본문 다이제스트를 검증한다. 200자 미리보기만으로 같은 본문이라고 판정하지 않는다. 확인 불명은 조회·조정한 뒤 재시도한다.
- 자동 재시도는 조회와 변경 요청을 구별한다. 소비하는 조회도 변경으로 취급하며, 연결이 끊긴 변경은 대상과 의도한 상태를 다시 확인한 뒤 복구한다. 현재 어떤 팀/연결이 존재한다는 사실만으로 요청한 대상에 적용됐다고 판정하지 않는다.
- 수명은 요청·대화·보류·첨부별로 명시한다. 오프라인 대기, 재개 대상, 만료 시점과 처리 결과를 발신자에게 알린다. 새 동명 대화가 과거 대화의 메시지를 물려받는지는 0017의 결정에 따른다.
- FYI는 저장과 깨우기를 분리한다. 자연스러운 소비 시점까지 실제로 읽히는지 검사하며, 조용히 저장됐다는 사실만으로 후속 전달 성공을 판정하지 않는다.
- xsm이 소유한 헤드리스 수신자는 업무 수신 확인 전에 복구 가능한 요청을 보관하고, 결과 생성 뒤 회신 실패에는 결과를 재사용한다. 답장 실패가 곧 과제 재실행이 되지 않게 한다. 사용자가 연 일반 세션과 기성 하네스의 업무 수명은 임의로 인수하지 않는다.

각 증거가 허용하는 표현을 고정한다. 기존 status 문자열과 새 증거 필드의 구체 매핑은 호환 설계에서 결정한다.

| 증거 | 허용하는 판단 | 별도로 필요한 증거 |
|---|---|---|
| 로컬 요청 보관 | 원문과 ID가 복구 가능함 | 전송·원격 저장 |
| 전송 명령 접수 | 전송 시도를 시작함 | 명령 성공·대상 수신 |
| 인증된 상대 저장 ack | 상대 우편함에 저장됨 | 하네스 문맥 인계 |
| 네이티브 큐·소켓·훅 인계 확인 | 해당 런타임 경로에 인계됨 | 모델 이해·업무 실행 |
| 요청에 연결된 실제 회신 | 상대가 회신함 | 과제 성공·답의 정확성 |
| 명시적 task outcome | 수신자가 해당 결과를 보고함 | 독립 검증 |
| 발신자의 독립 검사 결과 | 명시된 검사 범위에서 확인됨 | 검사하지 않은 전체 동작 |

held/refused/expired/unknown은 위 단계를 임의로 올라가는 근거가 아니다. 수신 능력 하향은 앞으로의 전달 예측을 바꾸며, 과거 인계 증거를 소급 생성하거나 지우지 않는다.

## 기존 결정과 이행

0002의 영수증 원칙과 0011의 task outcome을 유지한다. 기존 원장 필드는 읽을 수 있어야 하며 새로운 상태/증거 필드는 버전 또는 지원 능력으로 식별한다. 기존 기록에서 입증되지 않은 read·runtime-confirmed를 소급 생성하지 않는다.

## 수용 검사

- A18-01: queue 실행 실패·소켓 쓰기 성공 뒤 수신 실패를 주입하면 런타임 도달 성공으로 보고하지 않는다.
- A18-02: 확인 직전 수신 클라이언트 종료와 대기 취소를 재현해 미독을 회수한다. 정상 확인 뒤 같은 메시지가 반복 실행되지 않는지도 별도로 확인한다.
- A18-03: 같은 ID의 같은 본문은 중복 처리하지 않고, 같은 ID의 다른 본문·발신자·대상은 거부한다. 앞 200자만 같은 두 본문도 검사한다.
- A18-04: 데몬 또는 클라이언트 재시작 뒤 원 ID와 대화 이름이 유지된다. 저장 중 강제 종료·확인 유실을 검사한다. 변경 요청 직전·직후 연결을 끊어 조회만의 자동 재시도와 대상 상태 readback을 대조한다.
- A18-05: 추가 사용자 프롬프트 없이 일반 Codex 다중 홈 수신과 실제 회신을 확인한다. 이전 Reason 실패 표본을 통과한 것으로 간주하지 않는다.
- A18-06: FYI를 보낸 뒤 다음 자연 소비 시점에서 읽히는지 확인한다. unread 저장만 성공한 경우와 분리한다.
- A18-07: offline·held·expired·refused·unknown·succeeded를 서로 바꿔 보고하지 않는다. 시간 역행과 이전 버전 레코드를 검사한다.
- A18-08: 소유한 수신자를 요청 보관 직후·수신 확인 직후·답 보관 직후·회신 직후에 각각 종료한다. 재개 시 요청·답의 중복과 과제 부작용을 관찰하고, 이미 저장된 답을 보내기 위해 과제를 다시 실행하지 않는다.

## 비용과 되돌리기

확인 기록·다이제스트·만료 이력과 복구 작업이 늘어난다. 영구 보관은 민감한 본문과 저장 비용을 늘리므로 보존 정책을 정해야 한다. 새로운 상태 필드의 쓰기를 중단해도 기존 요청의 상태와 결과를 조회할 수 있어야 한다. 저장 형식을 바꾸면 복구 가능한 내보내기와 이전 reader 검사를 먼저 둔다.

## 미결 매개변수

인계 확인 기한·재시도 간격·최대 보존·사용자 우편함 수명·본문 보존 범위·첨부 만료의 관계는 실측과 사용자 판단이 필요하다. Reason의 90초·하루 등의 값을 xsm 기본값으로 채택한 것은 아니다.
