# ADR-0015: 연결 의도와 참여 범위를 실행 가능한 계약으로 잇는다

- 상태: Proposed
- 관련 목표: G1, G2, G5
- 작성일: 2026-10-24
- 비교 근거: [Reason 비교 노트](../references/reason.md)
- 기존 결정 효력: 이 문서는 아직 Accepted ADR을 대체하지 않는다.

## 질문

사용자가 원하는 세션 간 협업을 의도·자격·범위 확인에서 실제 연결과 보관 요청 전송까지 어떻게 이어갈 것인가?

## 맥락

Reason은 머신의 팀 가입 뒤 등록된 세션을 디렉터리에 올리고 저장소마다 별도 연결을 만들지 않는다. 새 저장소의 세션과 실제 왕복한 이전 표본이 있다. 넓은 가입 범위가 이 편의를 만든다. 팀 가입만으로 모든 업무·파일 접근까지 승인됐다고 볼 수는 없다. [Reason 기본 정책](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/config.rs), [비교 S5](../../deliverables/xsm-reason-live-comparison-2026-10-23.md).

xsm은 같은 저장소와 linked worktree를 자동으로 연결하고, 다른 범위는 프로젝트·폴더 연결·세션별 도달 허용으로 표현한다. [connect.plan_for](../../xsm/connect.py)는 상황에 맞는 계획을 제안하고 [outbox](../../xsm/outbox.py)는 보관 요청을 유지한다. 기능 부재가 문제인 것은 아니다. 실제 사용자 승인 뒤에도 비동기 답이 consent 기록에 없어 정상 재실행과 문서상 대체 입력이 모두 거절된 표본이 있다. 연결 이후 비교는 아직 미검증이다.

[0004](0004-communication-scope.md)의 사용자 결정은 쉬운 연결과 한쪽의 의사 표현을 인정한다. [0013](0013-native-claude-messages-by-scope.md)은 원하는 대화를 구성요소 고장으로 막지 않는다고 정한다. 부모·워커 예외를 전체 협업 토폴로지로 확대하지 않는다.

## 선택지

| 안 | 방식 | 이점 | 비용·위험 |
|---|---|---|---|
| A | 현재 연결 종류와 재실행 절차를 그대로 노출 | 저장 형식·권한 의미 유지 | 에이전트가 절차와 수명을 기억하고 누락을 복구 |
| B | 연결 의도를 받은 뒤 현재 정책을 해석하고 승인·전송을 한 흐름으로 수행 | 내부 프로젝트 지식 없이 협업, 기존 범위와 호환 | 승인 상태·보관 요청·실패 복구의 명시적 결속 필요 |
| C | Reason처럼 네트워크 가입만으로 모든 등록 세션 연결 | 새 저장소 참여가 간단 | 공유 범위와 기본 권한이 바뀌며 기존 승인 범위를 확대할 수 있음 |

## 제안 계약

B를 제안한다. C의 가입 편의는 명시적으로 승인한 협업 집합 안에서 구현할 수 있는지 함께 검증한다.

- 연결 의도는 요청자·대상·업무·허용 통신 범위·수명·사용자 의사 출처를 가진다. 사람의 명령, 하네스의 사용자 응답, 동료의 주장과 자동 검토 결과를 구분한다. 실제 사용자 출처를 확보하지 못한 상태를 승인으로 바꾸지 않는다.
- 도구는 확인 가능한 정보를 채우고 이미 유효한 권한을 재사용한다. 새 권한이나 더 넓은 범위가 필요할 때 그 차이를 사람에게 보여 준다. 사용자에게 내부 프로젝트 이름·ref 문법을 외우게 하지 않는다.
- 사용자 답과 연결 계획·보관 요청을 같은 요청 식별자에 결속한다. 의도 수집 실패, 미응답, 명시적 거부, 승인 후 적용 실패를 서로 다른 상태로 보존한다.
- 승인한 계획을 적용하고 원래 요청을 같은 ID로 전송한다. 적용 직전에 요청·대상·세대·승인 범위가 여전히 일치하는지 대조한다. 적용 중 실패해도 원문을 잃지 않는다. 승인 범위가 달라지지 않은 재시도는 다시 동의를 요구하지 않는다. 권한 철회는 이후 전송에 반영한다.
- 형제 세션과 다른 부모의 세션도 동일한 범위 규칙을 사용한다. 연결 계획은 시작 계보에 의해 임의로 달라지지 않는다.
- 원격에서는 머신 인증·팀 가입과 해당 사용자가 업무를 허용할 권한을 각각 확인한다. 같은 머신의 uid 경계를 원격 사람에게 그대로 확장하지 않는다.

제안하는 내부 상태의 관측 의미는 다음과 같다. 모델이 이 상태를 수동으로 갱신하는 API를 요구하는 것은 아니다.

| 상태 | 진입 근거 | 다음 동작 |
|---|---|---|
| 의도 수신 | 사용자 요청 또는 업무상 필요한 동료 연결 요청을 기록 | 대상·기존 자격·필요 범위를 해석 |
| 사람 판단 필요 | 기존 권한으로 부족한 차이를 확인 | 요청 원문과 열릴 범위를 한 질문에 결속 |
| 승인 확인 | 확인 가능한 사용자 응답이 해당 요청과 일치 | 연결 적용. 반복된 같은 응답은 같은 결과 참조 |
| 연결 적용 중 | 승인한 계획의 적용을 시작 | 성공하면 같은 ID의 보관 요청 전송, 실패하면 복구 상태 유지 |
| 연결 활성 | 승인한 범위가 실제 적용됨 | 범위·수명·철회에 따라 전송 |
| 거부·취소·만료·확인 불명 | 각 원인에 해당하는 직접 증거 | 원 요청 보존과 이유 표시. 서로의 상태로 바꾸지 않음 |

## 기존 결정과 이행

0004의 범위 데이터를 읽는 호환 계층부터 설계한다. 기존 연결을 새 권한으로 재해석해 넓히지 않는다. 일회성 요청을 폴더 전체의 지속적 연결로 자동 확대하지 않는다. 다만 일회성 권한이 기본이라는 결정도 아직 하지 않았다. 새로운 연결 단위·기본 수명을 정하면 0004를 대체하거나 보완하는 사용자 결정이 필요하다. 0009의 이미 폐기된 세션 핸드셰이크를 복원하지 않는다.

## 수용 검사

- A15-01: 같은 저장소·linked worktree는 추가 질문 없이 기존처럼 왕복한다.
- A15-02: 새 저장소 연결의 비동기 사용자 승인 원문이 요청에 연결되고, 정상 API로 승인 반영·연결·원 요청 전송까지 끝난다. 이전 S5 실패를 먼저 재현하고 같은 경로로 검증한다.
- A15-03: 승인 수집 어댑터를 끊으면 승인 여부는 unknown으로 남고 원문·복구 위치가 보인다. 기록 파일이 없다는 이유로 임의 문장을 승인하지 않는다.
- A15-04: 거부·취소·추가 질문은 연결을 만들지 않는다. 늦은 유효 응답과 중복 응답은 0020 계약을 따른다.
- A15-05: 별도 부모의 두 워커가 승인된 같은 협업 범위에서 직접 조율한다. 부모의 수동 중계가 필요하지 않다.
- A15-06: 요청 하나에 대한 동의로 다른 세션·폴더·업무 권한이 추가되지 않는다. 철회·재개 시 수명 계약을 적용한다.

## 비용과 되돌리기

의도와 기존 범위 설정 사이의 번역, 승인 대기 상태, 복구 어댑터를 유지해야 한다. 표시를 단순화해도 실제 권한 차이는 설명해야 한다. 되돌릴 때 기존 scopes/links와 보관 요청을 유지하고 새 의도 레코드는 읽기 전용 이력으로 남긴다. 자동으로 만든 연결의 소유·철회 이력이 필요하다.

## 미결 매개변수

기본 연결 단위와 수명, 업무 종료를 판단하는 주체, 재개 후 승인 재사용 범위, 머신 가입이 기본 공개할 메타데이터는 사용자와 논의해야 한다. 현 단계에서 임의 TTL이나 영구 연결을 확정하지 않는다.
