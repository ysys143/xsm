# ADR-0014: 공유 메시지 풀과 시각 대시보드

- 상태: Discussing
- 관련 목표: G4, G6
- 작성일: 2026-10-03

## 질문

여러 기계의 세션 기록을 한곳에 모아 사람이 보는 공유 메시지 풀과 대시보드를 도입할 것인가. 도입한다면 Buzz를 쓸 것인가, 직접 만들 것인가, 그리고 xsm과는 어떤 관계로 둘 것인가.

## 맥락

### xsm의 현재 상태

- **원격.** SSH로 짝지은 프로젝트끼리 이미 떠 있는 세션에 메시지를 보낼 수 있다(ADR-0007). 원격 짝은 이름 붙인 프로젝트로만 맺는다. 원격 세션은 `xsm list`에 나오지 않고, 별도 명령 `xsm remote sessions <호스트>`로 조회한다. 원격 수신기가 처리하는 op는 `send`, `ping`, `ping-back`, `status`, `unpair`, `sessions`이고, `sessions`는 짝지은 프로젝트의 살아 있는 세션 이름·ref·런타임만 돌려준다(`xsm/remote.py:357-380`).
- **기록.** 채널과 공동 문서는 기계마다 따로 있고 공유되지 않는다(`docs/xsm/README.md` "알려진 한계"). 보존 기간이 다르다. 채널은 정리하지 않고, 원장과 보류 본문은 30일, 멈춘 세션 기록은 7일 뒤 정리한다(`xsm/housekeeping.py:27`).
- **사람이 보는 수단.** 모두 CLI다. `/xsm log`, `xsm ledger`, `xsm held`, `xsm channel show`, `xsm workers`, `xsm approvals`, `xsm metrics`, 상태줄이 있다. `xsm otlp-export`는 자체 텔레메트리를 OTLP 수집기(Grafana, Jaeger 등)로 보내고, 원격 전달은 traceparent로 기계 사이 추적을 잇는다(ADR-0011).
- **기계가 읽는 출력.** `--json`은 `list`, `who`, `send`, `status`, `ledger`, `metrics`, `doc` 등에 있다. `channel`, `held`, `workers`, `approvals`에는 없다(`xsm/cli.py:2095-2355`).
- **세션이 아닌 발신자는 보낼 수 없다.** `xsm send`는 등록된 세션이 아니면 "this session is not registered"로 거부한다(`xsm/send.py:114`). cron이나 보드 서버, 브리지 같은 일반 프로세스는 지금 보낼 수 없다. 같은 문제를 Comma의 Salix는 Loops로 푼다. 작은 감시 프로그램이 상시 돌다가 필요할 때만 에이전트를 깨우고, 10분당 깨우기 횟수에 한도를 둔다(`docs/references/salix.md` 4장).
- **오늘의 기준선.** 사용자 SSH로 `ssh jaesol-macmini xsm channel show` 같은 원격 조회는 이미 된다. 별도 구현 없이 다른 기계의 기록을 볼 수 있는 방법이다.
- **파일 전송은 xsm 밖에서 된다.** 사용자 SSH 키로 에이전트가 `scp`·`rsync`로 보내고 `xsm send`로 알리면 된다. xsm 짝짓기 키는 `authorized_keys`의 강제 명령으로 수신기만 실행하므로 파일 전송에 쓸 수 없다. macOS 쪽은 sshd가 띄운 프로세스가 `~/Documents` 같은 보호 폴더에 접근하지 못한다(2026-09-22 실측).

### ADR-0005와의 관계

ADR-0005는 채널 원본을 `~/.xsm/channels/`에 두고 buzz·Slack 어댑터를 넣지 않기로 했다. 다시 열 조건 중 하나가 "다른 기계·다른 사람과 원본을 나눠야 할 때(ADR-0007과 함께)"다. 아래 선택지 중 B와 C는 원본을 다른 곳으로 옮기거나 복제하므로 이 조건에 해당한다. A는 원본을 읽기만 하므로 ADR-0005의 결정을 바꾸지 않는다.

ADR-0005 critic의 경고도 그대로 유효하다. 채널에 어댑터, export, 태그 보기, 멘션을 다 합치면 기능이 Buzz에 가까워지고 범위가 슬금슬금 커진다. 멘션으로 깨우면 N:N 채널에서 호출이 N²이 되고 답글 멘션이 루프가 된다. 로그에 비밀이 새는 문제는 미해결로 남아 있다.

### 사용 사례

YouTube 영상 "공짜 Slack인 Buzz 도입 전후 비교: AI 에이전트 관리가 이렇게 쉬워졌다고?"(제로초)의 전사본을 2026-10-03에 검토했다. 전사본은 저장소에 두지 않았다.

- 화자는 VPS 2대, 맥북, 윈도우까지 4대에 운영 봇(Hermes, OpenClaw)을 하나씩 두고, 24시간 켜진 VPS에 Buzz를 셀프 호스팅해 허브로 쓴다.
- 봇끼리 채널에서 서로 호출하고 파일을 주고받으며, 사람이 그 대화를 지켜본다. 코딩은 Buzz 밖에서 Codex 원격 연결로 한다.
- 가장 큰 불만은 "봇을 불렀는데 응답이 없다"였고, 화자는 API 비용 제한 설정을 원인으로 든다.
- 이 환경에는 xsm이 지원하지 않는 Windows가 있고, 대상도 사람이 띄운 코딩 세션이 아니라 상주 운영 봇이다. 이 사용자의 필요와 같지 않다. 영상 속 주장은 실측하지 않았다.

### Buzz

- **저장소(2026-10-03, GitHub API).** 라이선스 Apache-2.0, 별 35,431개, 커밋 2,799개, 마지막 푸시 2026-10-03. 언어별 바이트는 Rust 26MB, TypeScript 15.5MB, Dart 6.5MB, JavaScript 5.4MB, Swift 0.7MB다. crate 33개와 데스크톱(Tauri), 모바일(Flutter), 웹, 관리자 웹으로 이뤄진다. 핵심은 Nostr 이벤트 로그이고 신원은 Nostr 키다(`docs/references/buzz.md` 1절).
- **운영 부담.** 기본 compose는 relay, PostgreSQL 17, Redis 7, MinIO이고 relay가 MinIO에 의존한다(상류 `docker-compose.yml`, 2026-10-03). RAM은 최소 2GB, 권장 4GB이고, 게시자마다 Nostr 키쌍이 필요하다(`docs/references/supplement/T5-buzz-channel.md` 1.3절, 117-128행).
- **에이전트 연동(상류 `crates/buzz-acp/README.md`, 2026-10-03).** `buzz-acp`는 relay에서 @멘션을 받으면 ACP 에이전트를 자기 하위 프로세스로 띄워 stdio로 프롬프트를 넘긴다. goose, Codex(`codex-acp`), Claude Code(`claude-agent-acp`)를 지원한다. 에이전트는 Buzz CLI로 답하고, 죽으면 harness가 다시 띄운다. 즉 Buzz가 부르는 에이전트는 harness가 소유한 별도 프로세스이고, 사람이 터미널에서 띄운 TUI 세션이 아니다(`docs/references/acp.md` 1장). 이 경로를 xsm 쪽에서 실행해 보지는 않았다.
- **이벤트 종류.** 워크플로 승인 요청·승인·거부(kind 46010-46012), 작업 요청(43001), presence 등이 있다(`docs/references/buzz.md` 115행, `crates/buzz-core/src/kind.rs:442-582`). relay가 비표준 kind를 받아 화면에 보여 주는지는 확인하지 않았다.
- **클라이언트 수단.** `buzz` CLI는 REST와 NIP-98 서명을 쓰는 실행 파일이다. `buzz-ws-client`는 Rust WebSocket 클라이언트이고, `buzz-sdk`는 네트워크 호출 없는 이벤트 빌더다. 둘 다 Rust 워크스페이스의 path 의존성이라 Python인 xsm 쪽에서는 CLI를 하위 프로세스로 부르는 것이 현실적이다.

## 선택지

어느 안이든 xsm은 전달·깨우기·동의를 맡는 핵심으로 남고, 보드는 xsm 밖의 별개 구성 요소다. ADR-0003 기준 2("보조 구성 요소는 선택 사항이다")가 이미 이런 구성 요소를 허용한다.

### X1. Buzz만 쓴다 (기각 권고)

- 방식: 세션을 Buzz 멤버로 초대하고, 호출과 기록을 모두 Buzz로 한다.
- 기각 권고 이유: Buzz는 Claude Code·Codex를 `buzz-acp`의 하위 프로세스로 새로 띄울 뿐, 사람이 띄운 TUI 세션을 깨우지 못한다. xsm이 풀어 둔 inbox 소켓, `codex queue`, Esc로 멈춘 스레드 깨우기, 보류 예측을 Buzz 쪽에서 다시 만들어야 한다. 프로젝트 범위와 사람 승인 모델도 사라진다.

### X2. 에이전트가 xsm과 Buzz를 둘 다 직접 쓴다 (기각 권고)

- 방식: 유튜버처럼 세션을 Buzz 멤버로도 두고, xsm도 그대로 쓴다.
- 기각 권고 이유: 호출 경로(`xsm send`와 Buzz 멘션), 기록 원본, 신원(세션 ref와 Nostr 키)이 이중화된다. Buzz 채널을 거치면 xsm의 범위와 승인을 우회할 수 있다. 에이전트가 매번 어느 도구를 쓸지 골라야 한다.

### X3. xsm 자체를 확장한다 (기각 권고)

- 방식: 원격 채널 동기화, 웹 화면, 멘션 호출을 xsm 패키지 안에 넣는다.
- 경과: 라운드 2에서 ADR-0003(핵심 경로의 상주 런타임 금지)을 근거로 기각했다. 라운드 4에서 사용자가 "보드는 별개 제품"이라고 하자 이 근거가 보드에는 적용되지 않게 됐다. 남는 차이는 위치뿐이다. 같은 기능을 xsm 안에 두면 xsm 설치·갱신·doctor가 웹 서버와 함께 움직이고, 보드 장애가 xsm 장애로 보인다. 기능 면에서는 B와 같으므로 B로 흡수한다.

### D. 지금은 하지 않는다

- 방식: 보드를 만들지 않는다. 다른 기계의 기록이 필요하면 사용자 SSH로 `ssh <호스트> xsm channel show`, `xsm ledger --json`을 부른다. 빠진 `--json`만 채운다.
- 장점: 새 구성 요소와 새 노출이 없다. 필요가 실제로 얼마나 자주 생기는지 잴 수 있다.
- 단점: 여러 기계를 한 화면에서 보지 못한다. 휴대폰에서 보기 어렵다.

### A. 초간결 보드

- 방식: xsm 기록(레지스트리, 메시지 원장, 채널, 보류, 워커, 승인 대기)을 읽어 보여 주는 읽기 전용 웹 뷰다.
- 보여 줄 것: 기계별 세션 목록, 채널 스레드, 메시지 전달 상태(`delivered`, `sent-unconfirmed`, `held`), 보류 메시지, 워커와 승인 대기.
- 다른 기계의 기록을 가져오는 방식(A 전용 쟁점):

| 방식 | 내용 | 신뢰 범위 |
|---|---|---|
| A-1. 원격 읽기 op | xsm 원격 수신기에 채널·원장 읽기 op를 추가한다. `sessions`처럼 짝지은 프로젝트로 거른다 | xsm 짝 키로 읽을 수 있는 것이 늘어난다. ADR-0007 재개가 필요하다. 보류·워커·승인 대기는 지금 프로젝트 필터가 없어 그대로는 넣을 수 없다 |
| A-2. 사용자 SSH 미러 | 보드 기계가 사용자 SSH 키로 상대의 `~/.xsm` 일부를 `rsync`로 한 방향 복사한다 | xsm에는 새 동작이 없다. 사용자 SSH로 이미 가능한 범위다. 범위 필터가 없어 모든 프로젝트가 보인다 |
| A-3. 기계별 보드 | 기계마다 loopback에 보드를 띄우고, 필요할 때 SSH 포트 포워딩으로 본다 | 원격 노출이 없다. 한 화면에 합쳐지지 않는다 |
| A-4. 정적 HTML | 기계마다 `xsm channel export`를 넓혀 정적 HTML을 만들고, 사람이 연다 | 리스너가 없다. 실시간이 아니다 |

- 장점: xsm 기록을 변환 없이 그대로 보여 준다. 만들 것이 가장 적다.
- 단점: 보기만 한다. 휴대폰에서 지시하거나 보드에서 승인할 수 없다. 사람용 기능(검색, 파일, 다중 사용자)이 없다. 원격 수집 방식(A-1, A-2)은 B·C로 가면 쓰이지 않는다. B·C는 기계마다 커넥터나 브리지가 기록을 올리는 방식이기 때문이다.
- 운영 비용: 보드 프로세스 하나 외에 A-1은 프로젝트마다 사람이 하는 `xsm remote add`, 양방향 SSH, 꺼진 기계의 타임아웃 처리가 따라온다(ADR-0007 critic의 "목록 비용"). 원격 짝은 이름 붙인 프로젝트로만 맺으므로 기본 프로젝트의 원격 기록은 A-1로 보이지 않는다.
- 위험: 읽기 노출. 보드는 여러 프로젝트의 채널과 보류 본문을 한 화면에 합친다. 리스너를 loopback 밖에 열면 같은 네트워크의 다른 프로세스와 다른 기계의 에이전트도 읽을 수 있다. ADR-0004의 범위가 읽기 쪽에서 평평해지고, ADR-0005의 미해결 문제(로그의 비밀)가 화면으로 번진다.

#### A의 형태: macOS 메뉴바·노치 앱 (사용자 제안, 라운드 10)

웹 뷰 대신 메뉴바(또는 노치)에 상주하는 작은 앱으로 만든다. 평소에는 아이콘 하나로 상태를 보이고, 클릭하면 패널이 열린다.

- 참고 앱(2026-10-04, GitHub API와 README):
  - RunCat(`runcat-dev/RunCatNeo` 별 898개, `Kyome22/menubar_runcat` 별 511개, Swift): 메뉴바 아이콘의 애니메이션 속도 하나로 CPU 사용량을 보인다. 정보 하나를 클릭 없이 전한다.
  - CodexIsland(`ericjypark/codex-island` 별 349개, Swift): 노치를 Dynamic Island처럼 써서 Claude Code·Codex 사용 한도를 보인다. 마우스를 올리면 요약, 클릭하면 펼친 패널. 노치가 없는 화면에서는 메뉴바 알약으로 대신한다. CLI가 이미 써 둔 자격 증명과 로컬 기록만 읽는 로컬 우선 앱이다.
  - Codex Island(`Jarcis-cy/codex-island-app` 별 11개, Swift, macOS 15.6+): 노치·메뉴바에서 로컬과 원격 Codex 세션을 보이고 승인을 처리한다. `~/.codex/hooks.json`의 훅과 로컬 유닉스 소켓으로 세션을 지켜보고, 원격은 SSH로 `codex app-server`와 stdio로 말한다.
- 보여 줄 것:
  - 아이콘: 살아 있는 세션 수, 그리고 사람의 손이 필요한 것(보류 메시지, 승인 대기)이 있을 때의 표시. 상태줄(`xsm 2 peers · as builder · 1 held`)과 같은 정보를 화면 밖 어디서나 본다.
  - 패널: 기계별 세션 목록, 세션 사이에 오간 메시지(본문 전체, 답장 관계로 묶은 대화 흐름, 전달 상태), 채널 스레드, 보류와 승인 대기 목록. 오간 메시지를 대화로 보이려면 선행 작업 P3이 필요하다.
  - 알림과 쓰기: 아래 "대시보드 쓰기와 알림" 절.
- 장점:
  - **네트워크 리스너가 없다.** 로컬 파일과 `xsm ... --json`을 읽으므로 경계 계약 6(읽기 노출)이 구조적으로 지켜진다. 웹 뷰의 가장 큰 위험이 사라진다.
  - 철학(라운드 10 당시 README에 추가한 "All you need is a message channel")과 맞는다. 채널을 사람이 들여다보는 창일 뿐, 조율 기능이 아니다.
  - 상태줄은 그 세션의 터미널 안에서만 보인다. 메뉴바는 모든 세션의 상태를 한곳에서, 터미널을 보고 있지 않을 때도 보인다.
- 단점과 제약:
  - macOS 전용이다. xsm은 Linux도 지원하므로 Linux에서는 CLI와 상태줄이 그대로 화면이다.
  - Swift 앱이면 xsm(파이썬 표준 라이브러리)과 다른 빌드·배포·서명 체계를 진다. 파이썬으로 만들면 외부 의존(PyObjC 등)이 생긴다. 어느 쪽이든 xsm 패키지 밖의 별개 제품으로 둔다.
  - 다른 기계의 기록은 A의 수집 방식(A-1~A-4) 문제가 그대로 남는다. 첫 판은 이 기계의 세션만 보인다.
  - 패널에서 승인하거나 보류를 풀면 쓰기 경로가 된다(W1). 그래서 단계로 나눈다. 1판은 보기, 알림, 좁히는 연산이다. 2판은 W1과 아래 미결 사항(보류 해제 재설계, 프로젝트 삭제)이 정해진 뒤 승인, 해제, 삭제를 더한다.
- 주의: Codex Island처럼 별도 `codex app-server`로 원격 스레드를 재개하는 방식은, 사람이 쓰는 TUI와 같은 스레드를 잡을 경우 잠금 없이 분기될 수 있다(`docs/references/README.md` 0.5절). 보드는 읽기만 하고 이 경로를 쓰지 않는다.

#### 대시보드 쓰기와 알림 (사용자 요구, 라운드 12)

사용자는 대시보드에서 프로젝트 삭제, 권한 회수, 승인, 그리고 잠긴 것의 알림과 수동 해제를 요구했다. 사람 판정 기준도 정했다: **GUI 클릭은 사람 입력이다**(Touch ID 등 추가 인증 없음). 아래는 이 요구를 xsm의 현재 연산과 규칙에 대응시킨 것이다. 사용자 요청 네 범주만 다룬다. 넓히는 연산(link, join, unblock, frameworks ignore)은 요청에 없어 넣지 않았다.

**동작 대응표**

| 대시보드 동작 | xsm 연산 | 지금 | 필요한 것 |
|---|---|---|---|
| 링크·reach 회수, 차단, 워커 요청 거부 | `unlink`, `reach --drop`, `block`, `deny` | 누구나. 좁히기 원칙(`xsm/config.py:469`, `xsm/cli.py:490`, `xsm/cli.py:1861`) | 없음 |
| 원격 짝 회수 | `remote remove` | 누구나 | SSH로 상대에 `unpair`를 보내고 상대의 키를 지운다(`xsm/remote.py:298-306`). 다시 맺으려면 사람이 필요하다. 비동기로 실행하고 확인을 한 번 받는다 |
| 보류 메시지 버리기 | `held drop` | 누구나 | 경로 조작 버그를 고쳤다(라운드 13). 삭제 기록 남기기와 화면 확인 한 번은 2판 과제 |
| 워커 권한 승인 | `approve` | 사람 터미널(`/dev/tty`에서 `yes`) 또는 부모 세션과 사용자 답(`xsm/cli.py:1854-1896`) | W1 |
| 보류 메시지 해제 | `held deliver` | 수신 세션과 사용자 답. 본문을 그 세션 셸로 출력(`xsm/cli.py:809-865`) | W1과 전달 방식 재설계(아래, 미결) |
| 프로젝트 삭제 | 없음 | 폴더마다 `leave`를 반복해야 한다. 마지막 구성원이 떠나면 scope가 사라진다(`xsm/config.py:455-456`) | 새 명령. 범위와 문턱은 미결(아래) |
| Claude 네이티브 보류 | 없음 | xsm이 풀 수 없다(ADR-0013) | 알림과 "그 세션 화면에서 Deliver" 안내만 |

grant 회수는 넣지 않는다. grant는 1회용이고 600초 뒤 만료된다(`xsm/workers.py:199`). 만료된 grant 파일을 정리하는 코드가 없다는 점만 미결로 남긴다.

**W1 권고: 클릭을 사람 입력으로 받는 방식 (사용자 결정 전)**

- `human_terminal()`(`xsm/workers.py:963-986`)을 바꾸지 않는다. 대시보드가 pty를 열고 에이전트 표식(`CLAUDECODE`, `CODEX_THREAD_ID` 등) 없이 xsm 명령을 실행하고, 사람이 클릭하면 그 pty에 `yes`를 쓴다. 문턱은 오늘의 사람 터미널과 같다. 기록을 구별하려고 대시보드가 `XSM_VIA=dashboard`를 넣고, xsm은 이 값을 판정에는 쓰지 않고 기록(`via: dashboard`)에만 남긴다.
- 승인 화면에 보인 요청 요약의 다이제스트에 클릭을 묶는다(`consent.digest`와 같은 방식). 잘린 요약을 보고 다른 것을 승인하지 않게 한다.
- 택하지 않는 것:
  - "에이전트 표식이 없으면 사람"으로 판정을 넓히는 것. tty 조건이 빠지면 cron, launchd, `env -i xsm approve`, 비대화 `ssh host xsm approve`가 모두 통과한다. `human_terminal()`을 쓰는 다른 곳(`remote add`의 grant 면제 `xsm/cli.py:2012`, 풀 액세스 워커 `xsm/workers.py:562`, `--dir` `xsm/cli.py:29`, `decision` 작성 `xsm/channel.py:93`)도 함께 열린다. ADR-0013이 Claude 허용 목록에 넣은 명령의 전제("묻고 기다린다")도 깨진다.
  - `--via` 같은 플래그를 판정에 쓰는 것. `--reply` 자기 승인을 막은 것과 같은 이유다.
  - `approvals/*.json`을 직접 고쳐 쓰는 것. 경계 계약 2 위반이다.
- 한계: 같은 uid의 에이전트가 pty를 열거나 GUI를 조작하면 넘는다. 오늘의 판정과 같은 한계다.

**보류 해제의 재설계 (미결)**

지금 `held deliver`를 대시보드의 pty로 부르면 본문이 대시보드로 출력되고, 원장이 `delivered`가 되고, 보류 파일이 사라진다. 세션은 받지 못한다. 재설계의 제약:

- 같은 id로 다시 넣으면 보류 영수증 때문에 "already received"로 막힌다(`xsm/receive.py:386`, `:406`, 수신함 경로 `:742`). 그 앞에 예외를 두면 `check()` 전체(범위, deny, 헤더-소켓 대조)를 건너뛴다.
- 해제 기록이 id만 보면 `_repeat` 주석(`xsm/receive.py:383`)이 경고한 "free pass"가 된다. id, 보낸 ref, 본문 해시, 수신 ref에 묶고, 1회용에 만료를 둔다.
- Claude 수신자는 네이티브 게이트를 다시 거친다(ADR-0013). 발신 세션 없는 주입은 다시 보류될 수 있다. 헤더 없는 네이티브 보류분은 되넣을 xsm 헤더가 없다.
- 후보: 기존 `unchecked` 결정을 써서 "보류 사유에도 불구하고 사용자가 풀었다"를 수신 문맥에 담는다.
- 화면에는 주장일 뿐인 `from`보다 보류 사유를 먼저 보인다.

**프로젝트 삭제와 `leave` (미결)**

- `leave`의 사람 확인은 좁히기 원칙의 예외지만 사용자 결정이다(ADR-0009 결정 1, 2026-09-22). 바꾸지 않는다.
- 새 프로젝트 삭제 명령은 `leave`보다 큰 연산이므로 문턱을 낮추지 않는다. W1의 사람 경로를 요구한다.
- 삭제 범위 후보: config의 scope 항목만 지우고, 채널(ADR-0005, 정리 제외), 문서, 원격 짝의 `local_project`는 남긴다. 기본 프로젝트는 config 항목이 없어 삭제 대상이 아니다. 사용자 결정이 필요하다.

**알림**

대시보드가 지켜볼 소스:

- `~/.xsm/held/*.json`: 보류 메시지. 30일 보존
- `~/.xsm/approvals/*.json`의 `status: pending`: 워커 권한 요청과 폴더 신뢰 화면. 600초 뒤 거부로 끝남(`xsm/workers.py:56`, `:923-927`)
- `~/.xsm/asked/*.pending.json`: 응답 없는 동의 요청. 1800초(`xsm/consent.py:121`)
- `xsm doctor --json`의 `stuck`: 120초 넘게 `queued`인 메시지, `unknown`, `error`
- 원장의 `forecast: hold`: Claude 네이티브 보류 예측. 대화상자가 풀려도 원장은 `queued`로 남으므로 "아마 보류됨"으로만 보이고 시간이 지나면 낮춘다

풀 수 없는 것: Claude 네이티브 보류(안내만), 세션 안에 떠 있는 MCP 양식(`xsm/mcp.py:279-291`, 밖에 흔적이 없다). macOS 알림 기능은 지금 xsm에 없으므로 대시보드 쪽 기능이다.

### B. 자체 중규모 구현

- 방식: 보드의 기본 개념을 처음부터 xsm의 것으로 쓰는 Buzz 비슷한 제품이다. 기계마다 커넥터가 돌면서 그 기계의 xsm 기록을 보드 서버로 올리고, 보드의 요청을 `xsm` 명령으로 실행한다. 보드 서버는 상주하며 기록을 모아 색인하고 웹·모바일 화면을 제공한다.

| 개념 | 보드에서 | xsm에서 |
|---|---|---|
| 멤버 | 세션 주소 그대로(`이름@홈@기계`, ref) | 레지스트리의 세션 |
| 채널 | 프로젝트 범위 그대로 | `xsm join`한 프로젝트의 채널 |
| 글 | 같은 레코드(`id`, `t`, `channel`, `author`, `tag`, `text`, `reply_to`, `root`) | `xsm post` 레코드(`xsm/channel.py:146-147`) |
| 멘션 호출 | 세션을 골라 보내면 `xsm send` 실행 | `note`, `task`, `reply` |
| 전달 표시 | 원장 상태 그대로 | `delivered`, `sent-unconfirmed`, `held` |
| 승인과 결정 | 보드 화면의 양식 | `xsm_approve`, `xsm_decide`, `xsm_grant` |
| 워커 | 목록, 승인 대기, 종료 | `xsm workers`, `approvals` |

- 장점: 에이전트는 계속 xsm만 쓰고, 보드에는 xsm 세션이 멤버로 보이므로 호출 경로와 신원이 이중화되지 않는다. 보드에서 부른 에이전트가 실제로 깨어나고 결과가 `delivered`인지 `held`인지 보인다.
- 단점: 가장 비싸다. 보드 서버, 커넥터, 사람 인증, 화면 전체를 만들고 운영해야 한다. ADR-0005 critic이 경고한 대로 범위가 계속 커져 Buzz를 다시 만들 위험이 있다. 커넥터가 `xsm send`를 부르면 "등록된 세션이 아니다"로 거부되므로 xsm 쪽에 세션이 아닌 발신자 유형이 필요하다(쓰기 경로 선행 작업 W2).

### C. Buzz에 브리지만 붙인다

- 방식: Buzz를 수정 없이 띄우고, 기계마다 xsm 브리지를 둔다. 브리지는 `buzz` CLI로 xsm 기록을 게시하고, 사람의 Buzz 멘션을 `xsm send`로 바꾼다. 에이전트는 Buzz를 모른다.
- `buzz-acp`와의 관계: 사람이 띄운 세션은 브리지를 거쳐 xsm으로 부르고, 상주 운영 봇이 필요하면 `buzz-acp`가 띄우는 에이전트를 쓴다. 두 종류가 같은 채널에 섞이면 멘션이 어느 쪽으로 가는지 사람이 구분할 수 있어야 한다.
- 장점: 모바일 앱, 푸시 알림, 다중 사용자, 검색, 파일 같은 완성된 사람용 기능을 바로 얻는다. Buzz 갱신을 그대로 받는다.
- 단점: Nostr 키와 Buzz 채널로 대응시키는 계층이 필요하다. 세션마다 Nostr 키를 둘지 기계당 하나로 둘지 정해지지 않았다. 운영할 스택이 무겁다. B와 같이 브리지가 `xsm send`를 부르려면 W2가 필요하다.
- 미확인: xsm 고유 상태(보류, 전달 확인, 승인 대기)를 Buzz 화면에 어떻게 보일지. 승인 대기는 Buzz의 워크플로 승인 이벤트(46010-46012)에 대응시킬 수 있어 보이고, 나머지는 일반 메시지나 비표준 kind로 표현해야 한다. relay가 비표준 kind를 받고 화면이 보여 주는지는 시험하지 않았다(스파이크 S-C).
- 포크(권고): 하드 포크는 하지 않는다. 핵심(Nostr 이벤트 로그, Nostr 키 신원)을 xsm 개념에 맞게 고치면 포크로 얻는 것이 화면 코드뿐이다. 상류가 매일 움직이므로 병합 비용이 쌓이고, Rust·TypeScript·Dart·Swift를 한 사람이 유지해야 한다. Buzz 화면에 xsm 고유 요소를 꼭 넣어야 할 때만 상류 위에 작은 UI 패치를 얹는 얇은 포크를 고려한다.

### E. Buzz 상류에 "떠 있는 세션 깨우기"를 기여하고, xsm은 연구용으로 둔다

- 방식: Buzz의 약점(사람이 띄운 TUI를 깨우지 못함)을 Buzz 안에서 고친다. xsm에서 확인한 경로(Claude inbox 소켓, `codex queue`와 `thread/queue/start`)를 Buzz의 에이전트 연동에 넣자는 이슈를 먼저 올리고, 메인테이너가 방향에 동의하면 PR을 낸다. xsm은 이 경로를 실험하고 검증하는 연구 저장소가 된다.
- 상류 상황(2026-10-03 조회):
  - CONTRIBUTING은 작은 수정이 아닌 일, 특히 "사전 논의 없는 완전히 새로운 기능"은 이슈를 먼저 열어 방향을 합의하라고 한다.
  - 열린 이슈가 3,606개다. 최근 병합된 PR 28개 중 18개가 한 사람의 것이다.
  - 가까운 요구가 이미 있다. #3364(RFC: 관리형 에이전트를 기존 저장소·워크트리에서 띄우기, 댓글 4개, 다른 사용자 셋이 같은 필요를 적음), #4658(다른 기계에서 멘션하면 멈춘 에이전트가 깨어나지 않음, 깨우기가 보내는 쪽에서만 구현됨), #8045(자기가 시작한 스레드의 답글을 멘션 없이 듣기). "사람이 터미널에서 띄운 세션에 붙기"를 직접 다룬 이슈는 찾지 못했다(검색어 existing session, attach running, tmux, interactive claude, already running, wake).
- 장점: 사람용 기능과 깨우기를 한 제품에서 얻는다. 브리지가 필요 없다. 유지보수를 상류와 나눈다.
- 단점과 위험:
  - Buzz의 연동 모델은 harness가 에이전트를 하위 프로세스로 띄워 소유하는 것(ACP)이다. 사람이 띄운 세션에 붙는 것은 이 모델 밖의 새 기능이라 거절될 수 있다.
  - 넣을 경로가 플랫폼과 런타임 내부에 기댄다. Claude inbox는 macOS·Linux 유닉스 소켓이고, Codex 쪽 `thread/queue/start`는 실험 API다(`docs/xsm/README.md` "알려진 한계"). 상류가 Windows까지 지원하는 제품이라 받아들이기 어려운 조건이다.
  - 범위와 사람 승인 같은 xsm의 동의 모델은 따라가지 않는다. Buzz 쪽 권한 모델에 맡겨진다.
  - 메인테이너 응답 시점을 우리가 정할 수 없다. 그동안 필요한 기능은 C의 브리지로 채워야 한다.
- C와의 관계: 둘은 배타적이지 않다. C의 브리지가 동작하면 그것이 이슈에 붙일 작동하는 시제품이 된다.

### F. OpenRig에 대시보드와 팀 운영을 맡기고, xsm은 그 안에서 전달만 맡는다

- 방식: OpenRig(`docs/references/openrig.md`)가 rig 구성, 지속, 작업 큐, TUI 대시보드, Slack을 맡는다. xsm은 OpenRig seat 안에서도 세션 간 메시지를 런타임 고유 경로(Claude inbox 소켓, `codex queue`)로 전달하고, 워커는 띄우지 않는다. ADR-0010의 Orca·herdr 규칙과 같다.
- 장점: 보드를 만들거나 Buzz를 운영하지 않고, Claude Code·Codex를 다루는 완성된 대시보드와 팀 운영을 얻는다. OpenRig는 Claude Code·Codex 세션을 직접 다루므로 C처럼 대응 계층(Nostr 키, 채널)이 필요 없다.
- 단점: OpenRig 자체의 전달(tmux 붙여넣기)과 xsm의 전달이 한 세션에 공존한다. 에이전트가 `rig send`와 `xsm send` 중 무엇을 쓸지 갈리면 X2와 같은 이중화가 생긴다. OpenRig는 상주 데몬, SQLite, tmux를 요구하고 설치 시 Claude·Codex 설정을 많이 바꾼다(`openrig.md` 4장). tmux 밖이나 다른 프로필의 세션은 대시보드에 나오지 않는다.
- 미확인: xsm이 OpenRig seat를 감지하는 방법(관리형 seat에 들어가는 `OPENRIG_*` 환경변수로 보이나 시험하지 않음). xsm 기록(전달 상태, 보류, 승인 대기)이 OpenRig 화면에 보이는 방법은 없다.

## 보드가 지켜야 할 경계 계약

아래 계약은 코디네이터가 사용자의 "보드는 xsm 원칙을 반드시 지킬 필요는 없다"(라운드 4)를 바탕으로 재구성한 것이다. 사용자의 확인이 필요하다.

| # | 계약 | 이유 |
|---|---|---|
| 1 | xsm은 보드에 의존하지 않는다 | 보드가 죽어도 세션끼리의 전달은 그대로여야 한다(ADR-0003 기준 2) |
| 2 | xsm 상태는 xsm 명령으로만 바꾼다 | 보드가 `~/.xsm` 파일을 직접 고치면 원장과 채널의 정합성을 xsm이 보장할 수 없다 |
| 3 | 범위와 동의를 우회하지 않는다 | 보드에서 보낸 호출도 프로젝트 범위와 보류 판정을 그대로 탄다 |
| 4 | `decision`과 승인은 사람만 한다 | 보드가 사람의 입력임을 xsm에 증명할 방법이 필요하다(W1) |
| 5 | 보드 전용 도구를 세션에 설치하지 않는다 | 에이전트는 지금처럼 xsm의 CLI와 MCP 도구(`xsm send`, `xsm post`, `xsm_decide`, `xsm_grant`, `xsm_approve`, `xsm doc add` 등)만 쓴다. 보드 쪽 도구가 생기면 X2의 이중화가 생긴다 |
| 6 | 읽기 노출을 범위 안에 둔다 | 리스너는 기본으로 loopback에만 연다. 그 밖은 명시적 옵트인과 토큰 인증을 거친다. 보이는 범위는 ADR-0004의 범위보다 넓지 않게 한다. 본문은 이스케이프해 표시하고, 작성자와 `decision` 표시는 같은 uid가 위조할 수 있는 자기 주장임을 밝힌다 |

계약 1~4는 쓰기 경로가 있을 때 의미가 있다. 대시보드 1판(보기, 알림, 좁히는 연산)에서 실제로 걸리는 것은 계약 6이다. 계약 4의 구현 방식은 "대시보드 쓰기와 알림" 절의 W1 권고다.

## xsm 쪽 선행 작업

### 모든 보드 안에 공통

- **P1. 기계가 읽는 출력.** `channel`, `held`, `workers`, `approvals`에 `--json`을 더한다. 원장과 채널의 변경을 따라 읽는 방법(이벤트 스트림 또는 증분 조회)을 둔다. 조회는 상태를 고쳐 쓰지 않는다. 지금 `workers.approvals()`는 읽을 때 사라진 워커의 요청을 `denied`로 고쳐 쓴다(`xsm/workers.py:851-853`). D에서도 쓸모 있다.
- **P3. 오간 메시지를 원장에 온전히 남긴다.** 지금 원장(`~/.xsm/ledger/<id>.json`)은 본문 앞 200자(`preview`)만 남기고 `reply_to`를 저장하지 않는다(`xsm/ledger.py:30-33`). 답장 관계는 봉투 헤더(`xsm/envelope.py:74-75`)에만 실려 상대에게 가고, 원장은 30일 뒤 정리된다. 본문 전체와 `reply_to`를 원장에 남기면 `reply_to` 사슬로 대화를 묶고, 작업은 `close`의 결과로 끝을 표시할 수 있다. 정할 것: 보존 기간(지금처럼 30일인지, 채널처럼 정리하지 않을지), 그리고 본문이 원장에 남으면서 ADR-0005의 미해결 문제(로그 속 비밀)가 원장으로 번지는 것. 대안인 각 세션 transcript 파싱은 런타임 형식에 묶이고 범위 밖 내용까지 읽게 되어 택하지 않는다.
- **P2. 명세 문서.** 보드와 xsm이 따로 버전을 올리려면 레코드 형식과 명령 계약을 버전과 함께 기록해야 한다.

### 쓰기 경로

- **W1. 보드를 통한 사람(A의 대시보드 2판, B, C 공통).** xsm은 지금 터미널 여부로 사람을 판정한다. 보드는 터미널이 아니므로 증명 방식과 기록 형식이 필요하다. 사용자는 "클릭은 사람 입력"으로 정했고(라운드 12), 구현은 "대시보드 쓰기와 알림" 절의 권고를 따른다.
- **W2. 세션이 아닌 발신자(B, C).** 커넥터·브리지가 `xsm send`를 부를 수 있어야 한다. 발신자를 무엇으로 기록할지, 범위를 어떻게 판정할지 정해야 한다.

### A-1을 고를 때만

- 원격 읽기 op. ADR-0007을 다시 열어 별도 ADR에서 critic 라운드를 거친다.

## B로 갈 때 정할 것

1. **채널 원본의 위치.** 각 기계의 xsm 파일을 원본으로 두고 보드는 다시 만들 수 있는 색인으로 두는 안이 xsm을 보드 없이 온전하게 둔다. 이 경우 사람이 보드에서 쓴 글을 어느 기계의 xsm에 기록할지 정해야 한다.
2. **사람 인증.** 보드 로그인을 xsm이 어떻게 믿을지. `decision`과 승인의 무게가 여기에 걸린다.
3. **기계 간 중계.** 보드가 허브라면 기계 사이 메시지를 보드로 중계할 수도 있다. ADR-0007은 인증된 WebSocket 릴레이(선택지 B)를 상주 서버가 필요하다는 이유(ADR-0003)로 기각했고, 토론 1-보충(S9)에서는 agent-comms의 기본 허브가 제3자에게 장치 정보를 노출한다는 점을 들었다. 자기 서버로 두면 제3자 노출 사유는 약해지지만 상주 서버 사유는 그대로다. 중계를 xsm 전달 경로에 넣으면 xsm이 보드에 의존하게 되어 경계 계약 1과 부딪힌다. SSH 짝을 유지하는 것이 기본이고, 보드 중계는 xsm 밖의 선택 경로로만 검토한다.

## 스파이크

- **S-C (C 검증, 하루 규모).** 로컬에 Buzz를 띄우고 `buzz` CLI로 다음을 게시해 본다. (1) xsm 채널 레코드 하나, (2) 승인 대기를 워크플로 승인 이벤트(46010)로, (3) 전달 상태를 비표준 kind 또는 일반 메시지로. 화면에서 어떻게 보이는지, relay가 비표준 kind를 받는지, 기계당 키 하나로 여러 세션을 구분해 표시할 수 있는지 확인한다. Buzz를 Docker로 띄울 수 있는 기계가 필요하다.

## 미해결

1. 경계 계약 6개를 사용자가 확인하지 않았다.
2. 권고의 전환 기준 수치(아래)는 코디네이터 제안값이다.
3. A를 고를 경우 수집 방식(A-1~A-4) 중 무엇을 쓸지 정하지 않았다.
4. C의 화면 표현과 Nostr 키 모델은 S-C 전까지 모른다.
5. E의 이슈를 올릴지, 올린다면 언제(S-C 전 또는 후) 올릴지 정하지 않았다. 상류에 글을 올리는 것은 사용자의 승인이 필요하다.
6. F를 고를 경우 에이전트가 `rig send`와 `xsm send` 중 무엇을 쓰게 할지, xsm이 OpenRig seat를 어떻게 감지할지 정하지 않았다.
7. 메뉴바 앱을 Swift로 만들지 파이썬(PyObjC 등)으로 만들지, 배포와 서명을 어떻게 할지 정하지 않았다.
8. P3의 보존 기간과, 원장에 본문을 남길 때의 비밀 노출을 어떻게 다룰지 정하지 않았다.
9. W1 권고(pty와 `XSM_VIA=dashboard`, 다이제스트 결속)를 사용자가 확인하지 않았다.
10. 보류 해제의 재설계 방식을 정하지 않았다.
11. 프로젝트 삭제 명령의 삭제 범위(scope만인지, 채널·문서·원격 짝까지인지)를 정하지 않았다.
12. 만료된 grant 파일을 정리하는 코드가 없다. Claude 네이티브 보류의 만료 설정(`dialogExpiry`) 값은 확인하지 못했다.

## 권고

이 권고는 사용자 결정 전이다. 라운드 6의 "A로 시작"을 아래로 바꾼다. A의 원격 수집 방식이 B·C로 이어지지 않는다는 반론(라운드 7)을 받아들였기 때문이다.

1. **지금은 D로 간다.** P1(빠진 `--json`)만 넣고, 다른 기계의 기록은 사용자 SSH로 조회한다.
2. **필요 빈도를 잰다.** 2주 동안 다른 기계의 기록을 보려고 조회한 횟수와, 보드가 있었으면 했던 순간을 적는다.
3. **S-C를 돌린다.** 하루 규모로 C의 미지수(화면 표현, 비표준 kind, 키 모델)를 확인한다.
4. **갈라진다.**
   - 조회가 주 3회 미만이면(제안값) D를 유지한다.
   - 조회가 잦으면 A로 간다. 형태는 macOS 메뉴바·노치 앱(라운드 10 제안)이다. 1판은 이 기계의 세션에 대해 보기, 알림, 좁히는 연산을 한다. 2판은 W1과 미결 9~11이 정해진 뒤 승인, 보류 해제, 프로젝트 삭제를 더한다. 다른 기계는 원격 노출이 없는 A-3이나 A-4부터 시작한다.
   - 휴대폰에서 지시하거나 다른 사람과 함께 써야 하고 S-C가 통과하면 C로 간다.
   - 보드에서 xsm 상태를 직접 조작해야 하고(승인, 보류 해제, 호출) S-C에서 Buzz 화면으로는 부족함이 확인되면 B로 간다.
5. **C로 가면 E를 함께 연다.** 브리지가 동작하면 그것을 시제품으로 붙여 Buzz에 이슈를 올린다(사용자 승인 후). 상류가 받아들이면 브리지를 걷어 내고, 거절하면 브리지를 유지한다.
