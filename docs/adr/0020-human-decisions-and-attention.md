# ADR-0020: 사람의 판단 원문을 보존하고 중복 질문과 알림을 조절한다

- 상태: Proposed
- 관련 목표: G2, G5, G6
- 작성일: 2026-10-24
- 역공학 추적: R02, R24, R25, R26, R27, R38
- 기존 결정 효력: 이 문서는 아직 Accepted ADR을 대체하지 않는다.

## 질문

사람이 본 요청과 실제 답을 확실히 연결하면서 대기 취소·늦은 응답·중복 호출·알림을 어떻게 처리할 것인가?

## 맥락

Reason의 ask_user는 about으로 받은 동료 요청 원문을 먼저 보여 주고 질문·사용자가 본 내용·답·시각을 묶어 머신 키로 서명해 보낸다. 같은 질문은 기존 창을 기다리고, 대기가 끝난 뒤 온 답은 후속 메시지로 전달한다. OS 알림은 에이전트 전달과 별도이며 빈도·오래된 알림을 제한하고 승인창은 포커스를 빼앗지 않는다. [ask.rs](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/daemon/ask.rs), [notify.rs](https://github.com/reason-machines/reason-network/blob/b3557ff454cd26a04c2a18804ba83ae5db8b119d/src/daemon/notify.rs).

머신 서명은 해당 머신이 답을 기록했다는 증거다. 같은 사용자 권한의 프로그램 전체를 막는 인증 수단은 아니다. 사람이 보지 못한 잘린 원문까지 승인됐다고 해석해서도 안 된다. 플랫폼별 화면 표시 범위의 한계가 있다.

후속 [격리 실행](../references/reason-network/followup-findings.md)에서 OS 알림 명령의 완료 전에 `popped up` 응답이 오고, 나중에 명령이 실패해도 빈도 제한을 소모함을 0.12.10·0.12.11에서 확인했다. 인증 finisher의 pending 파일 교체 조건에서도 이전 결과 저장 경로를 관측했다. 실제 OS UI나 실제 다중 CLI 경쟁을 입증한 것은 아니며, 답·현재 요청·적용 단계의 결속을 분리할 근거다.

xsm도 [MCP person_answer·elicitation](../../xsm/mcp.py), [consent](../../xsm/consent.py), [channel의 결정](../../xsm/channel.py), [worker 승인](../../xsm/workers.py)을 구현한다. 새로운 사용자 질문 기능을 처음 추가하는 문제가 아니라 여러 승인 경로의 수집·출처·재대기 계약을 일치시키는 문제다.

## 선택지

| 안 | 방식 | 이점 | 비용·위험 |
|---|---|---|---|
| A | 하네스별 현재 승인 경로를 개별 유지 | 네이티브 UX 활용 | 타임아웃·비동기 응답·재시도 의미 불일치 |
| B | 공통 결정 레코드와 생명주기를 두고 하네스/UI는 어댑터로 사용 | 같은 답 재사용·원문 추적·늦은 응답 복구 | 영속 상태·취소 경쟁·표시 내용 결속 필요 |
| C | 자체 승인 UI·서명 서비스를 필수로 요구 | 표시와 응답 경로 통제 | 설치·접근성·원격 데스크톱·추가 런타임 의존 |

## 제안 계약

B를 제안한다. 자체 UI는 검증된 선택적 어댑터이며 기본 필수 조건으로 확정하지 않는다.

- 결정 레코드는 원 요청 ID·요청자·대상·승인 주체·실제로 보여 준 원문과 질문·답·출처 채널·시각을 포함한다. 잘린 내용을 표시하고 보이지 않은 범위까지 승인했다고 확대하지 않는다.
- approved·denied·unanswered·dismissed·transport-error·expired를 구분한다. 자동 승인 검토의 답과 사람의 답을 같은 출처로 기록하지 않는다. 하네스가 사람 거부와 자동 거부를 구별하지 못하면 그 한계를 표시한다.
- 같은 질문과 같은 범위의 재호출은 진행 중 질문에 합류한다. 질문 원문·범위가 바뀌면 기존 승인을 재사용하지 않는다. 중복 호출의 참조 수와 실제 답을 소비한 상태를 구분한다.
- 대기 취소·도구 타임아웃은 사람의 거부가 아니다. 늦은 답은 원 요청에 연결해 회수한다. 적용 직전에 원 요청 ID·대상·세대를 다시 대조한다. 요청·권한이 이미 철회되거나 바뀌었으면 답은 기록하되 자동 적용하지 않는다.
- 사용자 판단과 승인 적용 결과를 분리한다. 실제 승인했지만 연결이 실패한 경우 그 사실과 복구를 보여 준다. 같은 유효 범위를 적용하려고 다시 판단을 요구하지 않는다.
- 사용자 알림은 에이전트 깨우기와 별도 선택이다. 전달 여부와 OS에 알림을 넘긴 사실, 실제 사람이 본 사실은 다르다. 포커스·빈도·오래된 알림을 정책으로 조절한다.
- 원격 승인에는 인증된 머신의 증거와 원 요청 ID·승인 주체를 확인한다. 일반 메시지에 적힌 승인 주장을 신뢰 증거로 승격하지 않는다. 로컬 elicitation에 무조건 원격 서명 체계를 덧붙이지 않는다.

## 기존 결정과 이행

0004·0013의 승인 의도와 사용자 원문 기록을 유지한다. 0005의 결정 게시, 0006의 endorse, 0010의 위험한 워커 실행은 각자 원래 권한 범위를 유지한다. 공통 레코드를 도입했다고 모든 승인을 하나의 포괄 grant로 합치지 않는다. 권한 규칙·훅 신뢰 변경은 실제 구현 시 별도 사용자 승인이 필요하다.

## 수용 검사

- A20-01: 사람에게 보인 원문·질문·잘린 범위를 기록과 대조한다. 원 요청 본문을 바꿔 재사용하면 적용되지 않는다.
- A20-02: 같은 질문을 두 번 호출해 승인창은 하나이고 원래 요청에 한 번만 적용된다.
- A20-03: 대기 타임아웃 후 실제 답, 질문 취소 후 답, 승인과 철회 동시 발생을 검사한다.
- A20-04: 사람의 거부·창 닫기·하네스 자동 거절·데스크톱 부재를 구별한다. 사용자 거부를 장애로 보고 재촉하지 않는다.
- A20-05: 동료가 본문에 승인 태그를 넣거나 다른 요청의 실제 승인을 재사용해도 권한이 생기지 않는다.
- A20-06: 알림 미지원·OS 실패·알림 억제·오래된 요청을 검사한다. OS 명령을 장벽에서 지연·실패시켜 접수와 호출 성공의 표시를 대조하고, 실패 후 빈도 제한·재시도를 확인한다. 사용자에게 알렸다고 추정해 작업을 진행하지 않는다.
- A20-07: 앞선 xsm 비동기 승인 수집 실패를 같은 입력 채널로 재현하고 복구 경로를 실제 실행한다.

## 비용과 되돌리기

질문 원문과 답의 보존·개인정보 관리가 필요하고 여러 하네스의 응답 출처를 유지해야 한다. 중복 합치기가 서로 다른 요청을 잘못 묶지 않도록 전체 계약 다이제스트가 필요하다. 어댑터를 제거해도 진행 중 질문·결정 이력은 원래 하네스나 수동 회수 경로로 이어져야 한다.
