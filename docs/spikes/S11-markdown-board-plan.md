# 스파이크 S11 설계: 여러 에이전트가 함께 고치는 마크다운 보드

- 상태: 설계. 미실행
- 작성일: 2026-10-30
- 관련: ADR-0005(채널), ADR-0006(공동 문서), [채널 설계 토론](../plan/collaboration/channel-design-discussion.md)
- 목적: 별도 보드 기능 없이, 저장소의 마크다운 파일 하나를 여러 에이전트가 함께 고치는 방식이 공유 보드로 쓸 만한지 확인한다. 쓸 만하면 xsm은 보드를 새로 만들지 않고 변경 알림만 더한다.

## 1. 확인할 가설

| ID | 가설 | 틀렸다고 볼 관찰 |
|---|---|---|
| H1 | 서로 다른 항목을 동시에 고치면 모두 남는다 | 한 에이전트의 변경이 사라진 경우(lost update)가 1건이라도 있음 |
| H2 | 같은 항목을 동시에 고치면 뒤에 쓴 쪽의 편집이 실패하고, 그 에이전트는 다시 읽어 합친다 | 실패 뒤 파일 전체를 덮어쓰거나 셸 명령으로 우회해 남의 변경을 지움 |
| H3 | 에이전트는 보드를 항목 단위로 고친다(Claude Edit, Codex apply_patch) | 파일 전체 쓰기(Write, `cat >`, 셸 리다이렉트)가 보드 쓰기의 상당 부분 |
| H4 | 워크트리가 다르면 보드가 브랜치마다 갈라져 서로의 변경이 보이지 않는다 | (확인용. 보이지 않으면 가설 성립) |
| H5 | 모든 워크트리가 같은 절대 경로의 보드 하나를 쓰면 H4가 풀린다 | 같은 경로를 써도 서로의 변경이 다음 작업에 반영되지 않음 |

H1–H3이 이 방식의 성패를 가른다. H4–H5는 보드를 어디에 둘지 정하는 근거다.

## 2. 구성

- 대상: 시험 전용 임시 git 저장소. xsm 저장소와 사용자 프로젝트는 건드리지 않는다.
- 에이전트 3개: Claude 2(`claude -p`), Codex 1(`codex exec`). 구독 런타임만 쓰고 API 키 경로는 쓰지 않는다. 같은 시각에 시작한다.
- 보드 `BOARD.md`: 항목마다 `##` 제목 하나. 처음 내용은 아래와 같다.
  - `## 결정: 캐시 전략` (모두가 의견 한 줄씩 추가)
  - `## 담당: A`, `## 담당: B`, `## 담당: C` (각자 자기 항목만)
  - `## 진행 기록` (모두가 한 줄씩 추가)
- 지시는 보드를 고치는 방법을 지정하지 않는다. "보드의 이 항목을 갱신하라"까지만 준다. 실제 쓰는 방식을 보려는 것이다.
- 충돌을 만드는 장치: 별도 스크립트가 실행 중 무작위 시점에 `## 결정` 항목에 한 줄을 넣는다. 에이전트가 읽은 뒤 쓰기 전에 파일이 바뀌는 경우를 일부러 만든다.

## 3. 시나리오

| ID | 배치 | 과업 | 확인 가설 |
|---|---|---|---|
| S11-1 | 세 에이전트가 같은 체크아웃 | 각자 자기 담당 항목 갱신 + 진행 기록 한 줄 | H1, H3 |
| S11-2 | 같은 체크아웃 + 충돌 스크립트 | 셋 다 `결정` 항목에 의견 추가 | H2, H3 |
| S11-3 | 에이전트마다 별도 워크트리, 보드는 저장소 안 | A가 쓴 결정을 B가 읽고 자기 담당에 반영 | H4 |
| S11-4 | 별도 워크트리, 보드는 공통 절대 경로 하나 | S11-3과 같은 과업 | H5 |

시나리오마다 5회 반복한다(총 20회, 에이전트 실행 60회).

## 4. 기록과 판정

- 실행마다 남기는 것: 시작 전·후 `BOARD.md`, 충돌 스크립트가 넣은 줄과 시각, 각 에이전트의 도구 호출 로그(`claude -p --output-format stream-json`, `codex exec --json`).
- 셀 것:
  - lost update 수: 끝난 보드에 각 에이전트와 충돌 스크립트가 넣은 줄이 모두 있는지 대조
  - 보드 쓰기 방식별 횟수: 항목 편집 / 파일 전체 쓰기 / 셸 쓰기
  - 편집 실패 뒤의 행동: 다시 읽고 합침 / 덮어씀 / 포기
  - S11-3·S11-4에서 B가 A의 결정을 반영했는지
- 판정:
  - lost update 0이고 파일 전체·셸 쓰기가 보드 쓰기의 10% 미만이면, 마크다운 보드는 쓸 만하다고 본다. 이어서 xsm 변경 알림을 설계한다.
  - lost update가 있거나 실패 뒤 덮어쓰기가 나오면, 마크다운 직접 편집만으로는 부족하다. 쓰기를 xsm 명령으로 거치게 할지 다시 논의한다.
  - 기준 수치(10%)는 이 계획의 제안이며 사용자가 정한 값이 아니다.

## 5. 이 실험이 말해 주지 않는 것

- 항목 사이의 의미 모순(서로 다른 항목에 모순된 내용)은 잡지 않는다.
- 사람이 함께 고치는 경우, 머신 간 git push 충돌은 다루지 않는다.
- 장시간 협업, 실제 과업의 보드 크기에서의 컨텍스트 비용은 재지 않는다.
- 짧은 headless 실행이라, 대화형 세션의 거동과 다를 수 있다.
