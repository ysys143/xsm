# 스파이크 S12b 설계: 어려운 표본에서도 싼 모델이 보드 변경을 걸러 읽는가

- 상태: 설계. 필터 호출 전에 작성
- 작성일: 2026-10-30
- 관련: [S12 설계](S12-board-filter-plan.md), [S12 결과](S12-results.md), [팀 구현 계획 T9](../plan/collaboration/team-implementation-plan.md)
- 자료·스크립트: [deliverables/s12b-hard-sample](../../deliverables/s12b-hard-sample/)

## 1. S12와 무엇이 다르고 왜 다른가

S12에서 haiku와 luna는 재현율이 100%에 가까웠다. 그러나 S12 결과 문서 스스로 표본이 쉬웠다고 적었다. 작업 영역 네 개가 뚜렷이 갈라져 있었고, 항목은 한 문장이었고, 관련 변경이 세션 설명과 같은 단어를 썼고, 어려운 음성 사례가 적었다. 그 결과로는 "단어가 겹치니 고른 것"과 "뜻을 읽고 고른 것"을 가를 수 없다. S12b는 질문(Q1–Q4)과 라벨 체계, 조건, 집계를 S12에서 그대로 가져오고 표본만 바꾼다.

| 항목 | S12 | S12b |
|---|---|---|
| 항목 길이 | 한 문장 | 실제 팀 보드처럼 여러 문장, 60–200어절(공백 단위), 곁가지 세부 포함 |
| 전제 | 세션 설명에 `premises`로 목록 제공 | 목록으로 주지 않음. 작업 내용에서만 추론 가능 |
| 자원 | 세션 설명에 `resources`로 목록 제공 | 목록으로 주지 않음. 작업 내용에서만 추론 가능 |
| 단어 겹침 | 관련 변경이 세션 설명의 단어를 그대로 씀 | R2·R3·R4 변경은 그 세션 설명의 구별 단어를 하나도 쓰지 않음(기계 검사) |
| 어려운 음성 | 거의 없음 | 세션 설명의 구별 단어를 쓰지만 무관한 N 항목을 따로 배치 |
| 작업 영역 | 네 영역이 깨끗이 갈림 | 다섯 세션의 영역이 겹침(같은 공유 저장소, 같은 구매 흐름) |

## 2. 시험 자료 (필터 호출 전에 고정)

- 세션 5개. S12의 4개에서 하나 늘린 이유: 영역이 겹치는 구성을 만들려면 공유 자원(공용 인메모리 저장소, 구매 흐름)을 둘 이상의 세션이 함께 기대야 하고, 넷으로는 겹침과 비겹침을 함께 두기 어렵다. 늘린 만큼 사례는 50개(변경 판정 400건)가 되어 S12의 40사례(320건)와 같은 규모대에 있다.
- 각 세션의 작업 설명은 이름, 작업 한두 문장, 담당 보드 항목 번호, 다루는 파일 하나로만 이루어진다. 전제와 자원은 쓰지 않는다. 작성자는 라벨을 달기 위해 세션별로 숨은 전제·자원 메모를 따로 적어 두지만, 이 메모는 필터와 독립 라벨러 어느 쪽에도 주지 않는다.
- 변경 묶음 10개, 묶음마다 항목 8개. 묶음은 같은 초기 보드에 대한 독립 diff다(S12와 같다). 담당 항목을 고치는 변경은 이전 내용이 있고, 나머지는 새 항목이다.
- 세션별 "구별 단어" 목록을 고정 자료에 둔다. 세션 이름, 담당 항목 번호, 파일 경로와 그 조각, 작업 설명의 고유 명사·구성 요소 이름·핵심 명사다. "작업", "팀", "테스트", "확인" 같은 일반어는 넣지 않는다. 어디까지를 구별 단어로 볼지는 작성자 판단이며, 목록 자체를 고정해 공개한다.
- 고정 전 기계 검사(하나라도 어기면 고정하지 않는다):
  1. 각 항목 본문이 60–200어절이다.
  2. 세션 S에 대해 R2·R3·R4인 항목의 제목·본문에 S의 구별 단어가 하나도 없다(대소문자 무시, 부분 문자열).
  3. 세션 S의 어려운 음성으로 표시한 항목은 S의 구별 단어를 하나 이상 포함하고, S에 대해 N이다.
  4. R1 항목에는 세션 이름·담당 항목 번호·파일 경로 중 하나가 글자 그대로 있다.
  5. 세션 설명에 전제·자원 목록 필드가 없다.

## 3. 라벨 규칙

라벨 다섯 개와 우선순위(R4 > R3 > R2 > R1)는 S12와 같다. 정의만 이 표본에 맞게 고쳐 쓴다.

| 라벨 | 뜻 |
|---|---|
| R1 직접 | 그 세션의 이름, 담당 항목 번호, 담당 파일을 지명한다 |
| R2 겹침 | 다른 사람이 그 세션과 같은 일(같은 대상의 같은 변경)을 시작했거나 하고 있다. 이름 지명은 없다 |
| R3 전제 | 그 세션의 작업이 성립하려면 참이어야 하는 사실(작업 설명에서 추론되는 것)을 뒤집거나 무효로 만든다 |
| R4 자원 | 그 세션의 작업에 필요한 것(작업 설명에서 추론되는 환경·장비·계정·할당량)을 다른 작업이 점유하거나 쓸 수 없게 된다 |
| N 무관 | 위에 해당하지 않는다. 같은 단어가 나와도 다른 맥락이면 N이다 |

- 작성자 라벨을 먼저 달고, 별도 `claude -p` 실행(도구 없음, 작성자 라벨과 숨은 메모 없이 세션 설명·변경·위 규칙만)으로 독립 라벨을 받는다. S12와 같이 관련 셀만 열거하고 생략 셀은 N으로 본다.
- 두 라벨이 다른 셀은 필터 호출 전에 하나씩 본다. 작성자가 자기 라벨을 고칠 근거가 있으면 근거를 적고 고친다. 근거가 갈리면 "모호"로 고정하고 주요 지표에서 빼서 따로 센다. 이 처리도 필터 호출 전에 끝내고 해시로 고정한다.

## 4. 비교 조건

S12와 같다.

| ID | 필터 | 비고 |
|---|---|---|
| F0 | 기계적 문자열 일치: 세션 이름·담당 항목 번호·파일 경로 | 모델 없음. 대소문자 구분. S12와 같은 정의 |
| F1 | `claude -p --model haiku` | 도구 없음, MCP 없음, 세션 저장 없음 |
| F2 | `codex exec --model openai/gpt-6-luna` | ocx 프록시 경유, reasoning effort `low`. S12와 같은 Codex 홈(`~/.codex-3`) |
| F3 | `codex exec --model gpt-6.1-sol` | S12의 F3와 같은 모델과 effort `low`. 사전 선택한 묶음 B01·B05·B10의 5세션 = 15사례 |

- 프롬프트는 S12의 `filter-prompt.txt`를 그대로 쓴다. 입력은 세션 작업 설명(JSON)과 변경 diff다.
- 반복: 기본 50사례를 F1·F2에서 1회씩, 그리고 묶음당 1사례(10사례)를 F1·F2로 3회 더. 계획 호출 수는 F1 80, F2 80, F3 15, 합계 175회.
- 실제 응답 모델 확인: F1은 CLI 결과의 `modelUsage` 모델 이름, F2·F3는 ocx 로그의 `requestedModel`·`resolvedModel`·`servedModel`(대화 ID = `sha256(thread_id)[:32]`)로 확인한다. 첫 호출에서 확인하지 못하거나 다른 모델이면 멈춘다. 대체 모델은 쓰지 않는다.

## 5. 셀 것

- 라벨별(R1–R4) 재현율. R2·R3를 가장 중요하게 본다.
- 정밀도 TP/(TP+FP)와 N 통과율 FP_N/N. 어려운 음성 셀만의 N 통과율을 따로 센다.
- 인용 충실도: 반환한 인용이 그 항목 변경 후 본문의 비어 있지 않은 연속 부분 문자열인 비율(S12와 같다). 항목이 길어진 만큼 인용 길이 분포도 기록한다.
- 반복 차이: 같은 10사례 4회의 전체·라벨별 재현율 최댓값−최솟값.
- 호출당 입력·출력 토큰과 시간.
- 계획 대비 실행 호출 수와 모든 오류·이상치.

## 6. 기준값

S12의 기준값(R2·R3 재현율 90%, 인용 충실도 95%, 반복 차이 10%p)을 이 문서에서도 비교용으로 쓴다. **이 값들은 계획 작성자의 제안값이며 사용자가 정한 값이 아니다.** 실제 판정 기준은 사용자가 정한다. 결과 문서는 측정값과 제안값의 비교만 적고, 걸러 읽기를 스킬에 권장할지(D32)는 적지 않는다.

## 7. 운영 규칙

- 구독 경로만 쓴다. 모든 모델 호출 환경에서 `ANTHROPIC_API_KEY`·`OPENAI_API_KEY`를 뺀다. 키 값과 인증 파일 내용은 읽지 않는다.
- 계정 식별자를 남기지 않는다. 원시 표준 출력을 파일로 저장하지 않고, 집계에 필요한 필드(응답 본문, 사용량, 모델 이름, thread ID)만 골라 저장한다. 저장 전에 계정·조직·사용자 키 옆의 UUID 꼴 문자열과 이메일 꼴 문자열을 `<redacted>`로 바꾼다. 끝에 산출물 전체를 다시 검사한다. thread ID는 프록시 로그 대조에만 쓰는 대화 식별자라 남긴다.
- 사용자 설정을 바꾸지 않는다. 첫 Codex 호출 전에 `~/.codex`·`~/.codex-2`·`~/.codex-3`의 `config.toml` SHA-256을 기록하고 백업을 저장소 밖 임시 디렉터리에 둔다. Codex 호출은 git 저장소 밖 임시 디렉터리에서 `--skip-git-repo-check`로 한다. 마지막 호출 뒤 해시를 다시 비교하고, 달라졌으면 멈추고 바뀐 키를 보고한다. 인증 파일은 복사하지 않는다. ocx 설정은 건드리지 않고 로그만 읽는다.

## 8. 이 실험이 말해 주지 않는 것

- 표본은 여전히 한 작성자가 만든 합성 자료다. 어렵게 만들려는 작성자의 의도가 실제 보드의 분포와 같다는 보장은 없다.
- 구별 단어 목록 밖의 단어(동의어, 같은 뿌리의 다른 말)는 겹칠 수 있다. "뜻으로만 관련"이라는 주장은 목록 범위 안에서만 성립한다.
- 숨은 전제가 작업 설명에서 "추론 가능"한지는 판단의 문제다. 독립 라벨러와의 불일치가 그 경계를 일부 보여 줄 뿐이다.
- 실제 세션이 필터에 넘길 수 있는 맥락의 양, 필터 결과를 받은 세션의 행동, 누적 비용은 재지 않는다.
