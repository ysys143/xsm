# S11b 결과: xsm doc을 보드로 쓰기

- 실행일: 2026-10-30
- 계획: xsm 요청 `s11b-doc-board-20261030`의 지시와 [S11 계획서](S11-markdown-board-plan.md). 제품 코드는 고치지 않았다.
- 본 실행: **4개 셀 × 5회 = 20/20회**, Claude 하네스 2개·Codex 하네스 1개로 **60회** 실행. 실제 응답 모델은 60회 모두 OpenAI 구독 경로의 `gpt-6-luna`로 확인했다.
- 생략: S11-3 별도 워크트리·서로 다른 문서는 위임에서 허용한 대로 생략했다. S11-2는 렌더 파일 직접 주입과 노드 주입을 각각 5회인 별도 셀로 시험했다.
- 핵심 관찰: 성공한 `doc add` **73개 노드는 모두 보존**됐고 최종 그래프의 없는 parent는 **0건**이다. 반면 요청 표식 **11개는 형성되지 않았고**, 노드에는 있으나 최종 렌더에 안 보이는 표식 **7개**, 기대 제목이 빠진 렌더 **4회**가 있었다.
- 경계: 실제 Codex 세 홈을 포함한 보호 파일 **12개**는 사전 검증·각 셀·종료 때 모두 기준 해시와 같았다. S11의 실제 프로필 trust 변경을 반복하지 않았다. commit·push하지 않았다.

## 1. 선행 조건을 확인한 방법

처음부터 `XSM_HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`을 새 임시 경로로 설정했다. 기존 인증 파일을 복사하거나 사용자 API 키를 넣지 않았다. Claude에는 코드에 문서화된 비밀이 아닌 `opencodex-proxy` marker를 프로세스에만 주고, Codex에는 loopback OCX provider를 호출별로 지정했다. proxy의 기존 ChatGPT 구독 경로를 사용했다. 실제 사용자 설정 파일에 모델·권한·provider를 저장하지 않았다.

격리 홈에서 두 하네스의 실제 모델 호출이 성공한 뒤, 기존 설치 모듈의 `pin_python`, `apply`, `install_skill`, `install_mcp`를 임시 홈에만 적용했다. 전체 CLI 설치는 사용자 `~/.local/bin/xsm` 링크를 갱신할 수 있어 그 전역 링크 단계는 호출하지 않았고, 시험용 PATH의 링크만 만들었다. xsm 코드 수정이나 가짜 registry 행 생성은 하지 않았다.

설치 뒤 실제 Claude·Codex 일회성 세션을 열어 `xsm who`와 `doc add`를 실행했다. 각 native CID가 격리 registry에 등록됐고, 두 사전 노드의 `author_kind=agent`와 등록 ref를 확인했다. 그 뒤 본 실행 60개의 native CID도 격리 홈의 등록 행과 대조했으며, 성공한 73개 노드의 작성자가 해당 실제 세션임을 확인했다. 하네스 호출은 S11과 같은 Claude/Codex 실행 경로, Luna 요청, low effort 요청을 사용했다. 다만 S11b에는 설치된 xsm 훅·MCP·스킬이 필요하고 격리 홈을 사용했다. Claude는 Bash 실행을 허용하고 Codex는 신뢰된 시험 훅을 이번 호출에 한해 실행했다. 이는 임시 홈의 실험 구성이다. 이 차이와 아래 스킬 안내가 있으므로 쓰기 방식 변화를 불변 노드 엔진 하나의 인과 효과로 단정하지 않는다.

원 모델명은 Claude alias `ocx-claude-native--gpt-6-luna`, Codex `openai/gpt-6-luna`다. native session을 OCX conversation hash와 결속한 본 실행 요청 **373개**에서 실제 served model·provider·시도를 확인했다. 이름을 묻는 모델 자기 보고를 사용하지 않았다. 사전 호출은 본 60회에 포함하지 않았고, 모델 대체는 관측되지 않았다.

## 2. 초기 보드와 지시

현재 doc에는 항목 갱신·상태 합성 기능이 없다. 초기화는 사람 작성자라고 명시한 **시험 fixture**로 전체 보드 내용의 `report` 노드 1개와, 결정·담당 A/B/C·진행 기록의 `setup` 노드 5개를 만들었다. 항목 노드는 초기 report를 parent로 가졌다. 이것은 실제 사용자의 승인·endorse를 위조한 것이 아니다. 시작할 때 모두 render했고, 초기 6개 노드와 파일을 보존했다.

모델에는 위임대로 “BOARD.md는 xsm doc이 렌더한다. 직접 고치지 말고 doc add로 항목 노드 아래 기여를 더하고 필요하면 render한다”는 안내 한 단락과 초기 항목 ID 표를 줬다. Edit·patch·Write·셸 중 도구는 선택해 주지 않았다. 역할별 작업과 고유 표식은 S11 방식이다.

S11b-4의 B는 A 실행 종료를 알리는 준비 파일 뒤에 A 결정을 읽도록 지시했다. 준비 파일과 B 프롬프트에 A의 실제 무작위 결정값은 넣지 않았다. 이는 지시 수준의 읽기 순서 제어이며 모델이 항상 준수했다고 가정하지 않았다.

각 실행에서 원시 JSONL·stderr·명령·프롬프트, 노드 스냅샷, 모델·등록 근거를 수집했다. 에이전트 종료 시 렌더와 노드를 먼저 저장하고, 판정자가 기존 `doc.render`를 한 번 더 호출한 결과는 **별도 파일**로 저장했다. 판정자 render를 모델의 쓰기 횟수에 포함하지 않았다. [실행 프로토콜](../../deliverables/s11b-doc-board/protocol.json)

## 3. 보존·미작성·표시를 구분한 결과

요청 표식은 역할별 독립 기여 단위다. 같은 표식의 `-progress` 확장은 다른 기여이며 접두사 일치만으로 둘을 같은 것으로 세지 않았다. 관측된 노드가 사후 사라지는 유실, 처음부터 의도한 표식을 만들지 못한 경우, 노드에는 있으나 렌더에서 보이지 않는 경우를 구분했다.

| 셀 | 완료 | 성공 노드의 사후 유실 | 요청 표식 미형성 | 노드 보존·렌더 미표시 | 기대 제목이 빠진 렌더 | 없는 parent |
|---|---:|---:|---:|---:|---:|---:|
| S11b-1 담당·진행 | 5/5 | 0 | 5 | 5 | 3회 | 0 |
| S11b-2-render 렌더 직접 주입 | 5/5 | 0 | 2 | 0 | 0회 | 0 |
| S11b-2-node 노드 주입 | 5/5 | 0 | 1 | 0 | 1회 | 0 |
| S11b-4 공통 절대 경로 | 5/5 | 0 | 3 | 2 | 0회 | 0 |
| 합계 | **20/20** | **0** | **11** | **7** | **4회** | **0** |

성공한 73개 agent 노드와 5개 주입 노드는 모두 남았다. 초기 노드 120개도 바뀌거나 삭제되지 않아 최종 노드는 **198개 = 초기 120 + agent 73 + 주입 5**다. 성공 반환된 노드 ID와 실제 node 파일·작성자를 전수 대조했다. 요청한 agent 표식은 80개 중 69개가 최종 노드 또는 렌더에 있었다. 빠진 11개를 이미 쓴 노드의 lost update로 바꾸어 세지 않았다.

렌더 파일에만 직접 삽입한 외부 표식은 재렌더 후 **5/5개 사라졌고**, 노드로 삽입한 외부 표식은 **5/5개 보존**됐다. 앞의 5개는 canonical 노드에 기록된 적 없는 projection 편집이며, 이를 노드 데이터 유실 0이라는 수치 뒤에 숨기지 않는다.

agent 종료 시 렌더와 판정자 최종 렌더가 다른 셀도 **2회** 있었다. S11b-2-node-r2/r3에서는 최종 노드의 기여 한 줄이 agent 종료 시 화면에 없었고 다시 render하자 나타났다. 정확한 경쟁 시점을 모두 복원했다고 주장하지 않으며, 노드 보관과 projection 갱신이 별개라는 관찰로 남긴다.

## 4. 하네스별 쓰기·읽기 경로

| 측정 | Claude 40실행 | Codex 20실행 |
|---|---:|---:|
| 성공한 doc add 노드 | 50 | 23 |
| 렌더 파일 직접 편집: Edit·patch·Write·셸 | 0 | 0 |
| 노드 파일 직접 생성·수정 | 0 | 0 |
| 확인된 공식 doc render | 38 | 16 |
| doc add를 포함한 실패 도구 호출 | 42 | 4 |
| 성공 도구 호출에서 선택한 doc show | 13 | 19 |
| doc leaves | 0 | 2 |
| doc next | 0 | 0 |
| 렌더 파일 직접 읽기 | 12 | 18 |
| 노드 파일 직접 읽기 | 0 | 2 |

doc add 성공 수는 Bash 호출 수가 아니라 성공 반환된 고유 노드 수다. 한 Bash 호출에서 add 둘을 실행하면 둘로 센다. 실패 수는 add를 포함한 도구 호출 단위이며 노드 명령의 실패 횟수와 같다고 가정하지 않는다. 일부 명령 묶음은 앞 add를 성공하고 뒤에서 실패하므로 성공 노드와 실패 도구 호출에 모두 들어간다. `&&`로 실행되지 않았거나 출력으로 확인하지 못한 render 의도 11개는 공식 render 성공으로 세지 않았다.

실패 호출의 주된 출력은 본문 누락 21, 잘못된 태그 17, 지원하지 않는 플래그 5, 사람의 endorse가 필요한 요청 2, 기타 1로 합계 46건이었다. 이 분류는 실패 출력 기준이며 모델의 숨은 의도를 추정하지 않았다. 잘못된 parent·태그는 저장 전에 거절됐고, 등록 선행 조건의 실패와 혼합하지 않았다.

노드를 직접 만들거나 고친 파일 도구 호출이 없었고, raw 명령의 직접 쓰기 후보도 전수 확인했다. 공식 `doc add`를 셸로 실행한 것을 렌더 파일에 직접 쓰는 “셸 우회”로 분류하지 않았다. 사람이 아닌 모델의 endorse를 대신 승인하거나 실제 설정을 바꾸어 실패를 통과시키지 않았다.

## 5. 모델이 항목을 표현한 방법

성공한 73개 기여는 모두 초기 항목 노드의 ID를 parent로 사용했다. 직접 일치한 parent 분포는 결정 27, 진행 13, 담당 A 11·B 12·C 10이었다. 태그는 result 37, insight 20, wip 10, report 6이었고, 본문에 `##` 제목을 둔 것은 8개, 표식·서술 위주인 것은 65개였다. 항목이라는 별도 필드를 새로 만든 것은 아니다.

문제는 parent가 지정돼도 **부모 항목의 본문을 갱신하는 것이 아니라 자식 기여를 더한다**는 데 있다. 현재 render는 최신 report를 main body로 택하고 open ends를 첫 줄 요약으로 보여 준다. 노드의 두 번째 줄에만 있는 표식은 화면에서 빠질 수 있다. 작은 모델의 입력·출력에도 제약이 있었지만 이 동작은 로그와 코드가 가리키는 projection 계약이다.

## 6. 구조 손상과 읽기 실패

### 부분 report가 보드 전체의 report가 된 경우

S11b-1-r3/r4/r5, S11b-2-node-r1에서 모델이 자기 담당·진행·의견의 짧은 기여를 `report`로 추가했다. 기존 render가 이 노드를 문서의 report로 고르면서 **초기 5개 항목 제목이 모두 화면에서 빠졌다**. 4개 렌더의 제목 누락이며 원래 노드가 삭제되거나 parent graph가 끊긴 것은 아니다. 같은 root 아래 노드를 더하는 것과 상태 항목을 합성하는 것은 다르다.

### 노드 본문의 항목 이름 왜곡

S11b-4-r4의 Codex는 C 항목 노드 아래 `## 담당: S11b-4-r4-C-d3a1ba8f02\n대기.`라는 새 노드를 더했다. 이 1건은 렌더 파일의 기대 제목이 사라진 위 4회와 구분한다. graph는 유효하지만 “C 항목 갱신”이라는 본문 표현은 왜곡됐다. [해당 셀](../../deliverables/s11b-doc-board/S11b-4-r4/final-nodes.json)

### A 결정의 다음 작업 반영

S11b-4에서 A의 실제 결정값은 5/5회 노드에 남았지만 B의 자기 기여에 그 값이 반영된 것은 **4/5회**다. 실패한 r4에서 B는 새 child 기여 대신 초기 결정 항목의 `대기.`를 읽어 “A 결정 원문: 대기.”로 썼다. 긴 sleep 명령이 하네스에서 거절됐고 준비 조건을 따르는 경로도 어긋났다. 이를 공통 경로의 데이터가 물리적으로 보이지 않는 증거로 쓰지 않는다. 노드 그래프를 현재 상태로 읽는 방법과 기다림의 실패다.

## 7. S11과의 비교 및 판정

| 축 | S11 직접 편집 | S11b doc 기여 |
|---|---|---|
| 성공한 기록의 최종 유실 | 관측 0 | 성공 노드 73/73 및 주입 노드 5/5 보존 |
| 작성 실패·잘못된 작업 | 경로 오독 미작성 1, 제목 구조 손상 1 | 요청 표식 11개 미형성, 렌더 제목 누락 4회, 노드 본문 제목 왜곡 1 |
| 쓰기 방식 | Claude Edit 50, Codex patch 15·셸 4 | doc add 73, 렌더·노드 직접 편집 0 |
| 공통 경로 A→B | 5/5 | 4/5. 초기 항목과 새 기여를 혼동한 1회 |
| 실제 프로필 | 임시 trust 20개가 실제 프로필에 생겨 원복 | 처음부터 격리 홈 사용. 보호 12파일 불변 |

**10%는 S11 계획의 제안값이며 사용자 결정이 아니다.** S11b에서 agent 쓰기를 성공 doc add와 직접 편집/노드 파일 우회로 나누면 직접 편집 비중은 0/73이다. 공식 render는 projection 갱신이므로 그 분모와 별도다. 이 수치만으로 보드로 쓸 만하다고 판정하지 않는다. 실패 호출·표식 미형성·상태 projection 문제가 남았다.

이번 표본에서 doc 방식은 **기여를 불변 노드로 남기는 경로**로 사용됐지만, **항목별 최신 상태를 합치는 보드**로 자동 작동하지 않았다. 코드·데이터 보존과 모델이 올바른 CLI·태그·읽기 경로를 선택하는 것은 다른 문제다. S11b에는 안내·스킬·등록 훅·MCP가 추가됐으므로 S11과의 차이를 저장 표현 하나의 인과 효과로 단정하지 않는다. 어떤 방식으로 채택할지는 이번 실험에서 결정하지 않았다.
