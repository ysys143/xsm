# E1: v0.4.0 평가와 유사 제품 비교

- 평가일: 2026-09-27. 대상: 태그 `v0.4.0`(`da43890`).
- 방법: 에이전트 둘이 따로 조사했다. 하나는 저장소의 코드·ADR·리뷰·테스트를 읽는 내부 평가, 하나는 유사
  제품을 공식 문서·저장소 원문으로 확인하는 비교 조사다. 코디네이터가 무게가 큰 주장을 원문으로 다시
  확인했다(아래 "코디네이터 확인" 표시).
- 앞선 R1~R5는 계획 단계의 적대적 리뷰다. 이 문서는 첫 릴리스를 놓고 한 평가다.

## 1. 결론

**알파 후반.** 이미 떠 있는 Claude Code와 Codex 세션을 브로커 없이 각 런타임의 입력 경로로 깨우는 제품은
조사한 범위에서 xsm뿐이다. 같은 기계·같은 프로필의 Claude끼리는 Claude Code 내장 기능이 이미 공식으로
해결했으므로, xsm의 몫은 네 가지로 좁혀진다.

1. Claude↔Codex 전달
2. 프로필(`CLAUDE_CONFIG_DIR`) 사이 발견
3. Anthropic 서버를 거치지 않는 SSH 원격(API 키·Bedrock·Vertex 환경 포함)
4. 프로젝트 범위, 수신 게이트, 워커, 텔레메트리

## 3. 강점

- **상주 프로세스 없음.** 전달은 Claude inbox 소켓과 `codex queue` 두 경로뿐이다(`xsm/adapters.py:1-13`).
- **등록이 곧 동의.** 훅을 돌린 적 없는 세션은 주소가 없다(`xsm/registry.py:8-10`).
- **수신 게이트가 실패에 닫혀 있다.** 훅이 예외로 죽으면 피어 메시지는 막고 사람 입력은 통과시킨다
  (`xsm/receive.py:5-10`). 거부한 메시지는 버리지 않고 보관한다.
- **stdlib만.** OTLP도 SDK 없이 만들고, 송수신 경로에서 네트워크를 타지 않는다(ADR-0011).
- **실패에 이름이 있다.** `codex-internal-changed`, `sandbox-blocked`, `would be held`처럼 무엇이 막혔는지를
  결과에 적는다. 주석이 실측 날짜와 스파이크 번호로 이유를 남긴다.

## 4. 약점과 위험

| 영역 | 내용 |
|---|---|
| Claude 내부 의존 | 소켓 경로·auth 줄·30초 제한·수신 정책은 [공식 문서](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket)에 있다(코디네이터 확인). 메시지 프레임(`type`·`msg_id`·`priority`·`from`)과 `sessions/<pid>.json` 레지스트리는 문서에 없다. 소켓 경로는 2026-09-28부터 훅이 받는 `CLAUDE_CODE_MESSAGING_SOCKET`을 등록 기록에 저장해 쓰고, 레지스트리는 이름과 이 값이 없는 옛 기록의 대체 경로로만 읽는다. 기능 자체는 `tengu_harbor_kite` 플래그 뒤에 있다 |
| Codex 내부 의존 | 가장 깊다. 첫 프롬프트 전 스레드는 `queue_<n>.sqlite`의 `queued_items`에 직접 INSERT하고, 스레드는 `logs_<n>.sqlite`로 추정한다(`adapters.py:173-231`). 스키마를 먼저 검사해 다르면 멈추지만, Codex 업데이트 한 번에 이 경로가 닫힐 수 있다. `codex queue`의 공식 문서는 찾지 못했다 |
| 보안 | 경계는 같은 uid다. 발신자 `ref`는 같은 권한의 프로세스가 위조할 수 있다. 문서가 스스로 "보안이 아니라 동의 기록"이라고 밝힌다 |
| 플랫폼 | macOS·Linux 전용(AF_UNIX, `ps -o lstart`, `/dev/tty`, tmux) |
| 동시성·규모 | `flock`·`fcntl`이 없다(코디네이터 확인). 레지스트리는 읽고-고치고-쓴다. 수십 세션까지는 문제없어 보이나 스웜 규모는 검증하지 않았다 |
| 운영 | 설치 방식 둘(플러그인, `xsm install`), 홈 여럿, 직접 설치 사본은 수동 `--refresh` |
| 테스트 공백 | 원격 단위 테스트는 가짜 ssh 3건. 실제 inbox 수용과 Codex TUI 픽업은 수동 시험으로만 확인 |
| 코드 | `cli.py` 1672행, `workers.py` 1151행. `/dev/tty` 확인 코드가 `cli.py:1029`와 `:1187`에 중복. `test_xsm.py:617` ResourceWarning |

신호: 코드 8.2k행, 테스트 4.6k행·320건 통과, 2026-09-20부터 8일·커밋 144개(코디네이터 확인), 사용자 1명.

제품별로:

- **Claude Code 내장.** 설치가 필요 없고 보류 대화상자, rate limit·루프 차단, idle 알림, 클라우드 세션 도달을
  공식 지원한다. xsm만 하는 것은 Codex, 프로필 사이 발견, Remote Control 없는 원격, 프로젝트 범위·워커다.
  프로필이 다르면 서로 보이지 않는다는 점은 2.1.278 바이너리 분석과 실측 근거이고, 공식 문서에는 언급이
  없으며 2.1.283에서 다시 재지 않았다.
- **herdr, Orca.** UI·worktree·원격 운영이 성숙하고 사용자층이 크다. 대신 자기가 띄운 터미널의 세션만
  다루고, PTY 주입은 사람 입력과 구분되지 않는다.
- **MCP Agent Mail.** 스레드 검색, 파일 lease, 대시보드가 있다. 상주 서버가 필요하고 poll 방식이라 idle
  세션을 깨우지 못한다.
- **agent-comms.** 방·device-id 신뢰 모델이 풍부하고 pi·OpenCode도 지원한다. Codex를 깨우지 못하고 상태가
  메모리에만 있다.
- **OpenRig.** YAML 팀 구성, 스냅샷 복원, 작업 큐, TUI 대시보드, Slack까지 갖췄고 가장 빠르게 움직인다.
  메시지는 tmux 붙여넣기로 넣고, 그 위험을 화면 판독과 typing guard로 막는다. 상주 데몬이 필요하고 tmux 밖
  세션은 편입하지 못한다.
- **agent teams, Codex subagents, claude-squad.** 부모가 만든 자식만 다루거나 세션 관리만 한다. 경쟁보다
  보완 관계다.

## 6. 포지셔닝

1. **같은 기계·같은 프로필의 Claude끼리는 내장 기능에 맡긴다.** Claude 쪽에서 게이트·보류를 다시 만들기보다
   공식 `crossSessionInbound` 위에 얹는 편이 유지보수에 유리하다.
2. **핵심 가치이자 가장 취약한 곳은 Claude↔Codex다.** 여기가 막히면 존재 이유의 절반이 흔들린다.
3. **프로필 사이 발견은 언제든 사라질 수 있는 우위다.** Anthropic이 추가하면 끝난다.
4. **SSH 원격은 차별점이지만 반쪽이다.** Remote Control을 못 쓰는 환경에서는 유일한 선택지일 수 있는데,
   원격 세션이 목록에 나오지 않는다.
