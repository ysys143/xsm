# xsm 공개 프로토콜과 런타임 확장 계획

## 1. 목표와 완료 기준

xsm의 협업 기능을 **하네스와 독립된 공개 프로토콜**로 정리한다. 제3자가 명세와 적합성 검사기만으로 참여자를 구현할 수 있어야 한다.

각 런타임의 연결 코드는 세션 이벤트·입력 큐·사용자 UI 연결만 담당한다. 발견·범위 정책·DM·팀 보드·첨부·승인 결속·복구·원격 전달을 런타임마다 다시 구현하지 않는다.

사용자가 정한 기준을 유지한다.

- 대상: Claude·Codex와 신규 Pi·OpenCode·Hermes·OpenClaw.
- 운영체제: macOS·Linux.
- 지원 범위: 기존 기능 전체와 로컬 UI·외부 메신저 세션.
- 모델·외부 메신저 없는 핵심 회귀 검사: **전체 120초 이내**.
- 정상 연결된 유휴 세션의 로컬 메시지 저장부터 네이티브 입력 큐 인계까지: **p95 1초 이내**. 모델 응답 시간과 외부 플랫폼 지연은 제외한다.
- 기존 CLI·MCP·승인·저장 데이터의 의미를 보존한다. 독립 채널을 새로 만들지 않고 현재 DM·팀 보드 계약을 따른다.

## 2. 구조와 공개 인터페이스

### 공통 프로토콜과 실행 구조

초기 전송은 **UTF-8 JSON Lines 위의 JSON-RPC 2.0, stdio**로 고정한다. 로컬 TCP 서버·중앙 데몬·xsm 전용 에이전트 실행 래퍼는 필수로 만들지 않는다.

런타임의 확장이 세션 또는 호스트 수명에 묶인 `xsm protocol serve --stdio` 자식 프로세스와 연결한다. 여러 대화를 호스팅하는 런타임은 한 연결에서 세션별 문맥을 명시한다. 기존 CLI·MCP는 같은 공통 서비스 함수를 호출한다.

MCP는 모델이 협업 기능을 호출하는 인터페이스로 유지한다. ACP는 공통 연결에 활용할 후보로 기록하되, 이번 구조의 필수 의존성으로 삼지 않는다.

### 공개 계약

| 인터페이스 | 책임 |
|---|---|
| `initialize` | 프로토콜 버전·지원 기능 협상 |
| `session.open/update/close` | 프로필·대화에 결속된 참여, 상태 변경, 종료 |
| `operation.call` | 기존 협업 기능을 공통 서비스로 호출 |
| `events.subscribe` | 세션별 메시지·승인 요청·상태 변경 알림 |
| `delivery.report` | 입력 큐 수락·문맥 인계·거부 등 실제 관측 보고 |
| `decision.response` | 호스트가 수집한 사용자 답을 정확한 요청에 결속 |

`operation.call`의 공개 작업 목록은 기존 CLI·MCP와 대조해 명시적 허용 목록과 JSON Schema로 제공한다. 임의 셸 실행이나 내부 함수 호출 인터페이스는 제공하지 않는다. 세션 관리·사용자 답 수집 인터페이스는 모델용 도구 목록에 노출하지 않는다.

기능은 기본 참여·메시징 계약과 팀/보드·첨부·사용자 판단·워커의 확장 계약으로 나눈다. 확장은 전체 구현 범위를 나누는 모듈이며, 완료 범위에서 제외하는 장치로 사용하지 않는다.

### 신원·전달·복구

- 공개 신원은 머신·런타임·프로필·대화를 구분하는 불투명 식별자로 표현한다. 런타임 이름을 Claude/Codex 두 값으로 제한하지 않는다.
- 호스트의 실제 대화와 연결된 세션 핸들을 사용한다. 모델이 넘긴 발신자 이름·cwd·PID를 그대로 신원이나 권한으로 채택하지 않는다.
- 대화 신원과 실행 세대를 분리한다. 같은 대화의 재접속, 새 대화, 동명 세션 교체를 구별한다.
- 기존 요청 ID·정규화·다이제스트·인수 토큰·복구 저장소를 재사용한다. 단순 조회나 stdout 출력 성공으로 소비 확인을 만들지 않는다.
- 저장, 네이티브 큐 수락, 문맥 인계, 소비 확인, 회신, 업무 결과를 분리한다. 큐 수락만으로 최종 ACK하지 않는다.
- FYI는 깨우지 않고 다음 자연스러운 소비 경계에서 처리한다. 미지원 능력은 명시적으로 반환하며 임의로 깨우기·재개로 대체하지 않는다.
- 연결 종료는 미독 삭제나 상대 업무 취소를 뜻하지 않는다. 확인 불명인 변경 요청은 상태를 조회한 뒤 복구한다.
- 기존 승인 결속 규칙을 유지한다. 에이전트가 인용한 승인 문장을 사용자 답으로 승격하지 않는다.

### 공통 클라이언트와 연결부

TypeScript·Python 클라이언트를 제공한다. 연결·재접속·요청 상관관계·알림·오류 처리를 공유하고, 정책·정본 저장은 xsm 공통 서비스가 담당한다.

하네스 연결부에는 다음만 남긴다.

1. 실제 세션·프로필·작업 폴더·생명주기 취득.
2. 입력 큐와 작업 경계에 메시지 전달.
3. 사용자 질문 표시와 실제 답 반환.
4. 워커 시작·중단 등 네이티브 실행 기능 연결.

새 런타임을 추가할 때 공통 엔진에 런타임 이름별 분기를 넣지 않는 것을 구조 검증 기준으로 삼는다.

## 3. 구현 순서와 Reason 재사용

| 단계 | 산출물과 통과 조건 | 초기 예상 |
|---|---|---:|
| P0. 계약·현황 정리 | 기존 기능 전수표, 공개 명세·스키마, 신원·전달 상태 계약, 네 후보 안정판 API 확인 | 2–3일 |
| P1. 공통 서비스·프로토콜 | CLI·MCP 동작을 유지하며 공통 서비스 추출, stdio 서버, 일반 참여자 등록·수신·복구 | 7–10일 |
| P2. 클라이언트·검사기 | TS·Python 클라이언트, 독립 참조 참여자, 적합성·장애 주입 검사, 120초 검사 명령 | 3–5일 |
| P3. Pi·OpenCode | 두 런타임에서 같은 프로토콜로 기존 세션 참여·송수신·승인·워커·재개 검증 | 8–12일 |
| P4. Hermes·OpenClaw | 로컬 UI·게이트웨이 연결, 프로필·라우팅·외부 전송 경계와 전체 기능 검증 | 12–20일 |
| P5. 통합·배포 준비 | 두 운영체제의 전체 행렬, 실제 메신저 검사, 설치·업데이트·제거·문서 검증 | 5–8일 |

**총 37–58개 작업일, 숙련된 개발자 1명 기준 약 8–12주**의 초기 추정이다. 실제 이식 속도는 아직 측정하지 않았다. P0와 첫 네이티브 연결 후 남은 일정을 다시 산정하며, upstream API 변경을 기다리는 기간은 별도로 보고한다.

Reason 공개 소스는 `bcf045cf7eadcbff25965fd6b12afeb88ab819ea`를 재사용 검토 기준으로 고정한다.

- Pi·OpenCode의 이벤트 처리와 메시지 주입 코드를 가져와 공통 클라이언트에 연결한다.
- Hermes의 대화별 연결·프로필 분리·실패 복구와 관련 테스트를 재사용한다.
- Reason의 엔진·데몬·우편함·정책은 필수 의존성으로 도입하지 않는다.
- 가져오는 원본과 로컬 수정은 구분하고, 출처·라이선스·NOTICE·해시·변경 이력을 남긴다.
- Reason 테스트의 모의 호스트 결과를 실제 런타임 검증으로 계산하지 않는다.

조사 시점의 안정판인 Pi 1.4.0, OpenCode 1.19.5, Hermes 0.22.5, OpenClaw 2026.10.9를 첫 검증 기준으로 고정한다. 설치된 Pi 0.58.1은 차이와 업데이트 안내를 확인하는 별도 표본으로 둔다.

Hermes의 필요한 API가 안정판에 없거나 게이트웨이에 적절한 시험 경계가 없으면 해당 조건을 미완으로 기록한다. 자동으로 다른 버전·모델·축소된 지원 범위로 바꾸지 않는다.

## 4. 빠른 검증과 실제 환경 검사

### 매 수정 시: 모델·메신저 없는 핵심 검사

새 프로토콜과 변경된 핵심 경로를 한 명령으로 실행해 **120초 이내**에 결과를 반환한다. 기존 전체 테스트를 이 시간에 억지로 포함하거나 생략하지 않는다.

- JSON Schema·버전 협상·미지원 기능·표준 오류 검사.
- TS와 Python 참여자의 양방향 상호운용.
- 공유 호스트의 여러 세션, 같은 대화 ID를 가진 다른 프로필, 대화 전환과 이전 실행 세대의 늦은 응답.
- 중복 요청, 같은 ID의 다른 본문, 인수 후 종료, 확인 유실, 취소·재접속·권한 철회.
- FYI 무깨우기와 다음 자연 소비, 요청·회신·업무 결과의 구분.
- 승인 하나의 중복 사용, 다른 질문·대화의 답 오결속.
- 외부 모델 호출 없이 실제 파일·프로세스·stdio 경로도 실행한다. 시간 경과 검사는 가짜 시계를 사용하고, 영속성 검사는 실제 프로세스 종료를 사용한다.

검사기가 결함을 잡는지도 확인한다. ACK 선행, FYI 깨우기, 세션 문맥 누락, 승인 재사용을 각각 주입하면 관련 검사가 실패해야 한다.

### 연결부 변경 시: 실제 런타임 검사

격리 홈·임시 저장소에서 시작·종료·전환·입력 큐 인계·재개·사용자 UI를 검사한다. 모델 없이 확인할 수 있는 경계는 모델 없이 실행하고, 실제 회신과 사용자 답 결속은 별도 네이티브 시험으로 확인한다.

유휴 전달 지연은 macOS·Linux의 고정 버전별로 100회 측정한다. 단조 시계로 저장 시점과 실제 입력 큐 수락 시점을 기록하며 실패·타임아웃도 보존한다. p95 목표를 넘는 경로를 지원 완료로 표시하지 않는다.

### 관련 변경·릴리즈 시: 게이트웨이·메신저 검사

게이트웨이의 실제 세션·권한·큐 처리는 실행하고, 플랫폼 연결만 로컬 시험용 전송 계층으로 대체한다. Telegram·Discord 두 플랫폼을 실제 외부 전달의 기준 표본으로 삼고, 다른 플랫폼은 공통 게이트웨이 계약 지원과 실제 플랫폼 검증 여부를 구분한다.

실제 플랫폼에서는 라우팅·표시·사용자 답·최종 외부 전달을 확인한다. 외부 발송과 권한 변경은 승인된 시험 계정에서만 수행한다. 이 검사가 미실행이면 외부 메신저 지원은 미완이다.

최종 통합에서는 6개 런타임의 방향 있는 조합 **30개**, 같은 런타임의 서로 다른 세션 간 통신, 원격 머신 왕복을 확인한다. 조합별 메시징 검증과 각 런타임의 보드·첨부·승인·워커 검증을 구분해 중복을 줄인다.

## 5. 이행·문서·릴리즈 조건

문서는 `docs/protocol/`에 명세·스키마·예제·적합성 검사 실행법을 모으고, `docs/plan/runtime-protocol/`에 단계별 수용 조건과 증거를 기록한다. README에는 런타임·버전·실행 모드별 지원 상태와 제한을 표시한다.

이 작업은 기존 동작을 보존하는 구조 변경으로 진행한다.

- CLI·MCP는 별도 구현을 복제하지 않고 공통 서비스로 이동한다.
- 기존 Claude/Codex 전송과 저장 데이터는 실제 호환 대상으로 유지한다. 기존 메시지 헤더와 요청 다이제스트를 이유 없이 바꾸지 않는다.
- 새 능력 정보는 기존 기록을 읽을 수 있는 추가 데이터로 관리한다. 이전 기록에 없던 전달·소비 증거를 소급 생성하지 않는다.
- 개발 중 새 프로토콜 경로는 미완일 수 있지만, 각 단계의 기존 경로 회귀 검사는 통과해야 한다. 미완 단계를 전체 지원 완료로 발표하지 않는다.
- 전체 회귀·운영체제·런타임·승인·메신저·설치 검증이 끝나기 전 병합·릴리즈하지 않는다.
- 기존 안정 릴리즈와 상태 백업으로 되돌리는 절차를 검증한다. 새로 생성된 협업 기록을 삭제해 되돌리지 않는다.

최종 완료는 **공개 명세만 보고 구현한 참여자의 상호운용**, **네 신규 런타임의 전체 기능 증거**, **120초 핵심 검사**, **p95 1초 로컬 인계**를 모두 충족했을 때 선언한다.
