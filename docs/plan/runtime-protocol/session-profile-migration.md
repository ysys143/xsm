# Home 간 세션 승계와 승인 복구 통합 계획

2026-11-05. 상태: 로컬 구현과 필수 수용 검증 완료. home별 정체·명시적 승계·원본 은퇴·
24시간 전달·상태 이관과 실제 격리 Claude 두 home 시험을 실행했다.
[검증 결과](../../../deliverables/issue27-implementation-20261105/verification.md)에 14기준과
명령·원시 출력을 대응시켰다. 전체 저장소의 조건부 skip 3건은 별도 미실행으로 표시한다.
아래는 승인된 설계·구현 순서와 그 판단 근거다.

사용자 지시: [이슈 #27](https://github.com/ysys143/xsm/issues/27)을
[승인 복구 계획](approval-recovery-test-alignment.md)과 함께 해결한다.
사용자가 정한 예전 이름·ref 자동 전달 기간은 **승계 완료 후 24시간**이다.

## 사용자와 문제

계정 한도 때문에 같은 native 세션의 transcript를 다른 config home에 복사해
이어가는 사용자와, 그 세션에 보고하던 워커가 대상이다. 원본과 사본이 함께 살아
있어도 서로를 사칭하지 않고, 명시적으로 넘긴 뒤에는 원본이 다시 조율 자리를
차지하지 않아야 한다. 미처리 메시지와 요청의 출처·처리 여부도 이어서 볼 수 있어야 한다.

## 확인한 원인과 영향

조사 시점의 `identity.ref_of`와 canonical message identity는 runtime·home·session_id를
포함하지만, 당시 `registry._record_path`는 runtime·session_id만 포함했다.
`upsert`가 다른 home의 같은 세션 등록을 덮어쓴다. `_me`에도 home 없이 session ID만
비교해 호출자를 고르는 경로가 있다.

임시 홈에서 A → B → A 등록을 실행한 결과, 매번 등록 파일은 1개였고 마지막에는
B 환경에서 호출해도 A의 ref를 반환했다. 고정 fixture PID를 사용한 제품 함수 재현이며,
실제 두 Claude 프로세스 시험은 아니다. 원시 결과는
`deliverables/approval-recovery-issue27-plan-20261105/registry-collision.json`에 있다.
첫 프로브는 macOS 임시 경로의 realpath 차이 때문에 A/B 표시를 잘못 비교했다.
그 결과는 별도 파일에 오류로 보존했고, 정규화한 경로로 다시 실행해 확인했다.

AST로 찾은 직접 registry 조회·저장 호출은 **11개 파일 33곳**이다.
이는 영향 범위의 하한이며 inbox·workers처럼 session ID를 자체 키로 사용하는 경로는
별도로 조사한다. 직접 호출 목록은 같은 폴더의 `registry-call-sites.json`에 있다.

기존 `handover`는 팀 자리·미확인 DM·미완 질문의 이관과 주소 추적을 갖고 있다.
그러나 원본을 일반 세션으로 계속 실행하게 하며, 승인 요청의 home 재결속이나
worker coordinator 연결의 이관은 맡지 않는다. 기존 handover 전체를 새로 만들지 않고
이를 공용 서비스로 재사용하되, 프로필 승계에는 별도의 은퇴·기한·재개 규칙을 둔다.

## 설계 결정과 미확정 사항

- settled | 원본과 사본은 `(runtime, canonical_home, session_id)`가 다른 정체다.
  ref 계산을 바꾸지 않고 등록 저장·조회와 호출자 판별을 이 정체에 맞춘다.
- settled | 24시간은 승계 완료 시각부터 계산한다. 전달 만료와 원본 은퇴 해제는 별개다.
- settled | 자동으로 자리를 빼앗지 않는다. 대상이 등록돼 있다는 사실만으로 승계되지 않는다.
- settled | 요청 이관과 권한 답변 재사용은 별개다. 새 home에서 실행할 권한은 새 요청에
  결속한다. peer의 업무 질문과 실제 사용자에게 묻는 권한 질문도 구분한다.
- settled | 새 세션에서 `xsm migrate <이전 ref>`로 원본 하나만 지정하는 진입점을 구현했다.
  후임은 현재 세션으로 확정하고, 폼에 원본·후임·이관 효과를 보여 준다.
  CLI·MCP/native는 같은 서비스와 승인 controller를 사용한다. 인자 없는 호출은 따라잡기 조회다.
- assumed | native transcript 복사 자체는 하네스의 절차로 유지한다. xsm은 복사한 맥락이
  최신이라고 단정하지 않고 xsm에 보존된 메시지·상태를 보여 준다.
- open | 이미 덮어써져 원래 endpoint 근거가 사라진 기존 등록·발신은 자동 복원할 수 있는지
  별도 확인한다. 근거가 없는 항목은 unknown으로 보존하고 복원 성공으로 세지 않는다.

## 구현 순서와 단계별 통과 조건

### 1. home별 등록과 호출자 식별

등록 파일과 명시 조회에 home을 포함한다. home을 모르는 조회에서 같은 세션 ID가
여러 개면 첫 항목을 택하지 않고 모호함을 반환한다. 훅은 입력·환경의 실제 home을,
CLI/MCP는 해당 caller context의 home을 사용한다. 목록에 두 endpoint를 따로 표시한다.

등록·adoption·갱신·SessionEnd·정리·프로토콜 소유권 lock과 live-binding 검사를
함께 바꾼다. 조회·쓰기 API를 먼저 확정하고 확인한 33곳과 자체 키 경로를 이관한다.
home 하나의 종료나 prune이 다른 home의 기록을 지우지 않는지도 검사한다.

기존 저장 파일은 안에 기록된 home으로 정확한 새 키에 이관한다. 이미 사라진 다른
home의 기록을 추측해 만들지 않는다. 동시 갱신의 직렬화와 중복 이관 방지를 포함한다.
예전 바이너리와 새 바이너리가 함께 쓰면 은퇴 규칙이 적용되지 않을 수 있으므로,
승계 전 양쪽이 지원 버전을 쓰는지 확인한다. 제품이 전역 설정을 몰래 바꾸지는 않는다.

통과 조건: A/B 동시 존재, 각 home의 caller·종료 독립, 동일 home의 정상 resume,
기존 저장 파일 이관, 다른 네 런타임의 protocol 등록·소유권 검사 통과.

### 2. 승인 복구 테스트와 안내 정리

별도 승인 복구 계획의 작업 9종·허용/거절 18사례를 정확한 endpoint로 실행한다.
변경 전 106개·16실패를 기준으로 대응표를 만들고, 기존 helper의 CLI 전환 전제를
같은 MCP 복구로 이관한다. 문구 검사와 실제 권한 적용 검사를 분리한다.

통과 조건: 기존 12건과 추가 4건의 대응 검사가 모두 통과하고, 다른 home에 복사된
허용 답변·질문 ID를 현재 home의 권한으로 사용하지 않는다.

### 3. 명시적 승계, 원본 은퇴, 24시간 전달

승인 범위에 원본과 후임의 전체 endpoint 및 실행 세대를 고정하고 적용 전에 재검증한다.
승계 요청·준비·원본 차단·상태 이동·완료를 기록한다. 재시도는 같은 승계 ID로
이어가며, 중간 실패를 완료로 보거나 새 승인으로 위장하지 않는다.

프로필 승계가 확정된 원본은 훅 재등록·adoption·CLI·MCP 발신과 읽기 소유권 갱신에서
은퇴를 확인한다. 원본을 후임으로 가장해 발신시키지 않는다. 되찾으려면 현재 후임과
그 효과를 보여 주는 별도 사용자 결정을 받는다. 기존 handover의 일반 세션 동작은 보존한다.

이전 ref·보존한 이름·정확한 P2P endpoint는 24시간 동안 후임으로 전달한다.
동명 후보가 여러 개면 추측하지 않는다. 후임에 대한 현재 scope·block 등도 검사한다.
기한이 지난 주소는 후임 정보와 전달 만료를 알리고, 원본 소켓으로 되돌아가지 않는다.
24시간 전후의 실제 대기는 테스트 clock으로 대체한다.

연락하던 세션에 보내는 변경 공지는 승계 ID로 중복을 막고 실제 전송·미확인·실패를
나눈다. 새 전달 규칙과 기존 원격 handover 증언의 관계도 검사한다. 로컬 commit 성공과
다른 머신 통지 성공을 합쳐서 보고하지 않는다.

통과 조건: 허용/거절의 효과, 이전 창 재개 차단, 전달 기한 경계, 동시 발신과 공지의
중복 방지, retry·실패 복구를 확인한다.

### 4. 밀린 상태와 팀장 연결 이관

| 상태 | 승계 처리와 검증 |
|---|---|
| 미확인 DM·배달 | canonical 원문·발신자·원 대상·message ID·기존 배달 경로를 보존한다. 후임 수신은 별도로 기록하고 기존 ACK를 만들지 않는다. |
| 기존 claim·진행 중 ACK | 원본의 소유권을 종료하고 후임에서 새 claim을 만든다. 이전 token의 늦은 ACK가 후임 메시지를 닫지 못하게 한다. |
| held 메시지 | 보류 이유와 출처를 함께 이관한다. 승계를 보류 해제나 전달 승인으로 취급하지 않는다. |
| peer 질문·그룹 | 질문·응답 연결을 보존해 후임이 늦은 답을 확인한다. 상대의 최종 답을 합성하지 않는다. |
| 사용자 승인 요청 | 필요한 요청 내용을 이어받고 현재 대상 상태를 재검증한다. 새 home의 새 질문으로 결속한다. 기존 허용·소비·적용 기록은 원래 이력으로 보존한다. |
| 팀·보드·worker 연결 | 기존 handover의 팀 자리와 보드 이관을 재사용한다. coordinator를 후임에 연결하고, 워커의 대기 가입 요청이 다시 로컬 질문을 열거나 중복 DM을 만들지 않는지 검사한다. |
| 따라잡기 목록 | 승계 시각·원본/후임·원 대상·배달·ACK·이관 여부를 함께 표시한다. 복사 시점이 불명확하면 그 이전 메시지가 맥락에 없을 수 있음을 남긴다. 미확인 전체와 기간 조회를 제공한다. |

native 큐나 원본 transcript에 이미 들어간 내용을 지웠다고 주장하지 않는다.
xsm 밖에서 원본이 이미 시작한 파일 수정이나 cron을 이 기능이 중단시키지는 않는다.
새 xsm 권한 행위 차단과 이미 발생한 실행의 기록을 구분한다.

통과 조건: 승인 요청 이관 뒤 예전 allow가 적용되지 않고 새 질문이 필요한지,
held가 유지되는지, worker 요청과 미확인 원문이 빠짐없이 남는지 확인한다.

### 5. 거부된 발신 기록과 진단

resolve 실패도 message ID·요청 대상·발신 endpoint·시각·사유와 함께 기록한다.
대상이 확정되지 않은 본문은 우선 발신자의 기록이다. 승계 기록으로 이전 endpoint와의
관계가 증명된 항목만 후임의 따라잡기 목록에 보인다. 임의의 미등록 ref를 사용해
다른 사람의 발신을 읽게 하지 않는다. 자동 재전달을 선택한다면 현재 권한 재검사와
같은 message ID의 중복 억제가 필수다. 우선 구현 계약은 조회 가능한 실패 기록이다.

doctor는 같은 runtime·native ID의 home별 endpoint, 실행 세대, 승계·은퇴·전달
만료 상태를 보여 준다. 목록에서 안 보인다는 이유만으로 후임 종료를 단정하지 않는다.

통과 조건: 거부 내역을 후임이 확인할 수 있는 정확한 범위와, 복원 불가 항목의 unknown
표시를 검사한다. 진단 결과와 실제 endpoint·소켓 배달 기록이 일치해야 한다.

## 통합 검증과 완료 기준

다음 14항목을 검사 ID로 대응시키고, 아래 항목이 모두 충족되기 전 #27 완료로 쓰지 않는다.

1. A/B/A 재등록 뒤 두 endpoint와 각자의 발신자·수신 경로가 유지된다.
2. 모호한 home 조회는 다른 세션을 선택하지 않는다.
3. 기존 파일 이관과 home별 SessionEnd·prune이 서로의 상태를 손상시키지 않는다.
4. 승계 거절은 이름·자리·권한·메시지를 바꾸지 않는다.
5. 승계 허용 뒤 원본 재개·재등록·발신·늦은 ACK가 후임의 자리를 되찾지 못한다.
6. 같은 home의 일반 resume과 기존 일반 handover는 계속 동작한다.
7. 전달이 24시간 경계와 시계 역행에서 명시된 상태를 반환하며 원본으로 회귀하지 않는다.
8. 승계 중 들어온 메시지와 공지가 유실·중복 적용 없이 추적된다.
9. 미확인 DM·held·peer 질문·그룹의 원문과 처리 상태가 보존된다.
10. 사용자 승인 요청은 새 home에 재결속하며 예전 허용·claim을 재사용하지 않는다.
11. 팀장·worker 연결과 대기 가입 요청이 후임으로 이어지고 워커 로컬 질문이 생기지 않는다.
12. 실패 발신과 따라잡기 목록이 원 endpoint의 근거와 조회 권한을 지킨다.
13. 등록 충돌·은퇴·전달 기한·후임 상태를 doctor가 정확히 구분한다.
14. 단계별 중단 주입과 retry에서 거짓 완료·이중 적용 없이 복구되고 검사 목록에도 포함된다.

모델 호출 없는 임시 홈·프로세스·소켓·protocol wire 검사로 먼저 확인한다.
등록 키 누락, source fencing 누락, 24시간 경계 우회, 옛 home 답변 재사용,
중간 이관 누락의 결함을 각각 임시 복사본에 넣어 대응 검사가 실패하는지도 확인한다.

공통 경로 변경의 다른 런타임 영향은 각자의 protocol·native fixture 검사로 확인한다.
실제 원 사고 경로는 마지막에 격리 Claude 두 home에서 같은 native ID의 사본을 사용한
작은 시험으로 확인한다. 이는 사용자의 실제 프로필이나 진행 중인 세션을 이관하는 시험이
아니다. native 훅 변경이나 실제 환경 차이가 다른 하네스에도 영향을 주면 해당 경로를
추가 재시험하고, 실행하지 않은 범위는 그대로 미완으로 보고한다.

승인 복구의 기존 요구, 이 문서 14항목, 관련 unit/integration 검사, 정식 gate,
전체 Python 탐색 결과를 함께 보고한다. source commit·시각·하네스·합성/실측을

## 산출과 반영 경계

구현은 정체 → 승인 복구 → 명시적 승계 → 밀린 상태·진단의 로컬 커밋으로 나눈다.
각 단계에서 관련 검사가 통과한 근거를 붙인다. 저장 형식과 공개 API·결과가 바뀌면
해당 schema·SDK·CLI·MCP/native·README·스킬도 함께 갱신한다.
여러 하네스의 행동을 별도 승인 코드로 나누지 않는다.

정체 기반과 승인 복구의 구현·검사 자료는 `deliverables/issue27-implementation-20261105/`에
있다. 필수 수용 기준 14개와 승인 복구 기준은 해당 결과에서 확인했다.
조건부 과거 원시 로그 재생 2건과 relay 재시험 1건까지 실행했다고 주장하지 않는다.
사용자 프로필·권한·운영 세션은 바꾸지
않았고, 이슈 댓글·push·PR·병합·릴리즈도 하지 않았다.
