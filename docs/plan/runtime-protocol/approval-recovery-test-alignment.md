## 사용자와 목적

사용자는 가입과 권한 질문이 어떤 도구에서 시작됐든 일관되게 처리되기를 원한다.
에이전트는 사용자 답을 정확한 요청에 연결하고, 실제 허용 뒤에만 한 번 적용해야 한다.
개발자는 승인 구현을 바꿨을 때 정식 검사에서 회귀를 발견할 수 있어야 한다.

남은 실패 12건을 처리하면서, 문구 검사에서 가려진 뒤쪽 동작 검사까지 복구한다.

## 결정과 제약

- settled | 최초 요청은 구상이었고, 이후 사용자가 `계획 완수`를 지시해 구현을 시작했다.
  push·이슈 게시·PR·병합·릴리즈는 이 목표의 승인으로 추론하지 않는다.
- settled | 실제 런타임 재검증 비용을 줄이라는 기존 사용자 지시를 유지한다.
- settled | MCP에서 시작한 승인 복구는 정확한 원 질문으로 답을 받고 같은 MCP 도구와
  같은 인자로 재시도한다. CLI 자체에서 시작한 승인의 지원은 별도 경로로 유지한다.
- settled | 명시적인 거절, 질문 닫기, 표시 여부가 불명확한 client decline을 구분한다.
  불명확한 decline을 실제 사람의 거절이나 허용으로 만들지 않는다.
- settled | 기존 검사 삭제, 실패 제외, 문구 assertion 삭제만으로 해결 처리하지 않는다.
- assumed | 기존 승인 controller와 native 답변 판독기를 재사용한다. 공개 결과 계약을
  바꿔야만 해결되는 결함이 발견되면 이 가정을 다시 검토한다.
- settled | 사용자 답변: 예전 이름·ref의 자동 전달은 승계 완료부터 24시간이다.
  전달 만료로 원본 프로세스의 은퇴가 풀리지는 않는다.
- settled | home 변경 때 미처리 승인 요청은 이어받되 기존 home의 허용 답변·소비 표식·
  claim token을 새 home의 권한으로 복사하지 않는다. 대상 상태를 재검증하고 새 결속으로
  사용자에게 질문한다. 처리 완료 기록은 원 소유자의 이력으로 보존한다.

## 수정과 검증 순서

### 1. 실제 실패 목록을 고정한다

두 테스트 묶음의 첫 격리 실행은 위 106개·16실패로 기록했다. 기존 12건과 추가 4건
각각을 새 동작 검사에 연결하는 대응표를 만든다. 같은 경로의 추가 실패도 대응표에
포함한다. 문구 검사가 뒤의 동작 검사를 막지 않도록 두 책임을 분리한다.
home별 정체를 고친 뒤에는 이 기준 실행과 변경 후 실행을 나눠 기록한다.

### 2. 공통 helper를 새 승인 복구 경로로 이관한다

기존 문자열만 바꾸는 접근은 뒤의 CLI 전환 전제를 남긴다. 공통 helper가 실제 MCP
dispatch와 native 답변 판독기를 통과하고 부작용까지 검사하도록 바꾸는 방식으로 진행한다.
새 승인 구현이나 하네스별 승인 엔진은 만들지 않는다.

helper의 흐름은 다음과 같다.

1. 실제 operation을 MCP로 호출해 표시 불가 또는 질문 닫힘 상태를 만든다.
2. 보존된 원 질문과 선택지를 읽고, 호출 전후 권한 상태가 같은지 확인한다.
3. 임시 native 기록에 해당 질문의 사용자 답을 넣는다. 합성 근거임을 명시한다.
4. 같은 MCP 도구와 인자로 재호출하고, 실제 권한·기록·적용 횟수를 확인한다.
5. 한 번 더 재호출해 재적용이나 새 질문이 발생하지 않는지 확인한다.

작업별 검사는 link, join, leave, reach, worker approve, 기본 grant,
범위 밖 grant, remote pairing grant, 문서 endorse의 9종이다.
각각 허용과 거절을 실행하는 18개 사례에서 실제 효과와 무효과를 검사한다.
선택값은 작업의 실제 choices를 사용한다. 예를 들어 grant의 `allow once`,
endorse의 `endorse`와 `not now`를 일반 `allow`·`deny`로 바꿔 넣지 않는다.
remote grant 검사는 승인 대상 폴더와 grant 범위를 확인하며 실제 SSH 연결은 만들지 않는다.
해당 검사는 원격 통신 검증으로 보고하지 않는다.

표시 불가·cancel·명시적 거절·불명확한 decline의 차이는 공통 controller 검사로
확인하고, 작업별 18개 사례와 연결한다. 실제 권한 승인 여부를 안내 문구로 추론하지 않는다.

### 3. 안내와 문서 검사를 정리한다

- 정확히 일치해야 하는 원 질문·요청 표식·선택지는 그대로 엄격하게 검사한다.
  그 밖의 설명문은 질문 도구, 같은 MCP 재시도, 불필요한 CLI 전환 금지를 검사한다.
- Claude 안내에는 사용할 수 있는 질문 도구를 명시한다. 하네스별 안내는 기존
  공통 안내 함수를 재사용하되 원 질문 밖에 둬서 질문 원문을 바꾸지 않는다.
- Codex를 포함한 다른 하네스에 Claude 전용 도구를 지시하지 않는지도 검사한다.
- README의 직접 터미널 사용 예시는 에이전트에게 승인을 맡기는 흐름과 구분한다.
  문구 검사의 예외는 해당 예시에 한정한다. 사용자에게 터미널 입력을 떠넘기는
  제품 안내를 잡는 나머지 검사는 유지한다.

### 4. 답변 경계와 검사 자체를 확인한다

기존 검사와 중복되는 사례는 재사용하면서, 같은 dispatch 경로에서 다음을 확인한다.

- 다른 질문·세션·폴더의 답변으로는 적용되지 않는다.
- 만료되거나 소비된 답변은 재사용되지 않는다.
- 취소 지시는 이전 allow를 막고, 독립적인 재개 말만 원 질문의 답을 보존한다.
- 자동 reviewer나 다른 에이전트의 메시지는 사람의 답이 되지 않는다.
- 승인 폼이 열린 동안 워커가 종료되면 적용하지 않는다.

임시 소스 복사본에 다음 다섯 결함을 각각 주입해 대응 검사가 실패하는지 확인한다.
원 작업 트리에는 결함을 넣지 않는다.

1. 같은 MCP 재시도에서 native 답변 복구를 끊는다.
2. deny를 적용 허용으로 바꾼다.
3. 질문 일치 검사를 우회한다.
4. 적용 완료 결과의 재사용을 끊어 같은 작업을 다시 적용한다.
5. 정식 검사 목록에서 승인 테스트 묶음을 뺀다.

### 5. 정식 검사에 포함하고 전체 결과를 확인한다

`scripts/check-protocol.py`의 기존 격리·병렬 실행을 사용한다. 두 누락 묶음과
승인 복구의 필수 모듈을 중복 없이 포함하고, 목록 누락은
`tests/test_protocol_gate.py`에서 검사한다. 별도의 정식 검사기를 추가하지 않는다.

실행 순서는 아래와 같다. 모든 Python 탐색도 격리된 HOME·XSM_HOME·Claude/Codex
홈에서 수행하고, 종료 코드·실행 수·실패·skip을 원시 로그로 남긴다.

```bash
python3 -B -m unittest tests.test_person_decisions tests.test_mcp_forms tests.test_decisions tests.test_native_consent tests.test_answer_binding tests.test_open_consent tests.test_worker_project_flow -q
python3 -B scripts/check-protocol.py
python3 -B -m unittest discover -s tests -t . -q
```

직접 관련된 묶음 통과 뒤 정식 gate와 전체 Python 탐색을 각각 한 번 실행한다.
새 변경이나 실패 원인 없이 같은 검사를 반복하지 않는다. gate의 기존 시간 한도를
넘으면 원인을 측정하고 실행 구성을 조정한다. 실패 묶음을 빼서 맞추지 않는다.
추가 실패가 나오면 원인과 영향을 기록하고 완료 판정을 보류한다.

## 실제 런타임 검증 조건

현재 계획의 첫 검증은 모델 호출 없이 실제 제품 CLI·MCP·답변 판독 경로를 실행하는
통합 검사다. 기존 6종 실제 가입 자료는 이전 관측 근거로 보존하며 새 코드의 실측으로
다시 표시하지 않는다.

안내 문자열과 테스트 이관 외에 native 훅·답변 형식·하네스 어댑터가 바뀌거나,
실제 환경에서만 재현되는 차이가 남으면 해당 하네스에서 실제 승인 복구를 재시험한다.
Claude/Codex의 공통 안내 변경이 다른 네 런타임까지 실행을 요구하는지 역시 변경 경로로
판정한다. 필요한 실제 재시험이 끝나지 않았다면 해당 항목을 미완으로 남긴다.
모든 실제 시험은 격리 상태와 구독 경로를 사용한다.

## 운영 사례 보완: cctrace 훅 오류와 XSM 등록

사용자가 추가로 제공한 운영 보고는 Claude의 SessionStart·SessionEnd 훅 실패를
cctrace v0.7.82의 `--log-to-file` 미지원으로 진단했다.
보고 당시에는 `~/.claude`와 `~/.claude-3`의 네 명령에 해당 옵션이 있었고,
다른 시작 훅 세 개는 정상 종료했다고 한다. 이는 사용자 제공 관측과 원인 가설이다.

2026-11-05 현재 로컬을 읽기 전용으로 확인한 결과는 다음과 같다.

- 설치된 cctrace는 v0.7.82이고 `sync --help`에 `--log-to-file`이 없지만,
  실제 parser는 해당 옵션을 인식했다. 도움말만 요청하면 exit 0이므로 그것만으로
  옵션 인식 여부를 판정하지 않았다. 아래 대조 시험과 소스를 함께 확인했다.
- 빈 임시 HOME·Claude 폴더에서 `sync --dry-run --claude-dir <임시 폴더>`는
  `no profile found`로 exit 1이었다. 여기에 `--log-to-file`을 넣어도 같은 오류였다.
  실제 없는 옵션 `--xsm-unknown-probe-flag`를 넣으면 `unknown flag`로 exit 1이었다.
  앞의 프로필 오류는 의도적으로 빈 시험 환경을 만든 결과로, 운영 장애의 원인이라는
  뜻이 아니다. 데몬 기동·서버 동기화는 실행하지 않았다.
- 로컬 `claude-code-trace/cmd/cctrace/sync.go`에도 해당 bool 옵션의 등록과
  `MarkHidden("log-to-file")`이 있다. 도움말에서 빠졌다는 사실과 미지원은 다르다.
  현재 바이너리에서는 보고된 옵션 미지원 원인을 재현하지 못했다. 운영 당시 실제
  바이너리와 전체 stderr는 확보하지 않았으므로 과거 원인을 확정하지 않는다.
- `~/.claude/settings.json`의 시작·종료 훅 두 곳에는 옵션이 남아 있다.
  `~/.claude-3/settings.json`에는 현재 cctrace 훅이 없다.
  보고 당시의 네 곳을 현재 상태로 단정하거나 네 곳을 일괄 수정하지 않는다.
- 두 프로필의 XSM 시작·종료·사용자 프롬프트 훅은 설치 runtime
  `~/.xsm/runtime/08ee10b16402`를 가리킨다. 해당 설치본과 checkout의
  `xsm/receive.py`는 SessionStart 분기 전에도 `register`를 호출한다.
  Claude에서 첫 프롬프트 전 미등록을 무조건 정상으로 볼 수 없다.

따라서 다음 내용을 구현 시 검증에 포함한다.

1. 훅 오류는 프로필, 이벤트, 실제 실행 파일, 인자, 종료 코드로 구분한다.
   외부 훅의 Usage 오류를 XSM 등록 실패로 판정하지 않는다.
2. XSM은 시작·resume·첫 프롬프트의 등록 상태를 나눠 확인한다. 등록되지 않았다면
   `session_id`·home·pid 누락 또는 다른 상태 경로 사용 여부를 훅 관측과 대조한다.
   훅 설정의 존재와 exit 0만으로 실제 등록을 판정하지 않는다.
3. 지원하지 않는 옵션이라는 가설은 해당 시점의 실제 parser 오류로 확인한다.
   현재 지원되는 `--log-to-file`을 제거하는 수정은 이 조사로 정당화되지 않는다.
   cctrace 자체의 수정이 필요하면 별도 관리 영역에서 원인을 재현하고 처리한다.
   XSM 설치기가 외부 훅을 덮어쓰지 않는 기존 계약을 유지한다.
   실제 프로필 수정은 이번 구상에 포함하지 않는다.
4. 지원 옵션 확인과 실제 동기화 성공을 구분한다. 명령이 parser를 통과해도 데몬 기동과
   서버 수신을 확인하기 전에는 복구됐다고 쓰지 않는다. 반대로 잘못된 훅 명령만으로
   기존 데몬까지 멈췄다거나 모든 동기화가 중단됐다고 단정하지 않는다.
5. 외부 훅이 실패하는 환경에서 XSM이 실제로 계속 실행·등록됐는지는 독립적인 근거로
   확인한다. 제품 훅 단독 실행이나 합성 dispatcher를 실제 Claude의 훅 실행 근거로
   대신하지 않는다. 필요한 native 관측이 없으면 미확인으로 남긴다.

이 보완은 오류를 올바른 계층에서 진단하기 위한 것이다. XSM에 cctrace 의존성이나
외부 훅 자동 수리 기능을 추가하는 설계가 아니다. 이번에는 설정과 CLI 도움말·parser,
설치 코드를 확인했으며, 운영 세션 재현·추가 LLM 호출·서버 동기화는 실행하지 않았다.
