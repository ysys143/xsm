## 목표와 기존 결정

여러 에이전트가 합의·작업 분담·진행 공유의 문맥을 함께 보고, 반복 중계와 컨텍스트 낭비를 줄일 수 있는 채널을 설계 가설로 검토한다. 특정 상대의 실제 답과 업무 결과를 회수하는 DM, 프로젝트의 현재 상태를 정리한 문서, 공동 논의를 축적하는 채널은 함께 사용한다. DM과 상태 문서만으로 같은 효과가 나는지도 평가한다. 사람용 공유 뷰의 비중·형식과 채널의 효용·비용은 미확정이다.

다음은 기존 사실이며 이번 토론으로 변경하지 않았다.

- [ADR-0005](../../adr/0005-channel-thread-store.md): 채널은 프로젝트별 로컬 영속 기록이며 멘션 깨우기는 사용자 결정으로 제외됐다. 실사용의 반복 또는 다른 기계·사람과 원본 공유가 필요하면 재검토한다.
- [ADR-0006](../../adr/0006-shared-document-editing.md): 불변 기여 노드·parents·도출 문서·사람의 endorse를 사용한다. [기존 공동 문서 구현](../../../xsm/doc.py)을 아래 재사용 후보에 포함한다.
- [ADR-0014](../../adr/0014-shared-board.md): 공유 메시지 풀과 대시보드는 Discussing이다. 이를 이미 승인·구현된 보드로 간주하지 않는다.
- [ADR-0003](../../adr/0003-no-wrapper-runtime-boundary.md): 기존 세션·하네스를 계속 사용하고 로컬 핵심 경로에 새 상주 서버를 필수로 두지 않는다.
- [ADR-0021](../../adr/0021-cross-machine-network-and-membership.md): 네트워크 기기 멤버십은 세션 협업·파일·실행 권한이 아니다.
- [ADR-0024](../../adr/0024-discover-select-and-handshake.md): 선택한 실제 대화와의 결속을 유지한다. 두 개의 pair 허가는 제3자끼리의 허가를 만들지 않는다.

`DM`은 이 문서에서 특정 세션에 보내는 메시징을 가리키는 설명 용어다. 기존 명령·와이어 형식을 이름 변경하거나 기능을 활성화한 것은 아니다. 원격 공유·알림·보존은 검토 대상이며 그 구현 범위를 사용자가 확정한 것으로 쓰지 않는다. 아래 검증 순서는 범위를 축소하는 결정이 아니다.

### 사용자 원문과 다른 세션의 보고

이번 대화에서 사용자는 “이건 좀 필요한거 아냐? 다만 xsm의 p2p 모델과 충돌해서 그렇지”, “공유 채널의 명칭은 room, board, channel 중에 뭐가 좋을지 고민이네.”라고 탐색했고, “claude-worker와 함께 비판적 토론을 통해 설계를 정교화시켜봐.”라고 지시했다. 앞의 탐색을 원격 채널 구현이나 구체 정책 승인으로 해석하지 않는다.

claude-worker는 다른 대화에서 사용자가 에이전트 간 합의·작업 분담·진행 공유, 컨텍스트 낭비 억제, 사용자 승인을 받은 팀장과의 결재 연결을 언급했다고 보고했다. 공지에는 다중 수신 메시지·마크다운 상태판도 가능하고 결재 범주의 사전 고정은 선호하지 않는다는 설명도 전달했다. 이 보고의 원문은 [4차 회신](../../../deliverables/channel-design-debate-20261030/r4.json)에 보존했다. 코디네이터는 해당 사용자 대화의 인증된 원문을 확인하지 않았으므로 참고 요구와 확인 대상이며 이 세션의 사용자 승인으로 승격하지 않는다.

## 토론에서 달라진 판단

| 쟁점 | 최초 가정·제안 | 반례 | 정교화한 결과 |
|---|---|---|---|
| 채널 필요성 | 채널 사용이 적다는 관측을 확장 필요성에 대한 반대 근거로 봄 | 현재 채널은 전파·알림이 없어 낮은 사용량이 새 설계의 무용을 뜻하지 않음 | 필요성 미실측. 상태 문서·DM·다중 수신 전달을 기준선으로 비교 |
| DM 재사용 | 기존 DM으로 참여자에게 fan-out | fingerprint에 receiver가 포함되고 전역 ID가 충돌. 질문 회신은 한 target에 결속 | 게시 이벤트와 수신자별 전달 상태를 분리. DM의 전송 기술을 재사용하되 권한과 완료 의미는 자동 확장하지 않음 |
| 채널 권한 | 기존 pair 결속을 “N자 확장”하면 새 ACL 불필요 | A-B와 A-C 허가는 B-C 허가가 아님 | 채널별 read/post 권한 객체가 새로 필요. DM pair로 전개하지 않음 |
| 실행 | 채널에서 task/outcome을 빼면 실행을 일으키지 않음 | 모델이 글을 읽고 이미 승인된 업무를 수행할 수 있음 | 가입·게시 자체가 새 실행 권한이나 task 완료를 주지 않는다고 표현. 질문·다중 답글은 유지 |
| 반복 정지 | native wake만 보류 | 다음 자연 턴의 자동 요약으로 느린 순환이 계속됨 | 자동 wake·본문 주입·자동 요약 반영을 함께 보류. 수동 조회·쓰기 권한과 분리 |
| 철회 | 서명된 membership view만 있으면 소급 게시 판정 가능 | 제명된 작성자가 오래된 허용 head와 시각을 재사용 가능 | view는 필요 근거이지만 충분하지 않음. 증명되지 않은 사건의 격리·가용성 비용·증명 그래프를 별도 계약으로 남김 |
| 이벤트 식별 | 내용 해시와 parents면 충분 | 같은 내용의 두 의도적 게시, 부모 없는 root의 누락, 재시도 때 새 nonce 생성 | 생성 nonce와 canonical bytes를 먼저 저장. 재시도는 동일 이벤트. 별도 inventory/frontier로 누락 회수 |

벽시계 정렬에 관한 최초 주장도 정정했다. 현재 [render](../../../xsm/channel.py)는 답글을 root 아래에 묶으므로 root와 첫 답글이 언제나 뒤집힌다고 말할 수 없다. 같은 root의 깊은 답글 사이의 순서, 부모 미도착 때 숨는 orphan, 로컬 부모가 없으면 게시를 거부하는 경로가 구체적인 반례다.

## 1. 기록·권한·알림을 구분한다

사용 흐름은 다음처럼 검토한다. 참여자·공유 범위·알림 정책을 사용자가 선택했다는 가정의 예시이며 기본값을 확정한 것이 아니다.

1. 작성자는 채널에 제안·질문·진행을 한 번 기록한다. 결과는 로컬 보관과 replica별 전달 상태를 구분한다.
2. 각 수신 기기는 권한 있는 기록을 복제하고, 로컬 정책에 해당하는 구독에만 제한된 notice를 보낸다.
3. 참여자는 현재 권한으로 필요한 스레드를 페이지 단위로 읽고, 기존 업무 범위 안에서 토론·작업·답글을 이어간다. 본문을 읽기 전에는 소비 확인하지 않는다.
4. 특정 담당자의 답·업무 결과가 필요하면 해당 게시물을 참조한 DM 질문을 사용한다. 채널의 여러 답과 DM의 특정 상대 회신을 섞지 않는다.
5. 사람의 판단이 필요한 결론은 채택한 역할·결재 경로를 통해 실제 사용자에게 묻고, 확인된 답만 결정으로 연결한다. 채널 합의 자체는 사용자 승인으로 바뀌지 않는다.

다음 객체명은 계약을 설명하기 위한 가칭이다. 구현 자료형이나 공개 API를 확정한 것이 아니다.

| 객체 | 책임 | 다른 상태로 승격하면 안 되는 것 |
|---|---|---|
| 채널 정의·권한 | 안정된 channel ID, 검증된 구성원과 read/post 범위, 정책 변경의 근거 | 네트워크 가입·이름·폴더 유사성을 채널 권한으로 읽지 않음 |
| 게시 이벤트 | 불변 본문·작성자·채널·부모·자료 참조와 생성 당시 정책 근거 | 글의 question 태그나 지시문을 도구 실행 승인으로 읽지 않음 |
| 복제 상태 | 어느 허가된 replica가 어떤 이벤트를 보관했는지 | 보관을 UI 열람·모델 소비로 읽지 않음 |
| 참여자별 읽은 위치 | 실제 참여자가 어떤 이벤트를 조회·소비했는지 | 목록·notice 출력만으로 본문 ACK하지 않음 |
| 로컬 알림 상태 | 검증한 구독에 대한 알림·깨우기·자동 본문 주입·정지 | 원격 요청만으로 임의 CID를 깨우거나 로컬 정책을 변경하지 않음 |
| 연결된 DM 요청 | 지정 상대의 실제 회신과 outcome | 채널의 첫 답·마지막 답을 자동으로 task 완료로 읽지 않음 |

권한과 알림 선호·읽은 위치는 독립 개념이다. 이를 반드시 별도의 ACL 두 개나 저장소 두 개로 구현할 필요는 없다. 채널 구성원을 CID에 한정할지, 더 오래 사는 단위에 허가한 뒤 CID별로 구독할지는 U01에서 정한다. 새 CID에 이전 CID의 unread·읽은 위치를 자동 승계하지 않는다. 권한의 적용·승계 여부는 U01에서 택한 주체·범위와 검증 절차를 따른다.

## 2. 불변 이벤트와 인과관계

1. 채널 이름·저장소 경로 해시는 표시 또는 로컬 대응에 쓴다. 머신 사이에서는 명시적으로 결속한 안정된 channel ID를 사용한다. 기존 로컬 로그를 자동 공개·이전하지 않는다.
2. 이벤트는 검증된 작성자 신원, channel ID, 고정 생성 nonce, 부모 참조, 정책 근거, 본문과 자료 참조를 canonical bytes로 만든 뒤 **첫 전송 전에 영속한다**. 인증 서명·해시의 정확한 범위와 스키마는 후속 명세 대상이다.
3. event ID를 canonical 내용의 충분한 길이의 해시로 구성하는 안을 검토한다. 같은 의도의 재시도는 같은 nonce·내용을 재사용하고, 의도적인 두 번째 게시에는 새 nonce를 쓴다. 선언한 ID와 계산한 내용 해시가 다르면 거부·격리한다. 서명처럼 해시 범위 밖의 증거 필드는 별도 인증한다. 동일한 검증 내용에 대한 유효한 여러 증거는 내용 하나로 dedupe하고 증거를 보존하며, 무효 증거는 기존 원문이나 권한 상태를 바꾸지 않는다. 실제 같은 해시에 다른 내용이 검증되는 경우도 정상 중복으로 처리하지 않는다. 정확한 해시·서명 범위는 후속 명세 대상이다.
4. 현재 `uuid4().hex[:10]`은 40비트다. 균등 독립 ID라는 가정에서 10만 건의 충돌 확률은 약 0.454%, 100만 건은 약 36.54%다. 원격 병합의 전역 키로 그대로 쓰지 않는다. 기존 short ID는 origin/channel namespace를 가진 legacy alias로 보존하며 모호한 참조를 임의 해석하지 않는다. [계산 기록](../../../deliverables/channel-design-debate-20261030/id-collision.json)
5. 부모·답글 관계의 인과를 보존하고 동시 글에는 결정적인 표시 순서를 정한다. 모든 노드의 전역 실시간 순서나 벽시계의 진위를 약속하지 않는다. 명시적 read 권한이 없는 부모를 자동 fetch하지 않는다.
6. 부모가 늦으면 허용된 사건을 pending parent로 보존하고 누락 상태를 표시하는 안을 검토한다. 부모가 없다는 이유로 글을 조용히 숨기거나 완전한 스레드처럼 표시하지 않는다. 부모가 비공개·만료·삭제된 경우도 구분한다.
7. 내용 해시와 parents만으로 다른 root의 누락을 알 수 없다. 읽기 권한을 검증한 replica끼리 inventory/frontier를 교환하는 회수 계약이 필요하다. 발신자별 seq는 필수 여부가 미정인 회수 인덱스 후보이며 해시·인과와 같은 보장으로 설명하지 않는다.

권한 없는 상대에게 inventory·frontier·게시물 존재·개수를 공개하지 않는다. 크기·페이지·전송·저장 상한과 초과·회수 불가 표시도 계약에 포함한다. 보존 기간과 용량 수치는 아직 정하지 않았다.

## 3. DM 기술의 재사용과 권한 경계

[network_messages.Gateway](../../../xsm/network_messages.py)는 단일 sender/receiver와 그 둘을 포함한 fingerprint에 결속한다. [questions](../../../xsm/questions.py)의 회신도 원 요청의 정확한 target에서 온 것만 인정한다. 따라서 채널 글 하나를 같은 request ID로 여러 대상에 보내거나 여러 작성자의 답을 한 DM 질문의 final outcome으로 합치지 않는다.

기존 전송 어댑터, 내구성 있는 outbox·멱등 처리·claim/ACK 기법, [출처 표시](../../../xsm/provenance.py)를 재사용한다. 게시 이벤트와 수신자별 전달 ID는 별도다. 읽을 권한이 있는 채널의 notice를 받을 권한과 기존 DM pair 허가는 서로 대신하지 않는다. 새 채널 권한을 기존 native 수신 게이트와 연결하는 구체 인터페이스는 구현 전 명세가 필요하다.

채널 question 태그와 여러 참여자의 답글 스레드는 유지한다. 첫 답이 곧 결론은 아니다. 지정 상대의 답·업무 결과가 필요하면 이벤트를 참조하는 DM 질문을 별도로 사용한다. 채널 글을 자동으로 task로 바꾸거나 기존 DM 권한을 새로 생성하지 않는다. 채널에서 읽은 요청에 따라 이미 승인된 업무를 수행하는 것과 새 권한을 얻는 것은 다르다.

원격 기기가 주장한 `author.kind=human`, `decision`, 승인 문구를 로컬 사용자의 결정으로 기록하지 않는다. 기기 서명은 그 기기의 증언이지 수신 기기 사용자의 직접 승인 증거가 아니다. 원격 사용자 결정의 표시·수락은 별도 권한 계약으로 다룬다. 같은 UID가 로컬 파일을 고칠 수 있는 기존 위협 모델의 한계도 유지한다.

### 기존 공동 문서·상태판과의 관계

[doc.add](../../../xsm/doc.py)는 기여 노드를 O_EXCL로 만들고 parents·wip·endorse와 도출 정본을 제공한다. 불변 기여·부모 관계·사람의 명시적 endorse라는 의미와 표시 규약을 재사용 후보로 삼는다. 현재 노드의 경로·표시 작성자·로컬 부모 검사·짧은 ID는 원격 채널의 인증·전역 키·누락 회수와 같지 않으므로 기존 형식을 네트워크 와이어로 그대로 쓰지 않는다. 별도 데이터 엔진을 복제하기 전에 도출 뷰·참조 규약을 어디까지 공유할지 확인한다.

검토자는 기존 작업에서 `pg_cuvs_docs/bench-prep/PHASE.md`라는 조율자 단독 writer의 상태판을 Git으로 공유하고 변경을 DM으로 알렸다고 보고했다. 절 구성은 실행 중 단위·사용자 결정 대기·자원/비용·최근 변경·재개 메모라고 설명했다. 이번 작업에서는 그 파일의 존재·바이트·운영 효과를 직접 검증하지 않았고 별도 프로젝트를 새로 조사하지 않았다. 다만 **실제 사용했다고 보고된 기준선**으로 기록하고 효과를 비교할 때 원자료 확인을 선행한다.

팀장·결재 연결은 U04의 미결 정책이다. 채택한다면 채널 합의가 요청에 결속된 사용자 질문을 거쳐 결정 기록으로 돌아오는 흐름을 명시하고, 합의·팀장 역할·사용자 승인을 서로 구별해야 한다. 이를 xsm의 필수 계층이나 사전 고정 결재 범주로 확정하지 않는다. 기존 elicitation·decision·endorse를 검토하며 다른 세션의 승인 보고를 로컬 승인으로 복사하지 않는다.

## 4. 알림과 모델 소비

검토한 기본 구조는 **게시·복제를 먼저 보관하고, 로컬 정책에 따라 notice를 만들며, 읽기 시 현재 권한을 다시 검사하는 것**이다. 이것은 기본 알림을 켜기로 승인한 뜻이 아니다.

- notice에는 peer 본문·미리보기를 넣지 않는 안을 제안한다. 이름은 로컬에 결속된 표시값을 escape하고, 개수·이벤트 참조는 로컬의 검증된 기록에서 계산·제한한다.
- 발신자는 임의 수신 CID를 지정하지 못한다. 로컬의 검증한 구성원/구독에서 실제 native 대화를 고른다. `question` 등 peer 태그만으로 우선순위나 깨우기 강도를 높이지 않는다.
- pending notice를 묶되 시간·크기·최대 대기 상한을 둔다. backlog 동기화는 새 실시간 사건과 구별해 폭발적인 깨우기를 막는다. 구체 값은 미정이다.
- notice 성공·native 도달·UI 조회·모델의 본문 소비·ACK를 구분한다. notice를 읽었다는 이유로 본문을 읽었다고 표시하지 않는다.
- 저장 뒤 알림이 실패해도 게시를 실패로 되돌리거나 새 event로 재게시하지 않는다. 수신자별 부분 성공과 재시도 상태를 표시한다.
- notice와 본문 조회에는 명시적 입력 예산을 적용한다. 토큰을 정확히 셀 수 있는 tokenizer가 없으면 바이트/문자 수의 hard cap과 표시된 추정치를 사용하며 정확한 토큰 상한을 달성했다고 주장하지 않는다. 초과분은 페이지·참조로 넘기고 반환한 사건만 소비 확인한다. 자동 요약을 원문이나 확정 정본으로 대체하지 않는다. 예산 값·단위는 U03/U06에서 정한다.

사람이 보는 공유 뷰의 형식은 미결이다. CLI·MCP 조회·별도 UI 중 무엇을 제공할지 결정하지 않았으며, IRC 클라이언트·새 상주 서버·새 하네스를 필수로 만들지 않는다. 외부 네트워크 서비스가 멈춰도 로컬 기록·조회와 기존 DM은 유지해야 한다.

## 5. 철회·분단과 보장할 수 없는 것

현재 [기기 멤버십](../../../xsm/network_membership.py)은 전역 합의 시계나 악성 멤버의 암호학적 제명을 보장하지 않는다. 오프라인 replica가 제명을 모르는 동안 새 글을 옛 구성원에게 복제할 수 있고, 이미 받은 사본을 회수할 수 없다. 따라서 “어느 순간에도 현재 멤버만 읽는다”와 오프라인 가용성을 함께 약속하지 않는다.

이벤트에 작성자가 본 정책 view를 결속하는 것은 필요하지만 충분하지 않다. 제명된 기기는 오래된 허용 view를 다시 참조할 수 있다. 벽시각·서명·오래된 view만으로 제명 전 게시였음을 증명하지 못한다.

토론에서 나온 보수적 후보는 **제명보다 앞선 것으로 증명되지 않는 사건을 격리해 자동 표시·알림에서 제외하는 것**이다. 다른 허가된 구성원이 그 사건을 참조한 증언을 사용한다면, 그 증언 자체가 제명보다 앞섰는지를 검증할 수 있어야 한다. 현 멤버십 그래프와 이벤트 그래프를 연결하는 증명 형식은 아직 정의되지 않았으며 이 후보를 구현 가능한 완성 알고리즘으로 쓰지 않는다.

정직한 오프라인 작성자의 마지막 글도 증인이 없어 격리될 수 있고, 허용된 답글의 부모만 격리돼 문맥이 비는 경우가 생긴다. 이를 표시해야 한다. 격리 사건의 보관·조회·재분류와 정책 분기의 해소, 받은 사본의 보존은 사용자 정책과 후속 명세가 필요하다. 강한 현재성을 원한다면 온라인 권위·합의·lease 등 다른 가용성 비용을 검토해야 한다.

## 6. N:N 반복·정지·재개

[abuse](../../../xsm/abuse.py)의 directed pair별 관측을 채널 전체의 제어라고 부르지 않는다. fan-out 전달 N개를 게시 N개로 세지 않고 검증된 고유 이벤트를 센다. 스레드 안의 반복뿐 아니라 새 root를 계속 만드는 패턴과 작성자·채널별 집계도 본다. `traceparent`는 생략·새 root 생성이 가능하므로 관측 보조이며 차단 권한의 근거가 아니다.

local pause는 자동 wake와 자동 본문·요약 주입을 함께 보류하고, 원문 저장·동기화는 계속한다. 정지 상태·근거·미전달 범위는 재시작 후에도 복구하고 metadata로 표시한다. 기존 읽기·쓰기 권한과 수동 조회를 자동으로 박탈하지 않는다. 자동 발신 보류 여부는 별도 협업 정책이다.

원격 pause는 로컬 정책에서 권한이 확인되기 전까지 권고·표시다. 동료가 임의로 다른 기기의 모든 스레드를 정지시키거나 재개할 수 없어야 한다. 분산 합의 없이 전역 정확 cap이나 전역 동시 정지를 보장하지 않는다. 상한·집계 기간·재개 주체·사람의 개입 조건은 미정이다. 내용에 새 정보가 있는지는 스킬의 판단과 실행기 강제 조건을 구분한다.

| C19 | notice·본문·반복 조회가 입력 예산을 넘는 큰 이력 | 채택한 hard cap·token/추정 단위 표시, 페이지·참조·소비 위치 보존, 자동 요약을 정본으로 승격하지 않음 |

효용 평가는 같은 팀·같은 과업에서 상태 문서+DM/다중 수신 전달을 기준선으로 비교한다. 사람이 중계한 횟수, 같은 질문 재설명, 새 참여자의 catch-up, 중복 작업, 총 모델 입력을 본다. 기록 복제율·notice 도달·UI 조회·모델 소비를 따로 측정하고, 읽힘이 0인 표본도 실패 관찰로 남긴다. 자동 요약의 정확성과 토큰 비용도 비교하며 개선을 미리 가정하지 않는다.

검증 순서의 후보는 로컬 공유 대화의 실제 소비·효용 관찰 뒤 원격 공유를 채택한 경우 머신 간 복제·권한·분단 반례를 검증하는 것이다. 원격 검토 항목을 폐기하지 않으며 공유 범위의 채택은 U07로 남긴다. 구현 순서와 출시 판단은 사용자가 정하고, 로컬 성공을 원격 완료로 올리지 않는다.

## 9. 토론 증거와 남은 한계

1–4차 요청·회신 ID와 코디네이터 반박은 [원문 기록](../../../deliverables/channel-design-debate-20261030/transcript.md)에 있다. 3·4차의 `outcome=succeeded`는 검토 완료이며 구현·정책 승인이 아니다. 4차 문서 검토 뒤 새 CID의 unread/권한 승계 표현, 해시 내용과 증거 필드의 구분, 원격 요구의 미확정 상태를 바로잡고 공동 문서 재사용·입력 예산·결재 경로의 미결을 보강했다. 그 뒤 문서 수정을 검토자가 다시 승인했다고 주장하지 않는다.

claude-worker가 제시한 기존 사용량은 원장 잔여 파일 수·채널 줄 수·표시 이름·본문 preview와 시간 구간을 사용한 보고다. 코디네이터가 원자료를 전수 검증하지 않았고 별도 원시 근거 파일도 확보하지 못했다. 따라서 동기 설명으로만 보존하고 채널 필요성·중계 병목·토큰 절감의 결론 근거로 쓰지 않았다. 본 토론에서 새 원격 수집을 요청하거나 실행하지 않았다.

확인한 수치 계산은 40비트 ID 충돌의 확률식뿐이며, 이것도 실제 충돌 재현 검사가 아니다. 코드 읽기와 두 에이전트의 합의는 테스트 통과·사용자 동의·분산 프로토콜의 형식 검증을 대신하지 않는다.
