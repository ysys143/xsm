## T0

**ack 토큰 형식.** 수신 안내는 claim 객체를 보여 주며 "이 토큰으로 xsm_ack"라고 했지만, CLI와 MCP는 32자리 토큰 값만 받았다. `receive.claim_token`이 토큰 값, claim 객체, 그 JSON 문자열을 모두 받아 토큰을 꺼낸다(`ack_inbox`, `release_inbox`). 안내 문구는 `xsm_ack(tokens=[...])`와 `xsm ack <token>`의 정확한 형태를 보여 준다. MCP `xsm_ack`도 객체를 받는다. 검증: `tests/test_handoff_consumer.py::AckTokenFormTest` 4건, 수정 전 코드에서 실패 1·오류 2.

**MCP "hook record 없음".** 재현 조사로 확인한 것:
- 실패한 세션(`codex-worker-2`)과 같은 데몬의 다른 세션(`성과 요약하기`) 모두 등록 기록에 권한 모드가 없다(`mode: None`). 훅이 아닌 경로(CLI 자기 등록 또는 MCP 넘겨받기)로 등록됐다.
- 데몬과 MCP 서버의 `CODEX_HOME`은 `.codex-3`로 맞다. "서버가 자기 홈을 잘못 안다"는 가설은 틀렸다.
- 그 스레드는 지금 `.codex-3` 상태 DB에 있고 넘겨받기 조건도 충족한다. 실패 당시에는 스레드가 막 생겨 상태 DB에 행이 없었거나, 같은 데몬의 다른 기록이 끝난 상태였을 가능성이 있으나 재현하지 못했다.

원인을 확정하지 못했으므로 이번에는 진단을 고쳤다. MCP 거부 문구가 호출이 지명한 Codex 스레드와 호출자 조회가 끝난 근거를 싣는다(이전에는 서버 환경에 스레드 ID가 없어 Claude용 일반 문구 "no hook record for it"가 나왔다). 검증: `tests/test_mcp_identity.py::UnresolvedCodexCallTest`, 수정 전 실패. 다음에 같은 거부가 나오면 그 문구의 "caller lookup" 근거로 원인을 확정한다. 이 항목은 원인 미확정으로 남긴다.

## T1

`xsm/multisend.py`. `xsm send A B C --text ...`, MCP `xsm_send(targets=[...])`.

- 수신자를 먼저 모두 해석하고, 같은 세션을 두 번 지명하면 하나로 합친다. 자기 자신은 거부한다.
- 범위 밖 로컬 수신자는 연결 제안 없이 건너뛰고 결과에 이유를 적는다(D14). 원격(SSH·P2P) 수신자는 `send.send`가 판단한다.
- 수신자마다 자기 메시지 ID로 기존 `send.send`를 부른다. 묶음 ID와 수신자별 ID·상태·본문은 `~/.xsm/groups/<id>.json`에 남는다.
- 대기는 묶음 전체에 한 번(`--wait`), 그 안에서 로컬 수신자의 영수증을 센다.
- 종료 코드는 가장 큰(나쁜) 수신자 코드(D17). `--resend <묶음 ID>`는 미확인·unknown·error인 수신자만 같은 ID로 다시 보낸다(단일 `--resend`와 같은 기준).

구현 시 택한 기본값(사용자 확인 전):
- **수신자 표시 방식(D15)**: 본문 첫 줄에 `(also sent to: ...)`를 싣는다. 헤더 필드는 로컬에만 닿고 SSH·P2P 형식은 엄격해 양쪽을 함께 바꿔야 하므로, 세 경로와 구버전 수신자에 모두 닿는 본문 방식을 택했다. 받는 쪽에서는 보낸 쪽의 주장(peer data)이다.
- CLI 문법: 대상을 위치 인자 여럿으로 받는다. 한 번에 최대 16명.
- 첨부·`--held`·`--request-id`는 수신자 하나일 때만 받는다.
- 원격 수신자의 영수증은 묶음 대기에서 세지 않는다(로컬만).

검증: `tests/test_multisend.py` 11건(범위 밖 건너뛰기, 수신자 표시, 중복·자기 자신, 상한, 묶음 대기, 실패 수신자만 재전송, 다른 세션의 묶음 재전송 거부, CLI 종료 코드·JSON, 단일 대상 기존 경로, MCP `targets`). 관련 모음 407건 통과.

## T2

`xsm/question_groups.py`. `xsm ask A B C --text ...`, MCP `xsm_ask(targets=[...])`, `question-status <묶음 ID>`.

- 수신자 해석·범위 판정은 T1의 `multisend.plan_recipients`를 함께 쓴다. 범위 밖 수신자는 건너뛰고 결과에 적는다.
- 수신자마다 기존 `questions.ask`로 하위 질문 `<묶음>-<n>`을 만든다. 상관 회신·늦은 답·부분 답·outcome·ACK는 하위 질문마다 기존 경로 그대로다. 수신자 표시는 T1과 같은 본문 첫 줄.
- 묶음 상태: `pending`, `reply_received`(일부 답, 일부 대기), `replied`(모두 답했거나 끝남), `final`(모두 outcome), `refused`. `waiting_on`에 아직 답하지 않은 수신자를 적는다.
- 답의 claim 토큰은 하위 질문마다 `receive.claim_question_replies`로 붙이고 모아서 돌려준다(`question_groups.with_claims`).

구현 시 택한 기본값(사용자 확인 전):
- **`--wait` 종료 조건**: 모든 수신자가 답했거나 끝났을 때(또는 기한·취소). 첫 답에서 끝나는 선택지는 두지 않았다.
- 첨부·`--request-id`는 수신자 하나일 때만 받는다.
- 하위 질문은 `question-status`(ID 없이) 목록에 각자 나타난다. 묶음 자체는 목록에 따로 넣지 않았다.

검증: `tests/test_question_groups.py` 6건(건너뛰기와 하위 질문, 수신자별 답과 상태 전이, 다른 상대의 답 거부, 기한·전원 답·poll, 다른 대화의 묶음 읽기 거부, CLI·MCP). 질문·연결 관련 모음 50건과 전체 관련 모음 통과.

## T3

`xsm/teams.py`(로컬 기록·권한·주소), `xsm/team_sync.py`(머신 간 복제), `xsm team ...`, MCP `xsm_team`.

- 저장: `~/.xsm/teams/<팀>/team.json`. 구성원·팀장·세대 번호·변경 기록(누가, 무엇을, 어떤 승인으로).
- 권한(D19): `config.scope_for`에 팀 판정을 더했다. 두 세션이 같은 팀 구성원이면 `team:<팀>` 범위다. pair 허가로 펼치지 않으며 팀 밖 세션에는 아무것도 열지 않는다. `team_aware=False`로 팀을 뺀 범위를 따로 볼 수 있다(추가 규칙 판정용).
- 변경 규칙(D20, D5): 팀장은 같은 project(팀을 뺀 범위) 세션을 넣고 뺀다. 범위 밖 세션 추가는 사용자 승인. 팀장이 아닌 구성원의 추가도 사용자 승인. 팀장 지정은 항상 사용자 승인. 구성원은 스스로 나갈 수 있다. CLI는 `_person_or_refuse`(사람의 말을 판정으로 남김), MCP는 승인 양식(`allowed`)으로 묻는다. `xsm_team`은 정확한 호출자 신원이 필요한 도구(WIDENING)이고 설치기의 양식 도구 허용 목록에 들어간다.
- 팀 주소: `team:<팀>` 또는 `#팀`. 보내는 세션이 구성원이어야 하며, 구성원의 현재 주소로 펼쳐 T1·T2의 다중 수신 경로로 보낸다. 실행 중이 아닌 구성원은 보내지 않고 이름을 알린다.
- 알림(D23): 팀 DM은 보통 DM처럼 즉시. `xsm team mute`로 끈 구성원에게는 깨우기 없이 저장(`--wake never`와 같음)된다.
- 머신 간(D22): 팀이 바뀌면 그 머신의 서비스가 원격 구성원 머신마다 팀 기록을 끝점 형태로 보낸다(로컬 `team-publish`, 상대 `team`). 받는 머신은 보낸 머신과 자기 머신에 구성원이 있을 때만, 같은 팀 ID의 더 새 세대만 받아 자기 끝점을 로컬 이름 구성원으로 되돌린다. P2P 수신 허가(`network._permission`)가 팀 기록을 확인하므로 구성원 사이 DM에 쌍별 grant가 필요 없다. 팀 DM을 보내기 전에 원격 구성원이 있으면 다시 보낸다.

구현 시 택한 기본값(사용자 확인 전):
- **다른 머신 구성원은 대화(세션 ID) 단위**다. P2P 끝점에 이름이 없어서 이름으로 맞출 수 없다. 로컬 구성원은 이름 단위(D26). 다른 머신 구성원이 바뀌려면 인수인계(T8)를 거친다.
- 팀 이름은 머신마다 유일하다. 다른 머신에서 같은 이름의 다른 팀 기록이 오면 받지 않고 `conflict`로 답한다.
- 두 머신이 동시에 바꾸면 합치지 않고 더 새 세대(같으면 더 큰 기기 키)가 이긴다.
- 알림 끄기는 보내는 쪽이 같은 머신의 설정을 읽어 적용한다. 다른 머신 구성원의 끄기는 적용하지 않는다.
- 팀 생성자는 팀장이 아니다. 팀장은 사용자 승인으로만 정해진다.

검증: `tests/test_teams.py` 14건(이름·중복, 추가 규칙, 팀 권한이 구성원 사이에만 열리고 끝난 세션은 제외, 제거·팀장 규칙, 이름 단위 재시작, 팀 주소와 끄기, 비구성원·실행 중이 아닌 구성원, CLI 흐름, MCP 도구, 원격 기록 받기·순서·충돌·거부, 끝점 변환, 네트워크 허가 판정, 서비스에 닿지 못할 때의 알림). 네트워크 허가 시험은 팀 판정을 뺀 코드에서 실패한다. 네트워크·연결·수신 관련 모음 326건 통과.

## T4

- `connect`가 사용자 선택을 적용할 때 기존 선택 기록과 함께 구성원 둘인 팀 `pair-<선택 ID 앞 10자>`를 만든다(`teams.make_pair`). 결과 범위는 `team:pair-...`다. 사용자 선택·핸드셰이크(실제 상대의 상관된 성공 회신) 계약은 그대로다.
- 구성원은 선택한 두 대화 자체(세션 ID)다. 같은 이름의 다른 대화는 이 짝에 들지 않는다. 이름이 없는 세션도 대화 단위 구성원이 될 수 있다(`teams.member_of`가 이름이 없으면 세션 ID로 붙잡는다).
- 짝 팀에서 한쪽이 나가면 선택 기록도 내린다(`collaboration.drop_id`). 그래서 팀을 떠난 뒤 옛 선택이 권한으로 남지 않는다.
- 다른 머신 상대: 기존 선택 증언(grant) 전달 뒤 짝 팀을 그 머신에 보낸다(`team_sync.publish`). 새 상대는 팀 기록으로, 0.5.0 상대는 선택 증언으로 허가한다.
- 0.5.1 이전의 선택은 `xsm team list`(MCP 포함)가 짝 팀으로 보여 준다(`teams.adopt_pairs`). 권한은 이전과 같이 선택 기록 자체가 유지한다.

구현 시 택한 기본값(사용자 확인 전):

`xsm/board.py`, `xsm/board_sync.py`, `xsm board show|set|log|sync <팀>`, MCP `xsm_board`. `xsm/doc.py`에 항목(`item`)과 결재 참조(`decision`) 필드를 더했다(없는 노드의 ID 계산은 이전과 같다).

## T6

결재 기록은 보드 옆 `~/.xsm/teams/<팀>/decisions/<ID>.json`에 둔다(ADR-0026 결정 7). 회의록은 두지 않는다(D23).

- 기록 경로는 둘뿐이다. MCP `xsm_decide`에 `team`(과 선택적 `item`)을 주면 사용자가 양식에서 고른 답을 기록하고(`via: mcp-elicitation`), 사람이 직접 `xsm board decide <팀> <항목> --text <답>`을 실행하면 세션 없이 기록한다(`via: terminal`, 구성원 확인 없음). 그 밖의 `via`나 세션 없는 비대화형 호출은 거부한다. 세션이 CLI로 `board decide`를 부르면 xsm_decide를 쓰라고 거부한다.
- 기록 ID는 기록 내용의 해시(앞 12자)이고, 파일은 한 번만 쓴다(O_EXCL). 같은 ID로 다른 답을 덮어쓸 수 없다.
- 항목을 주면 그 항목을 답으로 정하는 사람 작성 노드를 쓰고, 노드에 결재 ID를 단다. 렌더는 기록이 있으면 "decided by …: 질문 -> 답"을, 기록이 없으면 "decision <ID> has no record here: not confirmed"를 보인다. 노드에 결재 ID를 적는 것만으로는 결재가 되지 않는다.
- 머신 간: 결재 기록도 보드 노드와 함께 원격 구성원 머신에 보낸다. 받는 머신은 ID가 내용과 맞는 기록만 받고 `from_machine`을 붙여 그 머신 사용자의 증언으로 보인다("decided on machine X by …"). 이 머신 사용자의 승인으로 쓰지 않는다(ADR-0021).
- 팀 없는 `xsm_decide`는 지금처럼 channel에 올린다. 이 경로의 새 위치는 T11에서 정한다.

구현 시 택한 기본값(사용자 확인 전):
- 결재 범주를 정하지 않는다(D21). 무엇을 결재로 올릴지는 스킬 안내(T10)가 정한다.
- 팀장 경유(D19)는 기록 조건으로 강제하지 않는다. 구성원 누구의 xsm_decide든 사용자의 답이면 기록한다. 팀장이 결재를 모으는 흐름은 스킬 안내(T10)로 둔다.
- `xsm board decisions <팀>`이 기록 목록을 보인다.

검증: `tests/test_board.py::DecisionTest` 6건(기록과 항목 설정·작성자 표시, 기록 없는 결재 ID 표시, 사용자 답만 기록·덮어쓰기 불가, xsm_decide 팀 경로, 사람의 `board decide`와 세션 거부, 다른 머신 기록의 증언 처리·변조 거부). 소스를 바꿔 넣은 변이 5종(기록 없는 결재 ID를 믿음, 받을 때 ID 검사 생략, 아무 `via`나 기록, 기록 덮어쓰기, 사람 확인 없는 `board decide`)을 각 시험이 모두 잡았다. 보드·팀·DM·질문·MCP·네트워크 관련 모음 425건 통과.

T3 시점 소스의 전체 회귀(py3.9, py3.14 각 1977건)에서 1건이 실패했다: T2에서 `skills/xsm/references/messaging.md`만 고치고 그 원본인 `xsm/instructions.py`의 `MESSAGING_GUIDE`를 고치지 않았다. 원본에 같은 문단을 넣고 `scripts/generate-messaging-guide.py --check`로 맞췄다. 같은 검사에서 사람에게 터미널 입력을 안내하는 문구 금지 규칙에 걸린 T6 문구 두 곳도 고쳤다.

## T7

`xsm/board_notice.py`. 수신 훅(`receive._with_bounces`, Claude·Codex의 UserPromptSubmit 공통 경로)이 다음 프롬프트에 팀마다 한 줄을 붙인다: `[xsm] board core: 2 items changed (decision: cache, owner/api); 1 decision recorded. Read it with ...`. 본문은 싣지 않고 항목 이름과 결재 수만 싣는다.

- 위치는 세션별로 둘이다. "읽음"은 그 세션이 보드를 읽을 때(`board show|log|decisions`, `xsm_board show|log`) 옮겨 가고, 자기가 쓴 노드와 결재는 쓸 때 읽음이 된다. "알림함"은 줄을 넣을 때 옮겨 간다. 그래서 같은 변경으로 매 턴 줄이 반복되지 않고, 새 변경이 오면 아직 안 읽은 것 전체를 센다.
- 끄기(D23): `xsm board mute <팀> [--off]`, `xsm_board` `mute`/`unmute`. 세션별·팀별이다. 꺼 둔 동안 온 변경은 알림함에 넣지 않으므로, 다시 켜면 한 번 알린다.
- 상한: 한 턴에 팀 5개까지 줄을 넣고 나머지는 "and N more team boards changed"로 센다(다음 턴에 알린다). 항목 이름은 3개까지("+N more"), 한 줄 240자. 팀마다 안 읽은 노드는 200개까지만 파싱하고 넘으면 "N+ items"로 쓴다.
- 비용: 팀 파일, 팀마다 노드·결재 폴더 목록 한 번, 안 읽은 노드만 파싱. 측정(이 머신, 팀 5개·팀당 노드 300개): 전부 안 읽은 첫 턴 39 ms, 새 변경이 없는 턴 2 ms. 보드 알림이 실패해도 프롬프트는 그대로 지나간다.
- 새 세션은 위치가 비어 있으므로 보드에 있는 것을 한 번 알린다(같은 이름의 구성원이라도 새 대화는 보드를 읽은 적이 없다).

구현 시 택한 기본값(사용자 확인 전):
- 위치를 구성원(이름)이 아니라 세션별로 둔다. 팀 DM 끄기와 같은 단위다.
- 줄은 "읽을지는 일과 관련 있을 때"라고 안내한다(스킬 `sessions.md`). 걸러 읽기(작은 모델 필터) 안내는 T9 결과를 기다린다.

검증: `tests/test_board_notice.py` 9건(한 번만 알림과 미읽음 누계, 자기 작성 제외, 여러 팀, CLI·MCP 끄기와 다시 켜기, 결재 수, 팀·항목·줄 길이 상한, 파싱 상한, 훅이 줄을 싣는지, 실패해도 프롬프트 유지). 소스 변이 10종(매 턴 반복, show가 읽음 안 옮김, 자기 작성 알림, 끄기 무시, 팀 상한·줄 상한·파싱 상한 제거, 훅이 줄을 버림, 오류가 프롬프트를 깨뜨림, 결재 수 누락)을 모두 잡았다. 관련 모음 466건 통과.

## T8

`xsm/handover.py`(기존 `handoff.py`는 받은 메시지의 claim·ACK이라 이름을 달리했다), `xsm handover <세션> --summary-file <파일>`, `xsm handover --show`, MCP `xsm_handover`(`hand_over`, `show`). 사용자의 결정이다: CLI는 `_person_or_refuse`, MCP는 양식으로 묻는다.

옮기는 것:
- 팀 자리: 옛 세션이 속한 모든 팀에서 구성원 자리를 후임으로 바꾸고, 팀장이었으면 팀장 자리도 옮긴다. 팀 기록에 `handover`로 남고, 원격 구성원이 있으면 팀 기록을 다시 보낸다.
- 보드 담당 항목: `owner/<옛 이름>`과 `owner/<옛 이름>/...` 항목을 `owner/<새 이름>...`으로 옮기고(본문 + "taken over from ..."), 옛 항목에는 "handed over to ..."를 쓴다. 팀마다 `handover/<옛 이름>` 항목에 무엇이 옮겨졌는지 적는다(D30: 팀 전체의 사실은 보드).
- 미독 DM: 아직 ACK하지 않은 메시지를 원문 봉투 그대로 인수인계 문서에 싣는다. 옛 세션 쪽 원본은 지우지 않고 `acknowledged` + `moved_to`로 닫는다(`handoff.move_out`). 옛 받은편지함 사본도 함께 옮긴다.
- 답 대기 질문: 옛 세션이 보낸 질문 중 최종 답이 없는 것의 발신자를 후임으로 바꾼다(`handed_over_from`에 원래 발신자). 질문 묶음도 같다. 최종 답이 온 질문은 옛 세션에 남는다.
- 작업 맥락 요약: 옛 세션이 쓴 요약을 인수인계 문서에 싣는다. 요약 없이는 실행하지 않는다.

이후 옛 주소로 오는 것:
- 이 머신에서 옛 세션에게 보낸 DM(이름·ref·`codex:` 주소, 옛 세션이 끝나 이름이 멈춘 세션만 가리킬 때 포함), SSH 원격 수신, P2P 수신(옛 끝점 앞 메시지, 옛 세션이 물은 질문의 원격 답)이 후임에게 간다.
- 옛 세션이 받은 질문에 후임이 답하면 이 머신의 질문 기록이 그 답을 받는다.

인수인계 문서는 DM이 아니라 후임의 다음 프롬프트에 훅이 한 번 싣는다(보드 알림과 같은 경로). 팀 자리를 옮긴 뒤에는 두 세션 사이에 범위가 없을 수 있어서다. 스킬 `sessions.md`에 "Handing over"(요약에 쓸 것: 목표와 완료 기준, 현재 상태, 결정과 이유, 열린 일과 다음 단계, 기다리는 질문, 사용자가 계속하라고 한 것)와 "Taking over"(보드 읽기, 팀에 알리기, 실린 DM에 답하기, 팀장이면 지시와 결재 경유를 이어 받기)를 넣었다. T10에서 다시 다듬는다.

다른 머신이 옛 세션에게 물은 질문(사용자 결정 2026-10-30에 따라 0.5.1 전에 구현):
- 처음 구현에서는 빠져 있었다. 묻는 쪽 머신의 게이트웨이와 질문 기록이 답한 끝점을 원래 받은 끝점과 비교하고, 이 머신의 게이트웨이도 회신 준비 때 원래 받은 대화와 보내는 대화가 같은지 확인했기 때문이다.
- 인수인계하면 이 머신의 서비스가 팀의 원격 구성원 머신과 옛 세션에게 메시지를 보낸 머신에 `{old, new}` 끝점을 보낸다(`handover-publish` → 상대 `handover`). 받는 머신은 보낸 머신이 두 끝점 모두의 머신일 때만 증언으로 받아 둔다(`remote-handovers/`, 첫 증언을 바꾸지 않음). 역방향 검사, 회신 준비의 소유 검사, 질문 기록이 "원래 끝점이거나 그 후임"을 받아들인다.
- 한계: 증언을 받지 못한 머신(그때 꺼져 있던 머신)은 그 질문의 후임 답을 받지 않는다. 다시 보내는 명령은 없다.
- 검증: `RemoteHandoverTest` 5건(증언 규칙, 연쇄, 묻는 쪽 질문 기록, 서비스의 전송 대상, 상대 요청 처리)과 실제 게이트웨이 시험 1건(후임의 회신 준비와 묻는 쪽 수락, 낯선 세션 거부). 소스 변이 9종을 시험이 모두 잡았다(역방향 검사를 늘 통과시키는 변이는 기존 시험 `test_body_binding_and_digest_are_required_even_when_callback_permits_reply`가 잡았다). 전체 회귀(py3.14) 2028건 통과(환경 조건 skip 1건).

확인 전:
- 살아 있는 옛 Codex 세션의 큐에 이미 들어간 사본이, 원본을 `moved`로 닫은 뒤 옛 세션 프롬프트에 다시 나타나는지. 실제 세션 확인 때 본다.

구현 시 택한 기본값(사용자 확인 전):
