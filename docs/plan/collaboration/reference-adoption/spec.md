# DSH·AgentTeams 반영: 효익·과잉설계 검토와 실행 계획

- 작성일: 2026-11-04
- 최초 검토 기준: XSM `4b0afd1`. 3절의 재현 결과는 구현 전 관측이다.
- 실행 상태: 사용자가 2026-11-04 계획 실행을 지시했다. P1~P3 구현과 검증 근거는 [반영 결과](results.md)에 기록한다.
- 입력: [dsh-superagent 조사](../../../references/dsh-superagent.md)의 D01~D19, [AgentTeams 조사](../../../references/agentteams.md)의 A01~A15.
- 목적: 34개 참고 후보를 현재 기능·실제 결함·추가 비용에 대조해 구현 계획을 세운다. 후보 전체가 구현 승인 목록이라는 전제는 두지 않는다.
- 근거 수준: 현재 코드·기존 테스트·격리 코드 경로 재현. 실제 에이전트의 사용 빈도·소음 감소·처리 시간 개선은 측정하지 않았다.

## 1. 검토 결론

새 작업 상태 기계나 필수 맡음 확인을 도입하기 전에, 현재 실패 집계와 중단 의미를 바로잡는 것이 첫 단계다.
격리 재현에서 **성공 이력 뒤의 실패가 0회로 계산되는 결함**과 **명시적인 사용자 중단이 실패로 집계되는 동작**을 확인했다.
사용자는 후자를 실패 횟수에서 제외하기로 정했다.

두 번째 후보는 기존 질문 상태 조회에서 명시적인 상대 세션 종료를 설명하는 것이다. `pending`과 늦은 회신 수용은 유지하고,
현재 확인 가능한 종료 사실만 기존 `reason`에 보충하는 형태를 제안한다. 자동 재배정·자동 재시도·새 종료 상태는 도입하지 않는다.
이 표시가 실제 사용자의 혼란을 얼마나 줄이는지는 아직 측정하지 않았다.

나머지 후보는 기존 수단을 먼저 대조하거나 추가 실패 표본이 필요한 것으로 분류했다. 총 34개 중 추가 코드 후보는 2개,
기존 수단 우선 검토는 22개, 추가 근거가 필요한 후보는 10개다. 이 분류는 검토자의 제안이며 후보 삭제나 장기 범위 축소에 대한
사용자 승인으로 취급하지 않는다.

효익의 적용 범위도 제한적이다. 실패 집계와 아래 once 동작은 `xsm spawn`의 기존 pane/background 워커 경로다.
`attempts.check`·`start`·`finish` 호출은 그 경로에 모여 있고 owned 정지는 별도 journal 제거 분기로 빠진다.
Orca가 띄운 일반 세션의 수명이나 모든 런타임의 작업 실패를 이 수정이 관리하지 않는다. Orca 안에서는 기본적으로 워커 생성을
Orca에 맡기는 기존 경계도 유지한다. 따라서 P1·P2는 확인한 작은 결함의 수정이며, XSM 전체의 작업 관리 계층을 새로 만드는 명분이 아니다.

## 2. 사용자 관점의 요구

1. 작업을 중단하라는 지시 때문에 같은 작업을 다시 시도할 권리가 소진되지 않아야 한다.
2. 실제 실패가 반복되면 기존에 정한 실패 상한이 성공 이력 유무와 관계없이 정확하게 작동해야 한다.
3. 보낸 질문이 아직 미응답일 때, 상대 세션의 명시적인 종료와 과제 실패를 구분해 알 수 있어야 한다.
4. 팀장·수평 워커·팀장 조율 팀의 역할과 보고 경로를 유지하면서, 에이전트가 기억해야 하는 추가 명령과 상태를 늘리지 않아야 한다.

## 3. 확인한 근거

### 3.1 격리 실행

임시 `HOME`·`XSM_HOME`을 사용했다. 워커 프로세스 종료·전송·실제 모델 호출은 실행하지 않았다.
정지와 회신 콜백은 외부 실행을 대역으로 바꾸고 실제 시도 기록 경로에 연결했다.
질문 조회는 시험용 세션 등록과 종료 기록을 사용했다. 이것은 코드 경로의 재현이며 실제 하네스 UI 시험이 아니다.
정지·once 재현은 XSM 기존 워커 경로에 한정되며, Orca 워커나 owned 실행의 동작을 관측한 결과가 아니다.

| 입력·상황 | 구현 전 결과 | 판단 |
|---|---|---|
| `failed` 세 번, 이전 성공 없음 | 실패 3회, 상한 3에서 거절 | 기존 의도와 일치 |
| `succeeded` 한 번 뒤 `failed` 세 번 | 실패 **0회**, 상한 3에서 허용 | 기존 집계 설명과 불일치. 수정 후보 |
| `failed` 두 번 뒤 outcome 없는 종료 | 실패 2회 | 미확정 결과는 실패를 늘리지도 초기화하지도 않음 |
| 무응답 워커에 사용자 요청 정지를 세 번 적용 | 세 기록 모두 `failed`, 상한 3에서 거절 | 사용자 결정에 따라 실패 집계에서 제외할 대상 |
| 질문 대상에 명시적 종료를 기록 | 질문은 여전히 `pending`, `final=false` | 종료가 실패라는 뜻은 아니므로 상태 유지 자체는 타당. 설명 가시성은 별도 후보 |
| 같은 결정 키로 동일한 질문을 두 번 등록 | 같은 ID, 저장 기록 1개, 조회 상태 `pending` | 기존 대기·중복 관리 재사용 근거 |
| `--once` 워커의 상관된 회신에 최종 outcome 없음 | 시도 기록을 outcome 없이 닫고 정지를 예약 | 중간 회신을 새 대기 표현으로 쓰려면 수명 계약까지 재검토해야 함 |

원시 관측은 로컬 `/private/tmp/xsm-adoption-review-probes.json`에 남겼다. 임시 재현 코드는 제품에 추가하지 않았다.
파일이 없어져도 판단 범위와 관측값을 확인할 수 있도록 위 표에 결과를 보존했다.

### 3.2 기존 테스트와 읽은 코드

```sh
python3 -B -m unittest tests.test_workers.AttemptsTest
```

결과: `Ran 8 tests in 0.346s`, `OK`, 종료 코드 0. 이 테스트는 성공 직후 초기화와 성공 없는 반복 실패는 확인하지만,
성공 뒤 실패가 다시 누적되는 시나리오는 포함하지 않는다. 기존 검사 통과가 위 집계 결함의 부재를 뜻하지 않는다.

- [attempts.py](../../../../xsm/attempts.py)의 `failures`: 역순 순회 중 과거 성공을 만나면 이미 센 실패 대신 0을 반환한다.
- [workers.py](../../../../xsm/workers.py)의 `stop`: 무응답 시도를 `failed`로 닫는다. `on_reply`: 최종 outcome 없는 회신도 `--once` 정지를 예약한다.
- 같은 파일의 `run_owned`·`_reply_owned`와 [owned_requests.py](../../../../xsm/owned_requests.py): 실제 결과 저장, 발행 소유권, 회신, 복구 이력이 이미 있다.
- [questions.py](../../../../xsm/questions.py)의 `_result`·`status`: 결과와 전달 근거를 구성하지만 대상 세션 종료를 조회하지 않는다.
- [결과 스키마](../../../protocol/question-result.schema.json): 단일·그룹 자식 결과 모두 `reason`을 허용하고 미정의 속성은 거절한다. 새로운 표시를 위해 임의 필드를 추가하면 스키마 작업도 생긴다.
- [decisions.py](../../../../xsm/decisions.py)의 `public_status`: 현재 호출자 소유의 결정 목록과 개별 대기·응답·적용 상태를 이미 조회한다.
- [조직 스킬](../../../../skills/xsm/references/organization.md), [팀 스킬](../../../../skills/xsm/references/teams.md), [워커 스킬](../../../../skills/xsm/references/workers.md): 역할·보고·직접 협업·보드·인수인계 안내가 이미 있다.

|---|---|---|---|
| 작업 소유·맡음·반환·대기·수락을 새 공통 상태 기계로 관리 | 자동 조율에 필요한 명시적 상태 | 프로토콜·저장·스키마·CLI·하네스별 관측·인수인계 전반 변경. 수평 의회형까지 특정 업무 절차에 묶을 위험 | 실제 소유권 누락·회신 누락 표본을 더 확인할 후보로 보존 |
| 기존 시도 기록·결정 저널·질문 조회를 좁게 수정 | 확인한 집계 결함 수정, 중단 정책 반영, 상태 설명 개선 | 일부 정지 호출 구분과 상태 조회 테스트. 새 필수 에이전트 호출은 없음 | 이번 단계의 권장 구조 |

전역 사람 대기 추적·턴 종료 차단 훅을 첫 단계의 전제로 삼지 않는다. 이 장치들의 후보 항목은 아래 표에 남긴다.

## 5. 34개 후보별 효익과 비용

분류는 다음 뜻이다. **코드 후보**는 현재 근거로 작은 수정을 제안하는 항목, **기존 수단**은 현재 기능·스킬을 먼저 대조할 항목,
**추가 근거**는 별도 구조를 설계하기 전에 구체적인 실패 사례나 비용을 확인할 항목이다. 기존 수단이라는 분류는 해당 제안이
전부 구현됐거나 효과가 입증됐다는 뜻이 아니다.

## 6. 단계별 구현 제안

### P1. 실패 횟수 계산 수정

- 효익 범위: XSM 기존 pane/background 워커의 task 시도 상한. 일반 피어·Orca 워커·owned journal에 같은 카운터를 확대 적용하지 않는다.
- 대상: `xsm/attempts.py`, `tests/test_workers.py`의 `AttemptsTest`.
- 변경 형태: 역순 순회에서 최근 성공을 만나면 그 뒤에서 이미 센 실패 수를 반환한다. 새 상태·필드·CLI는 추가하지 않는다.
- 완료 기준 R1: 성공 없는 실패 3회와 성공 뒤 실패 3회 모두 상한 3에서 거절한다. 성공 직후는 0회다.
- 완료 기준 R2: outcome 없는 기록은 실패 수를 늘리거나 초기화하지 않고, 다른 폴더·task 계보는 서로 영향을 주지 않는다.
- 반증: 현재 코드에서 `succeeded → failed → failed → failed`를 검증하는 새 회귀 검사는 실패해야 한다.

### P2. 명시적인 사용자 중단을 실패 집계에서 제외

- 사용자 결정: **사용자 중단은 실패에서 제외**. 기존 명시적 `failed` 회신은 계속 집계한다.
- 적용 범위: P1과 같은 기존 워커 경로. 다른 도구가 만든 워커의 정지 의도를 추론하거나 관리 권한을 추가하지 않는다.
- 대상: `xsm/cli.py`의 `cmd_stop`, `xsm/workers.py`의 `stop`과 호출 지점, `xsm/attempts.py`의 기존 기록, 관련 워커 테스트·안내.
- 변경 형태: 사용자 정지 진입점에서 내부 정지 사유를 분명하게 전달한다. 기존 outcome 없는 종료와 `why` 기록을 활용하는
  형태를 우선 검토하며, 사용자에게 새 정지 인자나 wire outcome을 요구하지 않는다.
- 일반 정지 외에 등록 실패 후 정지 2곳과 orphan 정리 경로가 있다. `--once`의 내부 정지는 회신 처리 뒤에 호출된다.
  모든 정지를 사용자 중단으로 바꾸지 않는다. 자동 정지의 기존 집계는 이 단계에서 일괄 변경하지 않는다.
- 완료 기준 R3: 명시적인 사용자 중단을 3번 반복해도 실패 3회로 거절하지 않는다. 이미 있던 실패 2회는 그대로 남는다.
- 완료 기준 R4: `failed` 회신 세 번은 계속 거절하며, 성공·실패 회신 뒤 정지가 기존 결과를 덮어쓰지 않는다.
- 완료 기준 R5: owned 서비스 제거와 once 정리의 수명 동작을 바꾸지 않는다. 사용자 중단이 완료나 성공으로 표시되지 않는다.
- 반증: 현재 정지 경로에서는 R3이 실패한다. 수정 후 해당 경로와 기존 자동 정지·once 회귀를 함께 확인한다.

### P3. 명시적으로 종료된 미응답 상대를 조회 결과에서 설명

- 대상: `xsm/questions.py` 또는 공통 질문 서비스의 읽기 경로, `tests/test_questions.py`, 질문 결과 안내.
- 호출자 경험: 기존 `xsm_question_status`·질문 조회를 그대로 사용한다. 추가 호출이나 새 플래그 없이, `pending`의 `reason`에
  "대상 세션이 명시적으로 종료됐으며 최종 회신은 아직 없다"는 관측 사실을 보충한다. 문구는 실패 판정이 아니다.
- 형태: 저장된 정확한 로컬 runtime·home·conversation과 현재 등록 기록을 대조한다. 이름으로 후임을 추측하거나 전체 directory·
  대화 기록을 스캔하지 않는다. 현재 기록이 없거나 stale·unknown이거나 원격이면 종료를 단정하지 않는다.
- 완료 기준 R6: 정확한 대상의 명시 종료에서 설명이 나오되 `status=pending`, `final=false`, 기존 recover_at과 원문 기록은 유지한다.
- 완료 기준 R7: 같은 대화가 재개되면 종료 설명을 제거하고, 늦은 최종 회신은 기존 방식으로 정상 수용한다.
- 완료 기준 R8: live·stale·missing·원격을 종료로 표시하지 않고, 다른 이름·다른 홈의 세션도 대상으로 대체하지 않는다.
- 완료 기준 R9: CLI·MCP·그룹 자식 결과에서 기존 reason 필드와 스키마를 유지한다. 조회가 추가 대기·깨우기·자동 재전송을 만들지 않는다.
- 반증: 현재 조회에서는 명시 종료 전후 결과가 같아 R6의 설명 조건을 충족하지 않는다.
- 효과 확인: 이 단계가 자동 복구나 실제 사용자 혼란 감소를 보장한다고 쓰지 않는다. 현재 문제는 정보 가시성이다.

각 단계는 독립적인 로컬 커밋으로 검토 가능하게 만든다. P1·P2를 먼저 수행하고 P3의 표시를 이어 검토하는 순서를 권한다.
사용자는 2026-11-04 "계획서대로 진행하자"고 지시했다. 실제 런타임 재검증 기본 0회 조건을 유지해 실행한다.

## 7. 검증의 크기와 경계

사용자 결정에 따라 **이번 P1~P3의 실제 런타임 재검증 예산은 기본 0회**로 둔다. 특히 OpenCode·Pi·OpenClaw·Hermes는
다시 실행·설치하거나 구독 모델·게이트웨이·메신저를 연결하지 않는다. Claude·Codex의 실제 세션 재시험도 기본 완료 조건에
넣지 않는다. 사용자에게 준비·질문 응답·메신저 왕복을 다시 요구하지 않는다.

확인한 결함과 바뀌는 동작의 격리 회귀 검사로 완료를 판단한다. 실제 저장·상태 계산 경로는 실행하되 프로세스 실행·종료와
외부 전달 경계는 fixture나 대역으로 바꾼다. 모델 응답을 얻거나 네이티브 UI를 재현하는 것이 이 수정의 전제는 아니다.

| 단계 | 기본 완료 근거 | 실제 런타임 재검증 |
|---|---|---|
| P1 | 임시 XSM_HOME의 시도 기록, 성공 뒤 실패 누적·초기화·계보 분리 회귀 | 0회. 런타임과 무관한 집계 함수 변경 |
| P2 | CLI 정지 진입점 → stop → 시도 기록을 연결한 격리 검사. 실제 프로세스 종료는 대역 처리 | 0회. 기존 워커의 정지 분류를 확인하며 네 런타임의 생성·종료를 실행하지 않음 |

OpenCode·Pi·OpenClaw·Hermes의 기존 순수 코드 계약·fixture 검사가 직접 영향을 받으면 해당 검사만 실행한다. 어댑터의
코드·설치·native callback·깨우기·취소 경로를 이번 변경 때문에 수정하지 않는 한, 그 실제 실행을 다시 인증하는 매트릭스는
추가하지 않는다. 관련 검사가 통과한 뒤 근거 없이 전체 회귀나 반복 실행으로 넓히지 않는다.

격리 검사로 판단할 수 없는 네이티브 경계의 문제가 드러나면, 먼저 미확인 사실과 영향 범위를 기록한다. 실제 실행이 필요한
이유·대상 런타임·최소 시나리오·예상 비용을 별도 제안하며, 자동으로 네 런타임 전체 재검증을 시작하지 않는다. 추가 실행은
사용자가 정한 범위와 비용 안에서만 수행한다. 이 조건의 재검토 담당은 XSM 유지보수자다.

결과 보고에는 변경한 공통 코드의 격리 검사 통과와 실제 런타임 재검증 미실시를 구분한다. 새 런타임 검증을 했다고
표현하지 않으며, 기존 지원 범위에 대한 과거 기록을 이번 변경의 새 실행 결과로 바꾸어 쓰지 않는다.

첫 단계에서 다음 조건을 지킨다.

- 기존 `succeeded`·`failed`의 wire 의미와 필수 인자 수를 유지한다.
- 새 필수 ACK·맡음·수락 호출, LLM 호출, 전역 백그라운드 감시를 추가하지 않는다.
- 모델이 말한 blocked를 임의로 최종 실패나 성공으로 추론하지 않는다.
- `--once` 중간 회신 정지는 이번에 관측한 기존 동작이다. 중간 회신으로 대기를 표현하는 기능을 도입할 경우에는
  질문 final과 워커 수명까지 함께 설계한다. 이번 계획에서는 그 정책을 몰래 바꾸지 않는다.
- 실제 사용자 프로필·설정·시험 계정을 바꾸지 않는다. 외부 발송·게시·릴리즈는 이 계획의 실행 범위에 포함시키지 않는다.
