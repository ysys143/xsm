# 경로 일관성 후속 수정 계획

2026-11-04. 사용자는 검토에서 발견한 결함의 수정 계획 작성과 실행, 가벼운 런타임 검증을 지시했다.
기준은 `46523ee`다. 이 문서는 앞선 [완료 기록](results.md)의 부족했던 경계 검사를 보완한다.

## 확인된 문제와 수정 순서

1. **즉시·지연 시작의 차이:** 일반 `spawn --task`는 시도 기록 없이 전송하고, 신뢰 승인 후의 `worker-finish`만 시도를 연다.
   과제 ID 저장·시도 시작·전송을 공통 함수로 모아 두 진입점에서 사용한다. 전송 경계만 대역으로 바꾸고 CLI와 지연 시작 경로를 검사한다.
2. **미시작 워커의 잘못된 종료 연결:** 같은 계보의 B가 신뢰 승인을 기다릴 때 정지하면 `task_id=None`으로 A의 열린 시도를 닫는다.
   과제 ID가 실제 있는 워커만 그 ID의 시도를 닫고, 명시한 ID와 다른 기록은 선택하지 않게 한다. A/B를 함께 둔 정지·후속 실패를 검사한다.
3. **이력 한도로 실패 집계 소실:** 실패 2회 뒤 중단 기록이 쌓이면 최근 20건 밖의 실패가 사라진다.
   최근 이력에서 제거하는 종료 기록의 실패 수를 작은 누적값으로 보존하고, 마지막 성공을 경계로 계산한다. 기존 기록은 누적값 0으로 읽는다.
   아직 열린 시도는 버리지 않고, 열린 시도가 앞에 있으면 그 뒤의 순서도 보존한다. 닫히면 다시 최근 20건으로 정리한다.
   같은 계보의 갱신은 파일 잠금으로 직렬화해 누적값과 기록의 경합을 막는다. 새 작업 상태 기계나 백그라운드 프로세스는 추가하지 않는다.

최근 이력과 별개로 유지한 집계도 성공·명시 초기화·기존 보존 기간에 따른 계보 정리 때 해제된다. 이미 과거에 잘려 나간
기록을 복구했다고 주장하지 않는다. 이번 보정은 이후의 이력 정리로 알려진 실패 근거를 다시 잃지 않도록 한다.

## 회귀 검사와 완료 기준

| C2 | A 실행 중 B가 아직 과제를 받지 않은 상태에서 B를 정지해도 A의 시도는 열린 채 유지된다. 이후 A의 failed가 정확히 1회 집계된다. |

독립 검토를 요청했던 동일 서브에이전트의 후속 검토를 가능한 범위에서 활용한다. 새 에이전트를 추가로 생성하지 않는다.

## 문서와 스킬

- `PROTOCOL.md`의 사용자 정지·자동 정지·실패 보존 설명을 코드와 맞춘다.
- 운영 README의 오래된 터미널 전용 승인 설명을 현재 사용자 답 검증 경로와 맞춘다.
- 한영 README에 사용자 중단·미응답 상대의 명시 종료 설명을 짧게 추가하고, Unreleased에 변경을 기록한다.
- 워커 스킬에서 once는 최종 outcome 없는 첫 상관 reply에도 정지한다는 경계를 명시한다. 진행·대기를 reply로 보내도록 새로 유도하지 않는다.
- 두 레퍼런스는 과거 기준 비교를 보존하면서 후속 반영 결과를 연결한다. 앞선 완료 기록은 독립 검토에서 드러난 한계를 함께 남긴다.

## 가벼운 런타임 확인

사용자의 추가 지시에 따라 실제 런타임 확인을 최소 범위로 수행한다. OpenCode·Pi·OpenClaw·Hermes의 사용 가능한 설치·캐시를
확인하고, 모델 호출 없는 로딩·진입 스모크를 각각 한 번 목표로 한다. XSM 공통 프로토콜의 실제 subprocess 확인과
각 네이티브 런타임 로딩은 구분해서 보고한다. 없는 런타임을 새로 설치하거나 사용자 프로필·토큰·권한을 변경하지 않는다.
모델 호출·메신저·게이트웨이 계정 왕복·100회 반복·지연 측정은 수행하지 않는다. 확인하지 못한 런타임은 미실행 이유를 기록한다.
