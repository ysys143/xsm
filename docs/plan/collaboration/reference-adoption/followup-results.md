# 경로 일관성 후속 수정 결과

2026-11-04. [후속 계획](followup.md)의 C1~C6를 구현·검증했다. 앞선 [초기 완료 기록](results.md)은 검사 범위가 제한됐고,
독립 검토에서 드러난 세 경계 결함을 놓쳤다. 이 문서는 그 보정 결과다. 핵심 코드 커밋은 `0b9f0f2`다.

## 코드와 경로

- 즉시 시작과 신뢰 승인 후 지연 시작은 모두 `workers.send_task`에서 과제 ID·시도를 기록한 뒤 전송한다.
  실제 CLI 경로로 실패 회신을 반복하면 시도가 집계되고, 다음 생성은 기존 상한 검사에서 거절된다.
- `stop`은 실제 과제 ID가 있는 워커만 해당 시도를 닫는다. 명시한 ID는 익명·다른 시도의 대체 선택에 쓰지 않는다.
  같은 계보의 미시작 B를 정지해도 실행 중인 A의 기록과 후속 실패를 보존한다.
- 최근 이력에서 잘라내는 종료 구간의 실패 수는 `earlier_failures`로 보존한다. 열린 시도 앞에서는 정리를 멈춰 순서를 유지하고,
  닫힌 뒤 다시 최근 20건으로 정리한다. 성공·명시 초기화·기존 계보 보존 기간의 의미는 유지한다.
  갱신·삭제는 같은 계보의 파일 잠금을 사용하며, prune은 잠금 안에서 현재 기록을 다시 확인한다. dry-run은 새 잠금을 만들지 않는다.

새 상태 기계·wire outcome·필수 CLI 인자는 추가하지 않았다. 이미 과거에 잘린 실패 근거를 복구했다고 주장하지 않는다.
모든 프로세스 간 경합 조합을 검증한 것도 아니다.

## 검증

새 `tests/test_attempt_path_consistency.py`의 최초 7개 중 6개가 수정 전 실패했다. 즉시 전송 전 기록 누락, 잘못된 과제 종료,
긴 중단 이력의 실패 소실, 열린 시도 소실, 동시 기록 누락을 각각 드러냈다. dry-run 보존 검사를 추가해 최종 새 검사는 8개다.

| 기준 | 결과 |
|---|---|
| C1 | CLI의 즉시 전송과 실제 `worker-finish` 흐름 모두 전송 시점에 시도 기록이 존재한다. 실패 3회 뒤 실제 생성의 admission은 거절된다. |
| C2 | 같은 계보의 미시작 워커 정지는 실행 중인 다른 시도를 닫지 않으며, 그 워커의 failed는 1회로 집계된다. |
| C3 | 명시한 과제 ID가 익명 기록을 닫지 않는다. 기존 회신·사용자 정지·자동 정지의 결과 보존 검사도 통과했다. |
| C4 | 실패 2회 뒤 중단 25회에도 실패는 2회다. 다음 failed에서 상한이 작동하고, 성공 뒤 중단을 반복해도 0회다. |
| C5 | 열린 오래된 시도가 후속 기록 25개 뒤에도 끝맺을 수 있고, 닫힌 뒤 이력을 정리한다. 동시 12개 기록과 기존 형식·clear·prune·dry-run 검사 통과. |
| C6 | 질문의 종료 설명·재개·늦은 회신, CLI/MCP·그룹 조회, owned 제거와 once 수명을 포함한 회귀 검사 통과. |

```sh
python3 -B -m unittest tests.test_workers tests.test_attempt_path_consistency \
  tests.test_owned_workers tests.test_questions tests.test_question_groups \
  tests.test_question_service tests.test_xsm.SkillLayoutTest
```

결과: `Ran 155 tests in 16.031s`, `OK`, 종료 코드 0.
워커 관련 98개를 먼저 실행했을 때는 오래된 MCP 복구 기대값 1개가 실패했다. 현재 제품 코드는 미응답 폼 뒤 동일 MCP 호출의
네이티브 답 복구를 안내하는데, 그 검사는 CLI로 전환하라고 기대하고 있었다. 승인 코드를 변경하거나 검사를 삭제하지 않고,
정확한 질문·동일 MCP 재시도·셸 전환 금지와 대기 기록 보존을 확인하도록 갱신했다.

같은 독립 서브에이전트가 핵심 코드 `0b9f0f2`의 세 항목을 집중 재검토하고 새 검사 8개를 실행했다.
`Ran 8 tests in 0.208s`, `OK`였으며 구체적인 blocker를 발견하지 못했다고 보고했다. 추가 에이전트는 생성하지 않았다.

## 가벼운 런타임 스모크

사용자의 추가 지시에 따라 기존 임시 캐시의 실제 런타임·플러그인 로딩 경로를 사용했다. 모두 별도 임시 HOME·XSM_HOME을
사용했고 모델 호출·사용자 UI·메신저·게이트웨이 계정 왕복은 수행하지 않았다. 합성 입력과 호출자 fixture를 사용한 스모크이며
실제 모델이 일하는 전체 작업이나 지연 수용 기준을 재인증한 결과가 아니다.

| 대상 | 실제 확인 범위 | 결과 |
|---|---|---|
| Pi 1.4.0 | 캐시된 실제 RPC 런타임과 XSM 확장, 네이티브 메시지 수신 1회 및 합성 UI 응답 | passed, 프로세스 exit 0 |
| OpenCode 1.19.5 | 캐시된 실제 서버·플러그인, 합성 입력으로 수신·도구 ACK의 최소 1회 | passed, 프로세스 exit 0 |
| OpenClaw 2026.10.9 | 실제 플러그인 loader·도구 실행·DM pull/ACK·세션 종료/재개·unload | passed, 프로세스 exit 0, modelCalls=0 |
| Hermes 0.22.5 | 실제 플러그인 registry·hook/tool 경로의 7개 model-free 검사 | passed, 프로세스 exit 0 |

Pi 준비 단계 실패 2건도 보존했다. 첫 실행은 전역 Pi가 0.58.1이라 고정 probe의 1.4.0 조건에서 중단됐고,
두 번째는 캐시의 패키지 namespace를 잘못 지정해 진입 파일을 찾지 못했다. 실제 캐시의 `.bin/pi`를 확인해 최종 1.4.0
스모크를 실행했다. 전역 Pi를 바꾸거나 새 의존성을 설치하지 않았다. 100회 반복이나 지연 gate는 실행하지 않았다.
