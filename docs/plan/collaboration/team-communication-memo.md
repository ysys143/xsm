# 팀 소통 모델 설계 메모: DM, 팀, 보드

- 작성: 2026-10-30
- 상태: 설계 결정 메모. 아래 결정은 사용자가 이 대화에서 내린 것이다. 구현은 착수하지 않았다.
- 결정 기록: [ADR-0025](../../adr/0025-team-and-multi-recipient-dm.md)(다중 수신 DM, 팀, 인수인계), [ADR-0026](../../adr/0026-team-board-on-xsm-doc.md)(doc 보드, 결재 기록, channel 정리). 이 메모는 그 배경과 결정 번호(D1–D33)를 담는다.
- 관련: [채널 설계 토론](channel-design-discussion.md), [S11](../../spikes/S11-results.md), [S11b](../../spikes/S11b-results.md), [S12](../../spikes/S12-results.md), [S10](../../spikes/S10-results.md), [DM·채널 레퍼런스](../../references/dm-and-channels.md)

## 출발점

여러 에이전트가 함께 일할 때, 1:1 메시지와 별도로 합의·분담·진행을 모두가 볼 수 있는 장소가 필요한지 검토했다. DM으로 막힌 사례는 아직 없다. 다른 프레임워크가 공유보드형 소통을 지원하고 그 모델에도 합리성이 있다고 보아 검토했다.

기존 사용 기록: 두 머신의 메시지 원장 약 10,700건 동안 `xsm channel` 게시는 5건(맥북)·0건(맥미니)이었고, 에이전트끼리의 소통에 쓰인 적은 없다. `pg_cuvs` 팀은 조율자 한 명이 쓰는 상태 파일(`PHASE.md`)을 git으로 공유하고 갱신을 DM으로 알렸다. S10 공동 편집 실험에서는 "채널에 `taking`을 남겨라"는 한 줄 규칙만으로 1:1 메시지가 0건이 되고 소통이 채널로 옮겨 갔다(그 런들이 S10이 무효로 선언한 일회성 실행 범위인지는 확인하지 않았다). 이 수치들은 동기 설명이며 필요성의 결론 근거로 쓰지 않는다.

## 모델

소통 경로는 DM과 보드 둘이다. 팀은 그 둘을 가리키는 이름이다.

| 개념 | 정체 | 역할 |
|---|---|---|
| DM | 받는 쪽을 지정한 메시지(message) | 세션 또는 팀 이름을 지정한다. 누군가를 움직이고 답을 받는 경로 |
| 팀(team) | 세션들의 구성원 목록 | 함께 일하는 모임. 한 세션이 여러 팀에 속할 수 있다. 팀장과 보드를 가진다 |
| 보드 | 팀의 현재 상태 | 지금 유효한 결정·분담·진행. `xsm doc`이 소유하고 항목별로 렌더한다 |

팀과 project:

| | project (`link`, `join`, `reach`) | 팀 |
|---|---|---|
| 묶는 것 | 폴더. 그 폴더의 모든 세션이 자동으로 들어오며 앞으로 열릴 세션도 포함 | 이름을 지정한 세션 |
| 저장소 경계 | 넘을 수 있다 | 넘을 수 있다 |
| 뜻 | 누가 말할 수 있나(통신 경계) | 누가 지금 함께 일하나 |
| 주소 | 아님 | 팀 이름으로 DM |
| 딸린 것 | 없음 | 팀장, 보드, 결재 기록 |

같은 project 안에서 팀은 권한을 새로 열지 않는다. 범위 밖 세션을 팀에 넣는 것은 지금의 "사용자가 골라 connect"와 같은 일이며, connect는 구성원 둘인 팀이 된다.

## 결정

### 원칙

| # | 내용 |
|---|---|
| D1 | 용어 "message"를 유지하고 문서에서 message = DM(direct message)임을 강조한다. direct는 받는 쪽을 지정한다는 뜻이지 일대일이 아니다. 명령·도구·와이어 이름은 바꾸지 않는다. README·README_ko·`docs/xsm/README.md`에 반영했다(미커밋) |
| D2 | 공유 기록은 주로 에이전트용이며 에이전트 사이의 합의·작업 분담·진행 공유를 담는다 |
| D3 | 컨텍스트 낭비는 반드시 막는다 |
| D4 | 공유 기록을 한 에이전트만 쓰게 하지 않는다 |
| D8 | 소통이 분산되는 것은 위험하다. 소통 경로는 DM과 보드 둘로 둔다 |
| D9 | `xsm doc`·`xsm channel`·마크다운 보드 셋을 모두 가져가지 않는다 |

### 팀장과 결재

| # | 내용 |
|---|---|
| D5 | 팀장은 사용자와 에이전트 팀의 소통으로 정하고 사용자가 승인한다. 절대적이지 않으며 팀장이 아닌 세션에도 직접 지시할 수 있다 |
| D6 | 결재는 사용자와 대면하는 팀장을 거친다. 결재 범주를 미리 정하지 않는다. 비용·외부 공개·범위 변경 같은 범주를 승인 대상으로 프롬프트에서 안내하는 정도는 한다 |
| D7 | 회의록을 따로 두지 않는다. 합의 결과는 보드 항목으로, 결재는 결재 기록으로 남고 논의 과정은 doc 노드 이력에 남는다 |
| D25 | 결재 기록은 팀 보드와 함께 둔다. `xsm_decide`가 결재를 보드 옆 보호된 기록에 남기고 보드 항목은 그 기록 ID를 가리킨다. 보드와 함께 머신 간에 맞춰 원격 팀원도 확인할 수 있게 한다 |

### 다중 수신 DM

| # | 내용 |
|---|---|
| D11 | `xsm send`에 다중 수신인을 지정할 수 있게 한다 |
| D14 | 수신자 일부가 통신 범위 밖이면 허용된 수신자에게만 보내고, 빠진 수신자를 결과에 적는다 |
| D15 | 받는 세션에게 다른 수신자 목록을 보여 준다 |
| D16 | `send`와 `ask` 모두 다중 수신을 지원한다. `ask`는 수신자마다 답을 따로 모은다 |
| D17 | 종료 코드는 가장 나쁜 수신자 결과를 따른다(하나라도 error면 4, 하나라도 미확인이면 3, 모두 전달이면 0). 수신자별 결과는 따로 출력한다 |

구조상 필요한 것(결정에서 따라옴): 메시지 하나에 ID 하나, 수신자별 전달 ID를 따로 둔다(P2P 전송은 요청 ID 하나를 수신자 하나에 묶는다). 트래픽 집계는 수신자 N명에게 간 메시지 하나를 1건으로 센다.

### 팀

| # | 내용 |
|---|---|
| D10 | 기존 `xsm channel`의 지위는 검토 중이며 제거할 수 있다 |
| D12 | channel 개념의 장점은 가볍게 여러 곳에 속할 수 있다는 것이고, 그 소속의 뜻은 "함께하는 팀"이다 |
| D13 | 팀은 project와 구분한다 |
| D18 | 이름은 team이다 |
| D19 | 팀 가입은 구성원끼리의 DM을 허용한다. 이는 새 권한이며 팀 밖 세션에는 아무것도 열지 않는다 |
| D20 | 가입 승인: 같은 project 안의 세션은 팀장이 넣고 뺄 수 있고, 범위 밖 세션은 사용자가 승인한다 |
| D21 | `connect`(고른 대화 한 쌍)를 구성원 둘인 팀으로 합친다. 사용자 선택과 핸드셰이크는 유지한다. ADR-0024의 의미가 바뀌므로 대체 결정 기록이 필요하다 |
| D22 | 다른 머신(P2P)의 세션도 처음부터 팀 구성원이 될 수 있다 |
| D23 | 팀 DM은 즉시 받고, 보드 변경은 다음 턴에 팀별 한 줄 요약으로 묶어 받는다. 세션별로 팀 알림을 끌 수 있다 |
| D24 | `reach`는 그대로 project 쪽에 둔다 |

### 구성원과 인수인계

| # | 내용 |
|---|---|
| D26 | 팀 구성원은 이름 단위다. 같은 이름으로 다시 열면 자리를 이어받는다 |
| D27 | 사용자가 어느 세션에서 "OO한테 인수인계해"라고 하면, 그 세션의 xsm 대화 위치를 OO가 물려받는다. 넘어가는 것: 팀 소속과 역할, 보드의 담당 항목, 안 읽은 DM과 답 대기 중인 요청, 작업 맥락 요약. 팀장 자리를 받은 세션은 지시를 이어서 하고, 워커들의 보고도 그 세션으로 간다. 상세 핸드오프 작성과 이어받는 행동은 스킬로 안내한다 |

### 보드

| # | 내용 |
|---|---|
| D28 | 보드는 `xsm doc`이 소유하고 항목별로 렌더한다(S11·S11b 결과로 결정) |
| D29 | 보드는 xsm이 정한 공통 경로(예: `~/.xsm/teams/<팀>/`)에 둔다. 워크트리마다 갈라지지 않는다 |
| D30 | "남을 움직이려면 DM, 모두가 알아야 할 사실이면 보드. 둘 다에 쓰지 않는다"를 스킬에 넣는다. 팀 전체에 해당하는 결정을 DM으로 받으면 보드에 옮기고 DM에는 위치만 남긴다 |
| D31 | 기존 지시로 쓰던 상태 파일(`PHASE.md` 류)은 따로 두되 적극적으로 동기화한다. 그 파일에 "에이전트 간 작업용 정본은 xsm doc 보드에 있다"고 알린다. 상태 파일은 사람이 진행 단계를 확인하는 용도다 |
| D32 | 싼 모델 서브에이전트의 걸러 읽기는 어려운 표본으로 다시 실험한 뒤 스킬 권장 여부를 정한다 |
| D33 | 기존 `xsm channel`은 팀·보드·결재 기록이 준비되고 `xsm_decide`가 옮겨진 뒤 제거한다. ADR-0005를 대체하는 결정을 함께 쓰고, 그전까지 문서에 "검토 중, 제거 예정"으로 표시한다 |

## 구현할 때 풀어야 할 것

결정에서 따라오는 설계 작업이며, 정책 질문은 아니다.

- **doc 보드**(D28): 항목 개념(노드가 속한 항목), 항목별 최신 노드 렌더, 같은 항목의 동시 노드는 "충돌 중"으로 둘 다 표시. `report` 태그가 보드 전체를 덮지 않게 렌더 규칙 수정. 쓰기 마찰 줄이기(태그 기본값, 빈 본문·잘못된 태그 오류 안내, 필요한 옵션). 샌드박스 Codex용 MCP 쓰기 도구. 사람의 직접 편집을 렌더 시점에 감지해 노드로 받아들이는 방식.
- **보드 위치와 공유**(D22, D29): 보드가 저장소 밖이므로 이력은 doc 노드가 맡고, 머신 간에는 xsm이 P2P로 노드를 맞춘다. 노드는 불변이고 이름이 겹치지 않아 합치기에 유리하다.
- **결재 기록**(D25): `xsm_decide`의 기록 위치를 팀 보드 옆으로 옮기고, 보드 항목이 가리키는 ID 형식과 원격 확인 방법.
- **팀 권한**(D19–D22): 팀을 pair 허가로 전개하지 않는 새 권한 객체. 수신 게이트가 팀 구성원 여부를 확인하는 경로. connect 통합에 따른 ADR-0024 대체 기록.
- **인수인계**(D27): 넘어가는 항목별 이전 방식(진행 중인 ask의 답이 새 세션으로 가는 경로 포함), 상세 핸드오프 형식, 스킬 안내.
- **다중 수신 DM**(D11, D14–D17): 수신자별 전달 ID, 부분 범위 처리, 수신자 목록 표시, `ask`의 수신자별 답 수집.
- **알림 묶음**(D23): 보드 변경 요약의 형식과 묶는 시간·크기 상한.
- **문서와 스킬**: D30·D31 안내, channel "검토 중, 제거 예정" 표시(D33).

## 이번 논의에서 드러난 결함

- 수신 안내는 `xsm_ack`에 JSON 토큰 객체를 넘기라고 하지만 CLI `xsm ack`는 그 형태를 거부하고 토큰 값만 받는다.
- `codex-worker-2` 세션에서 MCP `xsm_ack`·`xsm_send`가 "현재 세션의 hook record가 없다"는 오류로 실패해 CLI로 대신했다. 목록에서 그 세션의 권한 모드가 `mode?`였다. 원인 미조사.
- `codex exec`는 사용자 설정을 무시하는 옵션으로 실행해도 실제 Codex 홈의 `config.toml`에 임시 경로 trust 블록을 기록한다(S11). xsm 결함이 아니라 시험 실행기의 주의 사항이다.
