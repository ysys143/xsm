# Reason에서 배운 xsm 개선: ADR-0015–0023 구현 계획

- 작성일: 2026-10-24
- 상태: 발견·선택·핸드셰이크 설계와 구현목표 확정(2026-10-28). 원 제안 9개와 보완 ADR-0024의 범위를 유지한다. ADR-0021은 원격 제품 요구사항 확정으로 Accepted가 됐다. 전체 구현 목표는 유지하며 사용자의 일시정지 요청이 적용 중이다. [개정 개발 방침](development-policy.md)을 적용한다. 설계 확정은 제품 완료를 뜻하지 않는다.

- 대상: 구현 에이전트, 검토 에이전트, 정책을 결정할 사용자.
- 전체 범위: 원 ADR 9개와 보완 ADR 1개(총 10개, 현재 ADR-0021·0024 Accepted), 발견 R01–R43, 기존 수용 조건 62개와 추가 8개(총 70개). 단계 순서는 범위 축소나 나머지 항목의 생략을 뜻하지 않는다.
- 원문: [ADR 목록](../../adr/README.md), [역공학 보고서](../../references/reason-network.md), [발견 추적표](../../references/reason-network/README.md).
- 실행 추적: [병렬 실행과 단계별 게이트](execution.md), [수용 조건별 구현·검증 계획](acceptance.md), [기계 판독용 계획](plan.json).

## 확정 기준 (2026-10-28)

[발견·선택·핸드셰이크 설계](collaboration-contract.md)와 [Accepted ADR-0024](../../adr/0024-discover-select-and-handshake.md)가 관련 제안보다 우선한다. 후보는 **사용자가 명시 공개한 세션 ∪ 같은 repository의 폴더·워크트리 세션**이다. 머신·업무로 후보를 보여주고, 사용자가 특정 세션과 협업하라고 지정하면 중복 승인이나 내부 project 설정 없이 그 상대와 핸드셰이크한다. 실제 상대 응답 뒤 협업을 시작하며 다른 후보·폴더 전체에 새 권한을 주지 않는다. 같은 repository의 기존 자동 통신은 유지한다.

이번 확정은 원격 두 물리 머신 여정(P12/P13)을 포함하는 제품 목표다. B03의 로컬 구현만으로 원격 완료를 주장하지 않는다. 2026-10-28 결정만으로 API 철자·대기 수치·전송 backend를 승인한 것은 아니다. 이후 2026-10-29에 확정한 원격 제품 요구사항은 아래와 같다.

## 원격 네트워크 요구사항 확정 (2026-10-29)

[ADR-0021](../../adr/0021-cross-machine-network-and-membership.md)을 채택했다. 자체 P2P를 기본으로 하고 Tailscale은 같은 프로토콜의 선택적 접속 경로로 사용한다. 공개 relay 기본 지원과 자체 relay 설정, 계정 로그인 비필수, 기기키·초대 가입을 확정했다.

Reason처럼 기존 활성 기기 멤버 누구나 초대·기기 추가·제명을 할 수 있다. 최초 기기는 신뢰의 출발점이며 관리자 권한을 독점하지 않는다. 별도 소유자·관리자 계층과 가입 때마다의 관리자 승인은 두지 않는다. 앞서 제안한 관리자 모델은 이 사용자 결정으로 대체한다. 에이전트는 사용자의 의도를 대행하며 멤버십·공개·협업·파일/실행 권한은 구분한다.

D12의 제품 방향은 결정 완료다. 라이브러리·버전·relay 주소·초대 수치·리스너 등 구현 항목은 후속 명세에서 정한다. P12 구현·실측과 G07/G11/G12/G13의 미완은 유지하며 구현 goal은 일시정지 상태다. 이 문서 변경은 실제 네트워크·서비스·권한 변경 승인이 아니다.

## 1. 목표와 사용자 이야기

결과는 기존 Claude Code·Codex 세션에서 매뉴얼이나 내부 프로젝트 식별자를 외우지 않고 협업하는 흐름이다. 에이전트가 상대를 찾고, 이미 허용된 범위를 재사용하고, 필요한 판단만 사람에게 받은 뒤 원 요청을 전달한다. 상대의 실제 답과 자료를 회수하고, 연결이나 하네스가 중단되면 같은 요청에서 복구한다.

| 사용자 | 하고 싶은 일 | 완료 시 보이는 결과 |
|---|---|---|
| 일반 세션의 에이전트 | 담당 업무로 동료를 찾아 짧게 질문 | 후보의 업무·홈·대화가 보이고, 실제 답 또는 미완 사유와 회수 위치를 받음 |
| 사용자의 여러 저장소에서 일하는 에이전트 | 새 저장소 동료와 협업 | 이미 허용된 범위는 즉시 사용. 새 허용이 필요하면 한 요청에 대한 판단부터 연결·원문 전송까지 이어짐 |
| 긴 작업을 맡기는 에이전트 | 비동기 위임 후 자기 작업 계속 | 요청 ID에 수신 증거·부분 회신·최종 보고가 붙고 늦은 답도 회수 |
| 작업 중인 수신 에이전트 | 지금 필요한 개입과 나중에 읽을 참고를 구분 | 가능한 경로로 수신하며, 무기상 미지원과 실제 무기상을 구분 |
| 구현자와 독립 검토자 | 같은 자료로 여러 차례 수정·반례 검토 | 자료 버전이 명시되고 이전 실행자의 문맥이 독립 검토에 섞이지 않음 |
| 사람 | 추가 연결·위험 옵션에 필요한 판단만 제공 | 실제로 본 질문과 답이 보존되고, 같은 유효 범위의 적용 실패 때문에 다시 묻지 않음 |
| 다른 머신에서 일하는 사용자 | 네트워크 구성을 조립하지 않고 원격 협업 | 인증된 머신·공유 범위·실제 전송 경로가 보이고 로컬 동작은 독립적으로 유지 |
| 설치·업데이트 담당 에이전트 | 기존 설정을 보존하며 사용 가능 상태 확인 | 설정 존재와 첫 왕복 성공을 분리하고 자기 소유 항목만 업데이트·제거 |

### 이번 계획에서 실행한 기준 검사

`python3 -m unittest tests.test_mcp_identity tests.test_one_yes tests.test_discovery_latency -q`를 실행해 **91개, 30.676초, OK**를 확인했다. 현재 호출자 식별·연결 승인·탐색 예산의 기존 동작에 대한 검사다. 신규 62개 수용 조건이나 전체 제품 회귀를 통과했다는 뜻이 아니다. 전체 suite 실행은 P00에 포함한다.

저장소에 `pyproject.toml`과 `.github` 디렉터리는 없다. 존재하지 않는 패키지 설치·CI 명령을 전제로 하지 않고, 현재 stdlib/unittest 실행 방식을 사용한다.

### 조사 실패와 미검증의 승계

- 실제 xsm 비교에서 사용자 승인이 연결에 반영되지 않았다. 연결 뒤의 새 저장소 왕복은 미검증이다. P02에서 같은 입력 채널을 재현하고 P13에서 실제 왕복까지 닫는다.
- Reason 일반 Codex 다중 홈 표본의 전달 실패는 해결되지 않았다. xsm의 개선이나 Reason 합성 시험 성공으로 이 과거 표본을 성공 처리하지 않는다.
- Reason 공개 E2E의 마지막 결과는 309 통과·1 실패다. 알림 실행 완료 전에 성공처럼 반환하는 경계는 P07의 반례로 사용한다.
- 같은 호스트의 논리 머신, 가짜 모델·HTTP·OS 명령은 실제 물리 머신·모델·UI 검증을 대신하지 않는다.
- [남은 실환경 항목 20개](../../references/reason-network/residual-unknowns.json)는 plan.json의 `residuals`에서 다시 검사할 실행 단위와 연결한다. 미실행 항목은 미완으로 남긴다.

## 3. 제약과 보존할 동작

## 4. 공통 설계: 기존 경로를 연결하는 계약

아래 명칭은 내부 설계 가칭이다. 새로운 공개 명령이나 영구 포맷이 이미 존재한다는 뜻은 아니다.

### 4.1 호출 문맥과 신원

`CallContext`에 runtime, 정규화 home, native conversation ID, 실행 세대(pid/lstart), cwd, 인증된 머신 origin, 식별 근거와 확실성, 실제 하네스 능력을 담는다. CLI·MCP·훅·원격 ingress가 같은 의미를 전달한다. 표시 이름과 짧은 ref는 이 핸들의 표시·검색 키다.

매 호출의 문맥은 불변 객체로 전달한다. 서버의 `call_thread`, 상속 env, 가장 최근 이웃이 다른 동시 호출의 신원을 덮지 못하게 한다. 확실한 식별이 없을 때 기존 메시징 접근성은 보존하면서 `identity_basis`를 표시한다. 권한 확대와 외부 파일 읽기는 다른 세션의 신원으로 대신하지 않는다. 정확한 호출자 확인을 회복할 경로를 제공한다.

MCP에 동시 대기가 생기면 `probe._deadline`, `consent.supplied/used_via` 같은 프로세스 전역 상태도 점검한다. 첫 구현은 전역 상태를 그대로 둔 채 모든 tool을 thread pool로 돌리는 방식으로 만들지 않는다. 공유 입력 분배기와 짧은 임계 구역 또는 호출별 상태를 분리하고, 쓰기 소유권과 stdout 직렬화를 정한다.

### 4.2 요청·연결 의도·사람 판단

| 레코드 | 필수 의미 | 기존 위치와 이행 |
|---|---|---|
| 요청 | 원 ID, 완전한 발신/대상 핸들, 본문 및 의미 필드의 digest, reply_to, kind, 전달 옵션 | ledger·outbox·envelope를 확장. 원문 보존 여부는 D03에서 확정 |
| 연결 의도 | 요청 ID, 필요한 권한 차이, 대상 세대, 적용할 plan digest, 수명, 의사 출처 | connect.plan_for 결과와 outbox ID를 결속 |
| 사람 판단 | 질문 ID, 실제 표시 내용·잘린 범위, 사용자 답 원문, 채널·출처, 대상·범위·세대, 만료/철회, 적용 결과 | consent의 기존 typed/pending와 MCP·worker·channel 기록을 호환 |

연결 의도는 `received → needs_decision → decision_recorded → applying → active`를 구분한다. `denied`, `dismissed`, `unanswered`, `transport_error`, `expired`, `superseded`는 서로 바꾸지 않는다. 이는 모델이 수동으로 상태를 찍는 API가 아니라 도구가 관측한 전이다.

자유문장 답은 문장 자체를 자동 true로 변환하지 않는다. 확인 가능한 원문과 요청 범위를 해석한 결과를 결속한다. 기존 정책에서 요구하는 사람의 실제 의사와 모델 해석을 구분하고, 같은 명령을 일정 시간 뒤 반복했다는 사실만으로 새 승인을 만들지 않는다. 기존 show/consume 경로는 호환을 위해 유지하고 새 어댑터의 원문 결속과 적용 방식은 D01에서 결정한다.

적용은 `결정의 유효성 재확인 → 현재 권한 readback → 필요한 차이만 적용 → 결과 readback → 원 ID 전송`이다. 파일 여러 개를 하나의 트랜잭션처럼 가정하지 않고, 단계별 intent와 적용 결과를 저장해 재시작 시 조정한다. 권한 적용 뒤 프로세스가 죽어도 같은 범위의 판단을 다시 요구하지 않는다.

### 4.3 전달 증거와 답 대기

legacy `status`는 기존 reader를 위해 보존하고, 새 응답에는 `evidence`, `reply`, `outcome`, `wait_end_reason`, `recover_at`을 별도 축으로 추가한다. 예를 들어 `delivered` 호환 문자열이 있어도 새 증거는 `hook_accepted`까지만 관측됐다고 표시할 수 있다. 이를 모델 이해나 사람이 읽음으로 바꾸지 않는다.

정규형 digest에는 전체 본문, kind, reply_to, outcome, 발신/대상 핸들, 의미 있는 전달 옵션, 순서가 고정된 첨부 manifest를 포함한다. 표시 이름 변경과 transport 재시도 횟수처럼 같은 요청의 의미가 아닌 필드는 분리한다. UTF-8 정규화·개행·None 처리 규칙을 fixture로 고정한다. 승인 범위 변경이나 대상 대화 교체는 같은 ID의 재전송으로 허용하지 않는다.

답 대기는 저장된 reply_to 상관관계로 동작한다. 전달 영수증만으로 끝내지 않고, 실제 회신·대기 기한·호출자 취소·전송 거부·오류를 구분한다. 여러 부분 회신은 원 요청에 쌓으며 최종성 표현은 D02에서 정한다. 대기 취소는 상대 과제 취소나 수신 메시지 삭제로 전달하지 않는다.

### 4.4 수신 claim과 복구

수신 사본을 `pending → claimed(owner, generation, deadline) → handoff-recorded/acknowledged`로 다룬다. 이름은 가칭이며 원자적 rename·파일 잠금을 활용하는 방안을 먼저 검증한다. 응답 write/flush만으로 클라이언트가 내용을 소비했다고 단정할 수 없다. 실제 하네스가 후속 확인을 제공하는지 조사하고, 확인이 없으면 회수 가능한 상태와 at-least-once 경계를 표시한다.

claim 뒤 취소·stdout 오류·프로세스 종료·ack 유실을 주입한다. 확인 전 사본을 지우지 않고, 소유 프로세스 소멸이나 확인 기한에 회수한다. 훅과 inbox가 동시에 같은 요청을 읽을 때 한 경로의 정상 인계를 다른 경로가 파괴하지 않게 한다. 기존 중복 훅 예외와 native queue duplicate 제거는 별도 표본으로 유지한다.

`outbox.py`의 승인 전 보관과 원격 전송 대기, owned worker의 업무 저널은 의미가 다르다. 같은 이름의 저장소에 합치지 않고 각각 상태·소유자·수명을 명시한다. 이미 생성된 답을 재전송하기 위해 과제를 재실행하지 않는다. 부작용 직후 답 저장 전 중단은 중복 실행 가능성을 남기며 업무별 idempotency/readback이 필요하다.

### 4.5 첨부와 파일 권한

파일 manifest에는 수신자가 사용할 이름, bytes, digest, 출처 버전, 사본임을 표시한다. 원본 절대 경로는 공유 정책에 필요한 부분만 공개한다. MCP 프로세스가 sandbox 밖이라는 이유로 호출자가 못 읽는 파일까지 읽지 않게 한다.

하네스별 읽기 권한을 입증하는 방법은 D07의 설계·실측 과제다. 직접 경로 읽기가 권한을 확인하지 못하는 하네스에서는 호출자가 허용된 경로로 읽은 내용을 inline으로 제공하는 방식 등을 대조한다. 경로 입력과 inline 입력의 출처 강도 차이를 드러내고, 검증하지 않은 경로 모드를 지원 완료로 표시하지 않는다. 저장소 밖 임시 산출물과 숨김 일반 문서를 일괄 금지하는 것으로 이 문제를 대신하지 않는다.

송신 시 접근·공유 범위·실제 경로·제외 정책·크기를 검사하고, 같은 열린 파일의 내용을 읽어 digest를 계산한다. 검사와 읽기 사이 symlink 교체도 반례에 둔다. 수신 시 상대 경로를 신뢰하지 않고 수신자 생성 ID 아래에 저장하며 파일명·용량·할당량·내용 digest를 재검사한다. 첨부 저장과 본문 수신 중 어느 단계가 성공했는지 원 요청에 기록한다.

### 4.6 어댑터·도구·설치·원격 경계

능력은 `declared/observed/unsupported/unknown/degraded`와 관측 시각·해당 홈/대화/버전으로 표현한다. 하네스 이름 하나로 `can_wake=true`를 결정하지 않는다. 목록에서 도구를 숨기는 것은 검증된 능력에 한정한다. 캐시된 도구 목록을 갱신할 수 없는 하네스에는 조회 도구를 남겨 두며, 하향 뒤 미독을 회수할 경로를 항상 제공한다.

CLI와 MCP는 같은 서비스 함수를 호출한다. 메시징 지침은 skill 원문 또는 분리된 공통 원문 하나에서 생성하되, 실제 선택은 P03에서 파일 구조와 대조한다. 설치 allow 목록·도구 설명·사용 예시가 새 기능과 함께 업데이트되며 일반 작업 방식에 역할·종료 의무를 주입하지 않는다.

설치 레코드는 파일·항목별 이전 값, xsm이 쓴 값, 소유 근거, mode, 적용 단계·버전·복구 위치를 가진다. 현재 사용자 값이 xsm의 마지막 값과 달라졌으면 과거 백업으로 덮지 않고 충돌을 표시한다. setup은 준비·설정·신뢰·현재 세션 반영·첫 왕복을 따로 기록한다. xsm에 없는 계정 로그인을 이유 없이 새로 만들지 않는다. 선택한 원격 백엔드에 가입이 필요할 때만 해당 흐름을 연결한다.

원격은 `discover / send / status / capabilities / authenticated_origin / close`의 공통 의미를 제안한다. 전송 백엔드가 팀원을 accept해도 xsm 업무 범위 검사는 통과해야 한다. 기존 SSH와 새 백엔드가 로컬 신원·원장·첨부 규칙을 각각 복제하지 않게 한다. 비공개 Reason CLI나 호스팅 MCP를 로컬 필수 의존성으로 만들지 않는다.

## 5. 실행 순서와 의존성

실행 단위마다 끝나면 실제 사용자 경로 하나가 개선되어야 한다. 모든 저장 계층을 먼저 바꾸고 마지막에만 기능을 붙이는 순서로 진행하지 않는다. 각 단위에서 필요한 최소 공통 계약을 구현하고 다음 단위에서 확장한다.

| 단위 | 끝났을 때 사용할 수 있는 결과 | 필수 선행 | 난도·변경 묶음 예상 |

| P03 | CLI/MCP에서 실제 답을 기다리고 늦은 답을 회수 | P01, P02 | 큼, 2–3개 |

| P10 | 여러 홈의 설치·업데이트·제거와 실제 능력 진단 | P01, P02, P04 | 큼, 2–3개 |
| P11 | SSH/P2P/Reason 엔진/VPN+SSH의 같은 조건 비교와 선택 근거 | P00 | 큼, 조사·시험 2개 |
| P12 | 선택한 원격 경로에서 인증·가입·발견·첨부·질문·회신·복구 | P04, P05, P06, P07, P09, P10, P11 | 큼, 3–4개 |
| P13 | 실제 하네스·두 물리 머신·혼합 버전의 전체 여정 검증과 릴리스 자료 | P02–P10, P12 | 큼, 검증·문서 2개 |

변경 묶음은 검토 가능한 로컬 diff의 대략적인 크기 추정이며 PR 생성·게시 승인이 아니다. 실측과 사용자 결정이 남아 있어 달력 일정을 확정하지 않는다. P00의 재현 비용, P03의 MCP 입출력 방식, P11의 원격 실측 결과가 나오면 산정을 갱신한다.

P00→P01→P02를 우선하고, 이후 선행이 갖춰진 P03/P05, P04/P07/P09, P06/P08/P10을 병렬 후보로 진행한다. P11 원격 비교는 P00 뒤 로컬 구현과 겹친다. 배치는 일괄 장벽이 아니며 각 작업은 자신의 진입 게이트만 기다린다. [실행 계획](execution.md)에 가동 슬롯 3개의 계획 가정, 공유 파일 통합 담당, G00–G13의 진입·종료·실패·재검증 조건을 명시했다. 현재 요청의 산출물은 실행 계획이며 worker 시작이나 제품 구현은 진행하지 않았다.

## 6. 실행 단위별 상세 작업

각 단위의 종료는 그 단위에서 구현한 사용자 경로와 회귀 검사의 통과다. 뒤에서 생길 첨부·원격·설치 기능까지 포함하는 수용 조건은 먼저 부분 증거를 수집하고, [acceptance.md](acceptance.md)의 **수용 종결 선행** 단위까지 끝난 뒤 P13에서 최종 판정한다. 앞 단계가 담당한다는 이유로 조건 전체를 조기에 통과 처리하지 않는다.

### P00 — 기준선과 재현 시험체

**사용 경로:** 같은 저장소의 일반 세션 간 송신과 별도 저장소 연결 요청을 현재 버전 그대로 실행한다.

1. 기준 커밋과 CLI·훅·MCP·하네스·home·sandbox·설치 출처를 기록한다. 원본 사용 홈 대신 격리 XSM_HOME과 시험 설정을 준비한다.
2. 전체 `unittest discover`를 실행하고 실패·환경 의존을 원문 로그로 남긴다. 발견 지연과 호출자 lookup의 현재 예산을 기록한다.
3. 기존 비동기 승인 입력 표본과 실제 host 이벤트 형식을 대조한다. `<send_user_message_question_reply>`가 어느 이벤트·세션·질문 ID로 들어오는지부터 관측한다. 코드에 파서가 없다는 사실만으로 단일 원인을 확정하지 않는다.
4. 가짜 SSH·native queue·MCP client·시계·OS 명령의 기존 fixture를 재사용한다. 실제 프로세스를 지정 경계에서 죽이고 다시 실행하는 fixture를 추가한다.
5. 실제 하네스 시험에서는 승인된 전용 동료와 범위만 사용한다. 테스트 데이터에는 다른 세션 연락 금지와 파일 변경 범위를 명시한다.

**수정 후보:** tests/test_one_yes.py, tests/test_mcp_identity.py, tests/test_remote.py, tests/fixtures 및 신규 여정 runner. 제품 기능 변경은 이 단위의 성과로 계산하지 않는다.

**완료:** baseline 로그, 현재/기대 동작 분리, 재현 가능한 S5 승인 실패, 경계별 crash 제어를 확보한다. 재현 못 한 원인은 미확정으로 남기고 fixture 재현과 실제 재현을 구분한다. 기존 실환경 재현이 안 되면 과거 실패를 삭제하지 않는다.

### P01 — 기존 송신의 신원·무결성·증거 보강

**사용 경로:** 같은 저장소 동료에게 기존 송신을 하고, 오류 후 같은 ID로 재전송한다.

1. CLI·MCP·훅의 호출자 해석 결과를 공통 문맥으로 전달한다. 다른 홈의 같은 native ID, 상속된 다른 하네스 env, shared MCP의 A/B 교대 호출을 검사한다.
2. 일반 메시징의 기존 불확실 신원 대체 정책은 표시와 함께 유지한다. 허용 확대와 파일 읽기는 확실한 호출자 결속을 요구하며 정상 통신까지 일괄 거부하지 않는다.
3. 전체 요청 정규형과 SHA-256을 기록한다. preview는 표시용으로만 남긴다. `resend_refusal`과 수신 duplicate 검사가 같은 신원·내용 계약을 사용하게 한다.
4. queue 명령 성공·wake 시도·hook 수신·원격 저장을 분리해 기록한다. 소켓 write만 된 표본과 native queue 실패 표본이 런타임 수신 성공으로 표시되지 않게 한다.
5. 새 필드가 없는 구기록은 `legacy/unverified` 근거로 읽는다. 원문이 없는 과거 preview에서 전체 digest를 복원하지 않는다. 재전송 호환 방식은 D03 결과와 함께 명시한다.

**수정 후보:** xsm/identity.py, registry.py, mcp.py, send.py, receive.py, envelope.py, ledger.py, adapters.py. 별도 context 모듈은 실제 세 경로가 공유할 때 추출한다.

**검증:** A17-02, A18-01, A18-03, A23-03. 현재 tests/test_mcp_identity.py·test_open_mcp.py·test_xsm.py·test_remote.py를 확장한다. 앞 200자가 같은 다른 본문, 다른 홈·대상, reply_to/outcome 교체를 실패 표본으로 둔다.

**호환·되돌리기:** 기존 주소·status·일반 송신 입력을 보존한다. 새 증거를 sidecar 또는 버전 필드로 쓸 때 구 reader로 확인한다. 이전 writer가 새 필드를 지우는지도 검사한다. 새 writer를 끄더라도 이미 생성한 요청 증거는 조회할 수 있어야 한다.

### P02 — 연결 의도에서 원 요청 전달까지

**확정 목표:** 특정 후보 선택은 그 세션과의 협업에 결속한다. 다른 폴더의 상대 하나를 선택한 기본 경로가 폴더 전체 link/join으로 확대되지 않아야 한다. 기존 명시적 폴더 연결과 동일 요청 복구도 유지한다. ADR-0024/A24-04·07을 따른다.

**사용 경로:** “다른 저장소의 이 동료와 협업” 요청에서 필요한 판단만 받아 원 요청을 전송한다.

1. connect.plan_for의 기존 계획과 대상의 완전한 핸들·generation·원 요청 ID·plan digest를 결속한다. 대상이 모호하면 후보를 설명하며 다른 대화로 바꾸지 않는다.
2. 호출 가능한 기존 권한을 먼저 재사용한다. 추가 허용이 필요한 차이와 수명을 한 질문으로 표현한다. 프로젝트 이름이나 ID 입력을 사용자에게 요구하지 않는다.
3. P00에서 확인한 비동기 답 채널을 consent 어댑터로 연결한다. 요청 ID가 직접 제공되는 채널과 자유문장만 오는 채널의 결속 강도를 구분한다. 답이 수집되지 않으면 unknown과 회수 방법을 반환한다.
4. 판단 원문·적용 상태를 저장하고 승인·적용을 분리한다. 적용 직전 target/generation/scope/digest/철회를 다시 확인한다. 같은 유효 승인 아래 재시도에서 새 질문을 띄우지 않는다.
5. 권한 적용→전송 직전 중단, 적용 실패, 전송 결과 유실을 주입하고 readback 후 같은 ID로 재개한다. 새 의도를 link/join/reach로 번역한 결과를 보여 준다.
6. 형제 worker·다른 부모·부모 없는 세션이 승인된 공통 범위에서 직접 왕복한다. 기존 부모 전용 예외의 범위를 임의 확대하는 대신 사용자가 승인한 협업 집합을 적용한다.

**수정 후보:** xsm/connect.py, consent.py, outbox.py, config.py, mcp.py, cli.py, receive.py. 복수 경로의 공통 결정 레코드를 먼저 도입하고 P07에서 다른 판단 경로까지 확장한다.

**검증:** A15-01–06, A20-07. test_one_yes.py·test_link.py·test_open_consent.py·test_person_decisions.py를 확장한다. 실제 비동기 채널의 질문→답→연결→원 ID 전달→실제 회신을 하나의 trace로 남긴다.

**결정 지점:** D01·D04. 기본 연결 단위·수명이 바뀌는 새 정책의 활성화는 사용자 결정에 결속한다. 그 전에는 기존 범위·수명에서 같은 승인 적용을 견고하게 만드는 작업을 진행한다.

**호환·되돌리기:** 기존 연결·typed 명령을 읽는다. 이미 적용한 link를 무조건 지우지 않고 소유·적용 ID를 조회해 철회한다. 새 의도 기능을 꺼도 원문과 복구 위치가 남는다.

### P03 — 실제 답을 회수하는 질문과 비동기 인터페이스

**확정 목표:** 핸드셰이크는 실제 선택 상대의 상관된 응답으로 완료한다. 영수증만 있으면 대기 상태이며 같은 요청 ID로 후속 답을 회수한다. CLI/MCP는 같은 의미를 제공한다. 공개 API 철자·기본 대기 수치는 이번 사용자 결정에 포함되지 않았다.

**사용 경로:** CLI 또는 MCP 한 호출로 짧은 질문을 보내 실제 답을 받고, 기한 종료 뒤에도 같은 ID로 답을 찾는다.

1. 기존 `send --wait`와 별도의 질문 서비스/API를 추가한다. 공개 이름은 D02에서 정한다. 원 요청·실제 reply_to·상대 핸들을 대조한 회신만 수집한다.
2. 답 인덱스를 수신 훅과 inbox 양쪽에 연결하고 CLI/MCP가 같은 조회 함수를 사용한다. 전체 transcript나 최근 다른 답을 답변으로 선택하지 않는다.
3. MCP 단일 reader를 유지하면서 양식 응답·tool 호출·취소·ping을 ID로 분배한다. 긴 대기에서 다른 입력을 버리지 않는다. 요청별 context와 pending map을 사용하며 변경 연산의 잠금을 정한다.
4. 실제 하네스의 중첩 양식·동시 tool·취소 지원을 먼저 시험한다. 장시간 호출을 지원하지 않는 client는 짧게 ID를 반환하고 후속 회수로 하향한다. timeout을 성공 답변으로 포장하지 않는다.
5. CLI/MCP에서 priority·wake·reply_to·outcome·첨부 지원 능력의 의미를 맞춘다. 미지원 첨부는 P06 전까지 명시한다. sandbox Codex는 처음부터 MCP 경로를 선택하도록 지침·도구 설명을 생성한다.
6. 미독 안내·회수 도구를 능력에 맞게 노출한다. 동적 도구 목록을 반영 못 하는 client에서 숨김을 강제하지 않는다. 공통 지침의 단일 원문과 생성 결과 대조를 추가한다.

**수정 후보:** xsm/mcp.py, cli.py, send.py, ledger.py, inbox.py, receive.py, skills/xsm 및 설치 도구 목록. 새 reply-index 모듈은 저장·조회 공통 책임이 생기면 추가한다.

**검증:** A16-01–05, A16-07. 기존 test_channel.py·test_open_mcp.py 확장, 새 질문·MCP 입출력 시험. 영수증만 도착, 엉뚱한 reply_to, 동시 부분 회신, cancel과 reply 경쟁, 양식 대기 중 다른 호출을 반례로 둔다.

**호환·되돌리기:** 기존 send·inbox를 남긴다. 새 질문 계층을 제거해도 원 요청 ID와 답이 원장에서 회수된다. tool timeout 뒤 새 ID로 자동 재송신하지 않는다.

### P04 — 소비·인계 확인과 중단 후 회수, FYI

**사용 경로:** 수신 중 도구나 세션이 끊겨도 원 메시지를 회수하고, FYI는 다음 자연 소비 시점에 읽는다.

1. inbox.take의 즉시 삭제를 claim/ack 계약으로 전환하고 기존 queue duplicate 제거와 순서를 대조한다. 확인 기한과 owner generation을 기록한다.
2. 반환 write 전·중·후 종료, 대기 취소, ack 유실, hook/inbox 동시 접근을 주입한다. 확인이 없는 자료를 회수하고 이미 확인한 자료의 중복 처리를 억제한다.
3. 대상 홈·native conversation이 바뀌거나 daemon이 재시작하면 같은 ID를 올바른 대화에서만 회복한다. unknown 변경 연산은 readback 후 조정한다.
4. FYI를 저장만 하는 경로와 자연 소비 시점을 구현·시험한다. Codex queue 자체가 턴을 시작할 수 있으면 strict no-wake FYI를 queue에 넣지 않는다. 다음 prompt/tool 경계의 실제 소비 경로를 대조한다.
5. 보존·만료·offline·held·refused·unknown·outcome을 별도 축으로 표시한다. monotonic 대기와 저장 시각을 분리하고 시간 역행을 시험한다.

**수정 후보:** xsm/inbox.py, receive.py, ledger.py, send.py, codex_daemon.py, adapters.py, remote.py, housekeeping.py.

**검증:** A18-02, A18-04–07. test_open_receive.py·test_codex_wake.py·test_remote.py 확장, 별도 subprocess crash 시험. 일반 Codex 다중 홈의 실제 추가 사용자 입력 없는 수신·회신은 fixture 성공과 별도 기록한다.

**결정 지점:** D03·D05. claim 확인 기한과 보존 값을 시험체 입력으로 바꿔 검증하며 제품 기본값으로 굳히지 않는다.

**호환·되돌리기:** `.taking` 구기록·만료 claim을 새 reader가 회수하는 규칙, 구 reader가 읽을 export를 먼저 만든다. 구 reader가 삭제할 수 있는 복구 상태를 무분별하게 이중 기록하지 않는다.

### P05 — 업무 디렉터리와 대화 수명

**확정 목표:** 명시 공개 세션과 같은 repository의 폴더·워크트리 세션 합집합을 업무·머신·branch로 검색한다. 공개·후보 표시·선택·협업 권한을 분리한다. 업무 요약과 최신성으로 작업을 확인하게 하고 전체 경로나 transcript를 새로 공개하지 않는다. 원격 repository 동일성은 P12에서 검증된 매핑으로 구현한다.

**사용 경로:** 동명 동료를 담당 업무·repo/branch로 구분하고 후속 요청을 같은 대화로 보낸다.

1. registry 포인터와 native 이름을 유지하고 업무·branch·busy/idle·관측 시각·수신 능력을 부가 필드로 제공한다.
2. 기존 제목·계획·할 일 기록의 필요한 부분만 bounded tail로 읽는다. LLM 호출과 매번 전체 rollout 스캔을 넣지 않는다. 부분 JSON·파일 truncate/replace·오래된 cache를 검사한다.
3. 목록 필터 후 enrichment·업무 추출 순서를 유지한다. 실패한 추출기는 unknown이고 기본 발견·통신을 막지 않는다.
4. resume, 같은 pid의 새 대화, 다른 pid의 같은 대화, rename, pid 재사용, ref 충돌을 시험한다. 표시 검색 결과에서 확정한 핸들이 전송 직전에도 같은지 확인한다.
5. 제외 폴더와 metadata 공개를 등록·목록·첨부에 같은 의미로 적용한다. 심볼릭 링크와 아직 없는 하위 경로를 검증한다. 제외를 모든 미등록 세션의 통신 금지로 확장하지 않는다.

**수정 후보:** xsm/registry.py, identity.py, resolve.py, cli.py, mcp.py, probe.py, config.py. 업무 추출기는 하네스별 작은 함수/모듈로 분리한다.

**검증:** A17-01, A17-03–06. test_discovery_latency.py·test_self_registration.py·test_xsm.py 확장 및 제목/계획 fixture. 업무 요약의 의미·공개 적절성은 사람이 읽는 표본 검토도 필요하다.

**결정 지점:** D04·D06. doing·전체 경로 공개 기본값, 이름·오프라인 미독 수명, 최신성 예산을 정한다.

### P06 — 자료 사본과 기능 협상

**사용 경로:** 다른 폴더·홈의 동료에게 질문과 문서 사본을 보내 동일 버전으로 검토한다.

5. 수정본은 새 manifest/version으로 전달한다. doc 정본과 연결은 가능하지만 자동 덮어쓰기·병합은 하지 않는다.

**수정 후보:** xsm/mcp.py, cli.py, send.py, envelope.py, paths.py, remote.py, housekeeping.py 및 새 files 모듈. doc.py는 참조 메타데이터에 필요한 최소 변경만 한다.

### P07 — 사람 판단의 공통 수명과 주의 요청

**사용 경로:** 같은 질문의 여러 호출이 한 판단을 기다리고, 늦은 답과 OS 알림 실패를 정확히 처리한다.

1. P02의 판단 레코드를 grant·approve·decide·doc endorse에 적용하되 각 권한 범위는 합치지 않는다. 원문·실제 표시 digest·잘린 범위·응답 출처를 보존한다.
2. 같은 질문·범위·세대의 중복 호출은 진행 중 질문에 합류한다. waiter 취소와 실제 질문 취소·판단 소비를 분리한다.
3. 늦은 답은 기록하되 적용 직전 요청·대상·generation·철회 상태를 재확인한다. 원 질문을 바꾸거나 다른 요청의 승인을 붙이면 자동 적용하지 않는다.
4. 명시적 거부·창 닫기·자동 reviewer·client가 보이지 않게 decline·desktop 부재를 식별 가능한 범위에서 구분한다. 구분 불가는 unknown으로 표시한다.
5. OS 알림은 requested·OS-call-succeeded·failed·suppressed로 관측한다. 실제 사람이 봤다는 값은 별도 직접 증거 없이는 만들지 않는다. 지연 장벽에서 OS 명령을 멈추고 실패시켜 상태·빈도 제한·재시도를 검사한다.
6. 실제 UI에서 표시 잘림·중복 창·포커스·늦은 답 경쟁을 확인한다. 브라우저가 필요하면 ego-browser를 우선하며, 가짜 OS 명령 성공만으로 실제 UI 조건을 닫지 않는다.

**수정 후보:** xsm/consent.py, mcp.py, workers.py, channel.py, doc.py 및 선택한 notification 어댑터. 자체 UI·원격 서명 서비스는 필수 의존성으로 선행시키지 않는다.

**검증:** A20-01–06. test_person_decisions.py·test_open_consent.py·test_channel.py·test_workers.py 확장, 실제 UI observation. 승인 태그 위조와 잘린 본문 재사용도 포함한다.

**결정 지점:** D01·D08. 질문 수명·늦은 답 적용·표시 한도·알림 빈도·decision 보존을 정한다.

**호환·되돌리기:** 기존 판단 경로와 미처리 질문을 회수한다. 알림 어댑터를 꺼도 메시지와 판단이 남는다. 사용자 거부를 장애 복구 재시도로 돌리지 않는다.

### P08 — 소유 worker의 저널·답 재송신·문맥 수명

**사용 경로:** xsm이 소유한 worker에 두 발신자가 요청하고, 후속 질문·회신 실패·재시작에도 결과를 회수한다.

1. 기존 spawn/once/background 소유권과 기성 하네스 내부 spawn 거부를 유지한다. 일반 사용자 세션을 headless worker로 전환하지 않는다.
2. 요청 보관→수신 확인→실행→답 보관→답 전송의 저널을 추가한다. 답 전송 실패 뒤 같은 결과를 재사용한다.
3. 발신자·업무별 문맥 공유 단위를 명시하고 같은 공유 단위는 직렬화한다. 다른 단위는 허용 용량 내 병렬 처리한다. 독립 검토용 새 문맥을 분리한다.
4. 용량을 예약한 뒤 실행을 수락한다. 전부 busy일 때 새 요청은 persisted/queued/overloaded 중 실제 상태를 반환한다. 새 worker를 idle로 회수하거나 오류 문자열을 과제 성공 답으로 취급하지 않는다.
5. 일반 세션과 owned headless 경로의 native conversation ID·MCP 구성·후속 기억·권한을 각각 시험한다. 기본 조건과 별도 allowedTools 등 보정 조건의 결과를 섞지 않는다.
6. 요청 보관 직후·ack 직후·부작용 직후·답 보관 직후·답 전송 직후 종료한다. 모델 호출 수·부작용 수·답 ID·회수 결과를 기록한다.

**수정 후보:** xsm/workers.py, attempts.py, ledger.py, outbox.py 또는 별도 owned-request journal, adapters.py, codex_daemon.py. 새로운 serve 명령은 현재 존재하는 기능으로 문서화하지 않고 D09에서 공개 형태를 정한다.

**검증:** A16-06, A16-08, A18-08, A23-06. test_workers.py 확장과 새 저널·문맥 시험. 가짜 모델로 결정적 장애를 먼저 검사하고 구독 런타임의 실제 기억·최대 용량+1 시험을 별도 수행한다. Reason의 6명 숫자를 xsm 기본값으로 삼지 않는다.

**호환·되돌리기:** worker 기록 제거 뒤에도 요청·답 journal이 남아 조회된다. 새 풀을 끄면 기존 spawn으로 돌아가며 진행 중 작업을 임의 종료하지 않는다. 부작용 exactly-once는 약속하지 않는다.

### P09 — 출처 표시와 정상 협업을 보존하는 오용 제어

**사용 경로:** 구현자·검토자가 여러 차례 반례와 수정본을 직접 교환하고 악성 표시·무의미 반복만 구별한다.

1. 새 필드가 추가되는 각 앞선 단위에서 최소 경계 escaping을 함께 적용한다. 이 단위는 본문·이름·doing·branch·오류·첨부까지 전체 출처 표시를 감사한다.
2. 헤더·봉투의 구조 필드와 표시 문자열을 분리하고 예약 태그·ANSI·양방향 문자·유사 문자·중첩 봉투를 시험한다. 원문 자료를 무조건 훼손하지 않고 경계와 표시를 안전하게 한다.
3. 가짜 승인 주장·다른 요청의 실제 승인·authenticated machine 정보가 사람의 권한으로 승격되지 않게 한다.
4. 정상 N:N 검토 trace와 의미 없는 반복 trace를 대조한다. 반복 제한은 진단·회수·재개 위치를 제공하며 기존 attempts의 과제 실패 계보와 메시지 속도 제한을 혼동하지 않는다.
5. 정책 파일 오류에서 기본값으로 조용히 새 범위를 열지 않는다. 이전 유효 정책·오류 표시·미확인 새 grant의 적용 중단을 분리한다. 기존 fail_open과 native 통과는 별도 보존한다.

**수정 후보:** xsm/envelope.py, receive.py, policy.py, config.py, attempts.py, cli.py, mcp.py. 새 제한값은 D10의 실측과 사용자 결정 전까지 제품 기본값을 바꾸지 않는다.

**검증:** A22-01–06, K02·K06. test_envelope_nested.py·test_open_receive.py·test_vectors.py·test_workers.py와 새 renderer/반복 fixture를 사용한다. 허용되어야 할 정상 다회 왕복을 실패 표본과 같은 비중으로 둔다.

**호환·되돌리기:** 명시적 strict/deny는 보존한다. 새 오용 감지를 꺼도 출처 이력은 남으며 부모 계보 제한을 회귀로 잡는다.

### P10 — 설치·업데이트·제거·실제 능력 진단

**사용 경로:** 사용자 설정과 여러 홈을 가진 상태에서 설치/업데이트하고 기존·새 세션이 첫 왕복한다.

6. 공급 체크섬·서명/개발자 팀·핀 출처·라이선스·업데이트 소유자를 기록한다. P12에서 선택한 엔진만 실제 공급 시험을 추가한다. xsm 자체에 서명이 없는데 검증됐다고 만들지 않는다.

**호환·되돌리기:** 사용자 후속 수정을 보존하며 소유 항목만 복구한다. 리스너·credential·권한 규칙을 바꾸는 실제 실행은 별도 승인 근거와 결속한다. 기존 세션을 종료해 설치 성공을 만들지 않는다.

### P11 — 원격 백엔드 공통 비교

**사용 경로:** 같은 두 물리 머신·같은 업무를 SSH 개선안, 자체 P2P, 공개 Reason 엔진, VPN+SSH로 각각 연결한다.

1. A/B/C/D의 설치 입력·기존 전제·사람의 실제 조작·에이전트 도구 호출·첫 왕복·재연결·제거·로그 공개 범위를 같은 기록 형식으로 정한다.
2. 자체 P2P 후보는 인증·경로·복구를 확인하는 최소 spike를 만든다. 공개 Reason 엔진은 고정 버전 standalone 경로를 사용하고 비공개 CLI 의존과 분리한다. 후보 구현은 비교 시험체이며 제품 백엔드 채택이 아니다.
3. 양방향 SSH 불가, LAN, 같은 NAT, 서로 다른 NAT, UDP 차단, HTTPS proxy, 자체 relay의 조건을 실제로 확보한다. 환경을 못 만들면 그 셀과 필요한 운영자·장비를 미완으로 기록한다.
4. 직접/relay/SSH의 실제 경로와 포트, 계정·가입·키·project 권한을 각각 확인한다. 설치 로그만으로 통신 성공을 판정하지 않는다.
5. 설치 마찰과 운영·업데이트·키 회수·라이선스 비용을 비교한다. 결과·반대 증거는 보존하고 후속 실측을 계속 구분한다. D12의 제품 방향은 2026-10-29 사용자 결정으로 확보됐으며 비교 미완을 제품 선택 미응답으로 표시하지 않는다.

**수정 후보:** docs/spikes의 비교 계획·결과, tests/fixtures의 transport conformance, xsm/remote.py에서 실제 공유되는 작은 경계. 전송 전면 추상화만 만들고 끝내지 않는다.

**검증:** A21-03. A21-01/02/04–07의 실제 비교 표본도 수집하되 선택한 백엔드의 통합 수용은 P12에서 다시 확인한다. 후보의 지원 불가는 누락과 구분해 기록한다.

**호환·되돌리기:** 기존 SSH pairing을 이동·삭제하지 않는다. 비교 서비스와 fixture만 종료·제거하고 실제 사용자 네트워크는 별도 승인된 변경만 복구한다.

### P12 — 선택한 원격 백엔드의 제품 통합

**사용 경로:** 다른 물리 머신의 동료를 찾아 질문·자료·후속·회신을 주고받고 연결 중단 뒤 회복한다.

1. 확정한 자체 P2P를 공통 send/status/capabilities/origin 경계에 연결한다. Tailscale은 같은 프로토콜의 선택적 경로로 다루며 기존 SSH adapter도 호환 conformance를 유지한다.
2. 기기키·유효 초대로 가입하고 기존 활성 멤버 누구나 초대·추가·제명할 수 있게 한다. 계정 로그인과 별도 관리자 가입 승인을 필수로 두지 않는다. 가입 의도·대상 네트워크·공개·업무 허용을 구분하고 readback 불일치를 성공 처리하지 않는다.
3. 중복/만료/회수 초대·제명·오프라인 정책·key rotation·팀 전환 실패와 원 팀 복구를 시험한다. 백엔드가 강한 제명을 보장하지 않으면 그 한계를 표시하고 보장하도록 위장하지 않는다.
4. 원격 directory를 범위 내에서 제공하고 완전한 machine/home/conversation 핸들을 보존한다. 원격 이름·body에서 origin이나 권한을 만들지 않는다.
5. 첨부·reply_to·전체 digest·unknown 조정·수명과 만료를 로컬 서비스에 연결한다. backend 자체 accept로 xsm 판단을 건너뛰지 않는다.
6. 포트 점유·IPv6 부재·주소 변경·relay 중단·proxy에서 실제 경로와 하향 이유를 기록한다. 원격을 끄고도 로컬 왕복이 유지되며 소유 listener/service가 종료되는지 확인한다.

**수정 후보:** xsm/remote.py, config.py, consent.py, send.py, resolve.py, registry.py, install.py, probe.py 및 선택 backend adapter. Rust sidecar·라이브러리·버전·공개 relay 주소는 확정한 D12 요구사항 안에서 공급·운영 근거를 기록해 정한다. 실제 배포·유료 자원·사용자 권한 변경은 별도 승인 경계를 따른다.

**검증:** A21-01, A21-02, A21-04–07. 테스트망의 두 물리 머신에서 현재/이전 xsm, 다른 홈·런타임으로 실행한다. 같은 호스트 fake SSH만으로 완료하지 않는다.

**호환·되돌리기:** 새 backend를 끄면 기존 로컬·SSH로 돌아간다. 미완 원격 요청을 삭제하지 않고 조회·내보내기·정리 경로를 제공한다. key 폐기·제명은 사용자 작업으로 분리한다.

### P13 — 전체 여정·회귀·독립 검토와 배포 준비

**사용 경로:** 매뉴얼을 읽지 않은 에이전트가 설치부터 동료 발견·연결·자료 검토·후속·복구까지 수행한다.

1. 아래 여정 J01–J09을 실제 하네스에서 실행한다. 사람이 한 클릭·명령·승인·설정 수정과 에이전트 재호출·잘못된 첫 경로·복구 비용을 각각 센다.
2. 기존/신규 버전의 sender, receiver hook, MCP, state reader/writer를 섞어 실행한다. 구버전 미지원과 메시지 유실을 구별한다.
3. 구현에 참여하지 않은 검토자가 변경 diff·확정된 spec·수용 조건·실행 증거를 읽는다. 현재 계획 작성은 자체 대조이며 독립 검토를 이미 수행했다는 뜻이 아니다.
4. 70개 수용 조건을 각각 통과/실패/미실행으로 기록한다. 세부 셀이 남으면 해당 조건 전체를 통과로 표시하지 않는다. 기존 baseline 실패도 결과에 남긴다.
5. README·skill·MCP 지침·도구 목록·설치/제거 안내·프로토콜·테스트 계획을 실제 동작과 맞춘다. 기존 Accepted 결정 변경은 사용자 선택을 근거로 별도 기록한다.
6. 로컬 검토용 diff와 릴리스 노트·복구 절차를 준비한다. commit/push/PR/게시/배포는 기존 세션의 명시 승인 범위를 확인해 그 경계에서만 실행한다.

**완료:** P00–P12의 증거, K01–K11 회귀, J01–J09, 70개 조건의 판정, 남은 실환경 항목 처리와 사용자 정책 결정이 모두 일치한다. 시간·토큰 예산이 끝났다는 이유로 제품 완료를 선언하지 않는다.

## 7. 검증 여정과 실행 계약

### J01–J09 사용자 여정

새 테스트 파일 이름은 위 작업의 후보이며 존재하는 명령으로 제시하지 않는다. 실제 하네스·물리 머신 runner도 P00/P11에서 준비 후 명령과 환경 manifest를 고정한다. 제품 정책을 바꾸는 테스트는 사용자 확정 revision에 결속한다. 테스트를 먼저 작성하더라도 미결 정책을 사용자 결정으로 바꾸지 않는다.

각 단위는 현재 코드에서 실패하는 반례를 확인하고 수정 후 같은 경로로 통과시킨다. 가능한 경우 임시 복사본의 digest 비교 삭제·ack 이전 삭제 복원·flow ID 확인 제거 등 결함 변이를 넣어 검사가 실패하는지도 확인한다. 실제 제품·사용자 설정을 변이 대상으로 쓰지 않는다.

단위별 불변 검증 계약은 실제 positive/RED 명령과 fixture가 존재할 때 생성한다. 아직 없는 runner를 명령으로 채워 계약을 초기화하지 않는다. 계획 단계의 추적표는 실행 계약이나 제품 통과 증거를 대신하지 않는다.

### 관측 자료

시험마다 source revision, CLI/hook/MCP/harness version, home alias, mode, sandbox, machine alias, fixture/실환경 구분, request/reply/decision ID, 실제 경로, 시작/종료 사유, 명령과 exit code, 허용된 범위의 원시 증거 위치를 기록한다. 일반 계측에는 본문·credential·초대·절대 경로·사람 답 원문을 넣지 않는다. 필요한 민감 시험 원문은 접근 범위가 정해진 별도 증거로 보존하고 공개 보고에는 비식별 결과를 쓴다.

## 9. 이행과 되돌리기

1. **읽기 호환부터 확인한다.** 기존 record·receipt·asked·inbox·worker·pairing fixture를 새 reader로 읽는다. 새 데이터는 구 reader에 필요한 legacy projection을 함께 검증한다.
2. **필드 추가와 의미 변경을 구분한다.** 전체 digest·evidence·request/reply index는 additive하게 도입한다. 구 writer가 read-modify-write로 새 필드를 지우면 별도 sidecar 또는 writer 전환 방안을 선택한다.
3. **삭제와 이중 소비를 피한다.** claim/ack 같은 소유권 상태는 구 inbox reader와 단순 dual-write하지 않는다. 활성 reader 버전·세대를 확인해 소유권을 넘기거나 호환 export를 사용한다.
4. **진행 중 요청을 유지한다.** 설치 변경·어댑터 교체·backend 중지 전에 pending intent·decision·claim·reply·remote unknown을 조회하고 복구 경로를 남긴다.
5. **자동 cleanup을 분리한다.** 새 만료 정책은 확정 전 기존 자료에 소급 적용하지 않는다. attachment 원본, 사용자 설정, SSH pairing을 임의로 삭제하지 않는다.
6. **이전 코드로 실제 돌아가 본다.** 업그레이드 뒤 생성한 요청·답·설정이 있는 상태에서 이전 CLI/MCP/hook을 실행해 읽을 수 있는 범위와 미지원 범위를 확인한다. 백업 파일 존재만으로 rollback 성공을 판정하지 않는다.

권한 확대·사용자 설정 변경·키 제명·외부 서비스 시작의 되돌리기는 단순 코드 rollback과 다르다. 적용 요청과 소유 항목을 기준으로 readback한 뒤 사용자 승인 범위 안에서 수행한다.

## 11. 계획 실패를 미리 가정한 점검

| 실패했다고 가정한 장면 | 실패 조건 | 계획에 반영한 변경 | 확인 책임·시점 |

각 실행 단위의 구현 검토는 기존 기능과의 중복, 책임 계층, 끝에서 동작하는 사용자 경로를 함께 확인한다. 실제 공유 코드가 생기기 전 전송·정책·저장 프레임워크를 먼저 일반화하지 않는다. 이 판단으로 요청된 9개 ADR의 기능을 제외하지 않는다.

## 12. 완료의 두 수준

**이번 계획 작성의 완료**는 코드 근거·14개 실행 단위·병렬 배치 8개·G00–G13·D01–D12·원 제안 9개와 Accepted 보완 ADR 1개/43개 발견/70개 조건/20개 남은 실환경 항목의 연결, 공유 파일 소유권·슬롯·진입/종결 조건·링크·개수·의존성 자체 검증이다. 이것은 구현 완료나 정책 채택이 아니다.

**후속 제품 구현의 완료**는 확정된 정책 아래 P00–P13, K01–K11, J01–J09, 기존 수용 조건 62개와 추가 8개(총 70개)와 세부 실환경 셀의 실제 증거, 구버전 이행·복구·독립 검토가 충족된 상태다. 실패·미실행이 있으면 그 항목과 소유자·재개 조건을 남기고 전체 미완으로 보고한다.

## 2026-10-28 결정 반영

D04의 발견→선택→세션 협업 흐름과 D06의 공개 후보 집합은 ADR-0024로 확정했다. D02의 실제 응답 기반 핸드셰이크 의미도 확정했다. D02의 API 이름/숫자 대기값, D06의 수치 예산/보존값과 나머지 미결 정책까지 승인된 것은 아니다. 세부 범위는 [확정 설계 5절](collaboration-contract.md)을 따른다. 9절의 기존 결정표는 결정 항목 목록이며 이번에 확정된 부분을 다시 미결로 해석하지 않는다.
