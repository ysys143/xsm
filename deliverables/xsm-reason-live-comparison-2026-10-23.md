# xsm과 Reason을 같은 세션에서 사용한 비교

2026-10-23. xsm 0.4.20, Reason CLI 0.2.557, Reason 엔진 0.12.10, Claude Code 2.1.309, Codex CLI 0.163.0.

같은 저장소에서 질문하고 동료에게 검토를 맡기는 일은 두 도구 모두 잘됐다. 실제로 xsm에서도 이름만으로 상대를 찾아 추가 프로젝트 연결이나 ID 입력 없이 협업했다. 차이는 새 저장소를 연결할 때, 답을 회수하는 인터페이스, 일반 Codex의 유휴 수신에서 나타났다.

다른 저장소의 연결 후 비교는 미완이다. 사용자가 연결을 승인했지만 xsm이 비동기 응답을 기록하지 못했고, 문서에 있는 `--reply` 대체 경로도 거부했다. 이 승인 기록을 우회하거나 도구 코드를 고쳐 통과시키지 않았다.

## 비교 조건

- 같은 Claude 세션에 xsm과 Reason MCP를 함께 로드했다. alpha·beta는 현재 저장소 안의 서로 다른 작업 폴더, gamma는 별도 Git 저장소에 뒀다. 일반 Codex 세션도 같은 저장소 안에서 실행했다.
- alpha는 xsm부터, beta는 Reason부터 시작해 순서를 바꿨다. 같은 소스와 같은 입력에 대해 두 도구로 질문했다. 작은 표본이며 속도·모델 품질의 통계 비교는 아니다.
- Claude 세션은 동일한 실제 모델·auto 권한 모드였다. xsm 송신은 기존 설치의 허용 규칙을 사용했고, Reason 송신은 이전에 승인받은 평가용 세션 한정 허용을 사용했다. 그 보정을 하지 않은 완전 기본값 비교라고 주장하지 않는다.
- 일반 Codex는 `.codex-3`, workspace-write, approval_policy=never였다. 같은 세션에 두 도구로 보냈다. xsm 레지스트리의 권한 표시보다 실제 turn_context의 샌드박스 기록을 기준으로 삼았다.
- 비교용 과제는 앞서 만든 JSONL 요약 CLI의 출력·종료 코드 분석과 반례 검토였다. 원본 코드나 설정을 고치는 작업은 요청하지 않았다.
- 두 도구는 이미 설치돼 있었고 Reason 계정·네트워크 가입도 끝난 상태였다. 새 계정 가입, 새 머신 설치, 인터넷을 통한 원격 연결의 비교는 아니다. 새 저장소의 세션이 기존 협업에 들어오는 과정을 비교했다.
- 현재 대화에서도 두 MCP를 직접 호출했다. 앞선 Reason 조사에서 사용한 별도 JSON-RPC 연결 코드는 이번에 사용하지 않았다.

설치된 xsm CLI·Claude 런타임 사본은 커밋 `b29b39ce65c594e88e4b84684724fe02553ee2fc`의 0.4.20이었다. Codex 플러그인도 0.4.20이며 비교에 관련된 send·receive·config·mcp·adapters 파일이 체크아웃과 같음을 확인했다.

## 마찰이 실제로 갈린 곳

### 같은 저장소에서는 xsm도 간단했다

xsm은 `cmp-alpha`, `cmp-beta`, `cmp-codex`라는 이름으로 보냈다. 발송할 때 ref를 직접 입력하거나 프로젝트를 새로 선언하지 않았다. 같은 저장소라는 기본 범위가 바로 적용됐다.

이 조건에서는 “xsm은 먼저 복잡한 project와 ID를 다뤄야 한다”는 설명이 맞지 않았다. 범위를 넘어가는 순간에 그 개념과 연결 절차가 드러났다.

### 새 저장소에서는 Reason이 더 적은 단계로 연결됐다

gamma가 Reason 네트워크에 세션으로 나타난 뒤에는 같은 요청을 바로 보내고 답을 받았다. 네트워크 참여 권한은 이미 주어진 상태였고, 폴더별 추가 연결은 없었다.

xsm은 gamma를 발견했지만 addressable=false와 scope 없음으로 표시했다. 첫 메시지는 보내지 않고 보관했으며, 현재 저장소와 새 저장소를 잇는 사용자 승인을 요구했다. 이 최초 거부 자체는 현재 범위 정책의 동작이다.

그다음은 별개의 문제였다. 사용자는 비동기 질문에 “비교용 연결 허용, 종료 후 해제”라고 답했다. 같은 전송을 재실행해도 승인 읽기 단계로 가지 못했다. 문서에 있는 대체 방법으로 그 답을 그대로 `--reply`에 넣었지만, xsm은 사용자 기록과 일치하는 답이 없다며 무시했다. 해당 세션의 recent 프롬프트 기록에 승인 문구가 없고 pending verdict도 null인 것을 확인했다.

따라서 이 표본은 사용자 거절도, 승인 없이 연결하려 한 시도도 아니다. 이 실행에서 비동기 승인 응답이 xsm의 승인 기록으로 들어오지 않은 것이다. 일반 입력창 응답이나 다른 승인 UI까지 모두 실패한다고 일반화하지 않는다.

연결 해제 호출은 두 폴더가 연결되지 않았다고 확인했다. 승인 이후 통신이 얼마나 매끄러운지는 선행 조건이 성립하지 않아 검증하지 못했다.

### 일반 Codex 수신은 xsm 쪽이 성공했다

xsm으로 보낸 요청은 같은 `.codex-3`의 일반 Codex 세션에 도착했고, 실제 코드 분석 후 회신이 돌아왔다. 원장에서도 task succeeded가 확인됐다. 이는 수신자가 보고한 결과이며 독립 검증과 동일한 뜻은 아니다. 이번 분석 답은 별도 기준 실행과 대조했다.

회신 과정에 마찰은 있었다. Codex가 수신 문맥의 CLI 답장 명령을 실행했다가 샌드박스에서 거부됐고, 오류 안내에 따라 xsm MCP로 전환해 성공했다. 최종 성공에 이 한 번의 실패와 복구가 포함돼 있다.

Reason은 같은 세션을 idle·push로 목록에 표시했고 송신 도구는 Codex에 queued됐다고 반환했다. 그러나 데몬 로그에는 해당 스레드의 rollout을 찾지 못했다는 오류와 훅 대기로 대체한다는 기록이 남았다. 대상 TUI에 추가 입력을 주지 않은 채 다른 비교를 진행했고, 마지막 확인에서는 약 26분이 지난 뒤에도 request read_at=null, reply_count=0이었다. 이 시간을 모델 응답 속도로 해석하지 않는다. 모델이 요청을 읽지 못한 경로다.

앞선 조사와 같은 다중 홈 라우팅 문제를 이번의 동일 대상 비교에서도 관찰한 것이다. Codex의 모든 홈·실행 모드에서 Reason이 실패한다는 뜻은 아니다. 비교를 위해 Reason 설정을 고쳐 성공시키지는 않았다.

### 답변 회수 방식에는 서로 다른 편의가 있었다

Reason 답은 이 대화에 직접 들어왔다. 한 번은 제가 이미 주입된 답에 대해 check_inbox까지 호출해 No messages를 받았는데, 이는 실패가 아니라 중복 조회였다. 그 대기 시간을 제품 지연으로 세지 않았다.

xsm 답은 이 실행에서 inbox를 통해 회수했다. 대신 원 요청과의 연결, kind=reply, task succeeded가 함께 표시됐고 status 조회에도 결과가 남았다. 전달과 과제 결과를 기계적으로 구분할 정보가 있다는 점이 편했다.

짧은 질문의 CLI에서는 Reason이 더 간단했다. 한 명령이 실제 답까지 반환했다. xsm send의 wait는 전달 영수증을 기다리므로 실제 답을 읽는 단계가 따로 필요했다. 실행 시간의 직접 우열보다는 호출 단위의 차이다.

## 내 사용감에 대한 결론

평소 같은 저장소 안에서 여러 에이전트와 일하는 상황에서는 xsm도 충분히 매끄러웠다. 이름으로 찾고, 직접 검토를 요청하고, 후속 작업을 이어가는 핵심 흐름이 실제로 됐다. 부모·자식 관계 때문에 직접 협업이 제한된다는 식의 일반화는 이번 실행과도 맞지 않는다.

Reason에서 더 부드럽게 느낀 것은 이미 참여한 네트워크에 새 저장소 세션을 추가하는 과정과 답까지 반환하는 질문 명령이었다. 반대로 현재 내 환경의 일반 Codex 수신과 결과 상태 기록에서는 xsm 쪽이 유리했다.

따라서 “Reason이 전반적으로 마찰이 적다”보다 “새 협업 범위의 구성과 질문 인터페이스는 Reason이 간단했고, 같은 범위 안의 협업은 둘 다 됐으며, 현재 다중 홈 수신은 xsm이 작동했다”가 이번 증거에 맞는 설명이다.

구체적으로 드러난 xsm 개선 지점은 직접 협업 기능의 부재가 아니다. 비동기 사용자 승인 응답을 놓치는 경로, 샌드박스 수신자에게 CLI 답장을 먼저 안내하는 문맥, 질문부터 실제 답까지 이어주는 호출 단위가 검토 대상이다. 이 보고서에서는 제품 코드를 수정하지 않았다.

## 미완 구간과 정리

- 미완 구간: S5의 xsm 연결 성립 후 재전송·후속 요청 비교.
- 수행자·일자: Codex, 2026-10-23.
- 원인: 실제 사용자 승인 응답이 xsm의 승인 기록에 들어오지 않아 정상 연결 경로가 진행되지 않음. 문서상 대체 경로도 실패.
- 재검증 조건: 승인된 연결을 정상적으로 처리하는 경로가 확보된 뒤 동일한 폴더 관계로 수행. 사용자는 연결을 승인했으며 이 구간을 제외하라고 승인한 것은 아니므로 완료로 표시하지 않음.
- 평가용 Claude 세션과 실행기를 종료하고 Codex 평가 클라이언트를 닫았다. 기존 사용자 세션과 공유 런타임은 유지했다. 두 폴더의 xsm 연결은 남아 있지 않다.
- 실제 xsm 소스 31개의 해시는 전후 동일했다. 임시 과제와 로그는 Git 추적에서 제외된 평가 경로에 두었다. 비밀 연결 정보와 개인 경로를 제거한 증거만 보고서 옆에 보존했다.

이 결과는 두 도구가 함께 설치된 단일 머신의 작은 표본이다. 각각 단독 설치, 새로운 계정 가입, 다른 컴퓨터, 장시간 안정성의 우열은 판정하지 않는다.
