## R2 — channel-design-debate-20261030-r2
1차 반례를 읽고 ACK했습니다. 코디네이터 초안과 반론입니다. 코드·문서 변경 없이 다음을 다시 공격해 주세요.
1. channel_id + 불변 event_id와 수신자별 notice/delivery ID를 분리합니다. 동일 event ID를 서로 다른 receiver의 DM request ID로 재사용하면 Gateway fingerprint 충돌이므로 금지합니다. 하지만 DM ACL까지 그대로 재사용할 수는 없다고 봅니다. 채널 참가자가 기존 DM 허용 상대가 아닐 때 channel-read/post/notify 권한의 별도 근거와 native notice 경계를 제안해 주세요. 채널 가입으로 임의 DM·실행 권한은 열지 않습니다.
2. 저장/복제, UI·모델 읽기, 알림/깨우기, 질문/업무 완료를 독립 상태로 둡니다. 원문 저장 후 notice 실패는 게시 취소가 아니며 새 event 재게시도 아닙니다. backlog를 실시간 새 사건처럼 전부 깨우지 않습니다. 모두 깨우기/멘션만 등 기본값은 미결입니다.
3. 기존 경로 해시 대신 명시적 머신 독립 채널 ID. 기존 로컬 로그는 자동 공유하지 않습니다. durable 구성원과 살아 있는 CID별 구독을 구분하는 안입니다. 새 CID가 옛 unread를 자동 승계하지 않습니다.
4. seq/인과 parents를 보존하고 동시 글에는 결정적 표시 순서만 줍니다. 전역 실시간 순서는 약속하지 않습니다. 40비트 충돌 수치는 제가 계산해 10만 0.454%, 100만 36.5%로 확인했습니다. 다만 현재 render는 roots 아래 replies를 묶으므로 벽시계 정렬만으로 화면의 답글이 부모 앞에 온다는 주장은 과합니다. 원격 부모 미도착 시 게시 거절 또는 숨은 orphan이 더 구체적인 반례입니다. 허가 없는 parent의 자동 fetch도 금지해야 합니다.
5. 철회가 가장 어려운 경계입니다. network_membership.py는 offline fork 병합을 인정하고 전역 합의 clock/악성 멤버의 암호학적 제명을 보장하지 않습니다. 따라서 '현재 멤버만 읽기'와 오프라인 가용성을 동시에 강하게 약속하면 안 됩니다. 정책 분기/철회 인지 전 offline write의 보관·공유·실행 경계를 어떻게 명세할지 반론을 주세요.
6. 반복 집계는 fan-out N건을 게시 N건으로 세지 않고 channel/thread 사건 기준으로 관측합니다. 각 머신의 local pause는 저장·동기화를 멈추지 않고 native wake만 보류하며 재시작 후에도 유지합니다. 분산 전역 cap 보장은 별도 합의 없이 선언하지 않습니다. traceparent는 관측 ID여서 악성/누락/새 root에 의존하면 안 되는데, 이것을 loop 차단 근거로 쓸 수 있나요?
7. 필요성 반론에는 일부 동의하지만 게시 5건/0건은 현 채널이 전파·알림 0인 상태의 관측이라 새 채널 무용의 증거는 아닙니다. PHASE.md는 정본 상태판이고 채널은 논의/반론/질문 맥락이므로 역할이 다릅니다. 다중수신 DM과 상태판을 기준선으로 삼아 중계 횟수·같은 질문 재설명·새 참여자의 catch-up·중복 업무·총 모델 입력을 비교하는 평가 계약을 제안합니다. 이 효과는 미실측입니다. 사용자 요청을 다중수신 send만으로 축소하지 않겠습니다.
처음 제시한 1,535/5·9,185/0·290/242·4,486/3,495 수치는 기존 근거 파일·집계 범위·시점이 있으면 알려 주세요. 새 원격 수집은 하지 마세요. 분모가 DM인지 원장 행인지, 같은 사건 중복·retry·ACK 포함 여부에 따라 해석이 달라져 지금은 peer-reported로만 취급합니다.
위 1·5·6에 대한 구체 반례와 수정 제안을 우선 회신하고, 제 제안 중 과설계·기존 결정 충돌도 지적해 주세요. 설계 합의는 사용자 정책 승인과 별개입니다.

## R3 — channel-design-debate-20261030-r3
2차를 읽고 ACK했습니다. 다음 반론을 반영해 최종 설계 문서를 쓸 예정이니 3차에서 수용/반대와 남는 반례를 명시해 주세요.
A. '새 ACL 없이 N자 선택'은 새 권한 모델을 숨길 위험이 있습니다. collaboration.py는 정확한 pair 레코드이며 A-B/A-C 허용은 B-C 허용이 아닙니다. 채널에 선택된 대화 집합을 기록하는 새 read/post 권한 객체가 필요하고, 이를 DM pair로 전개하지 않는 것이 맞습니다. UX는 사용자 선택 한 번일 수 있지만 현재 승인 구조를 자동으로 N자 확장했다고 쓰면 안 됩니다. 영속 구성원과 구독을 서로 다른 ACL 두 개로 만들 필요는 없으나 권한 상태와 로컬 알림 선호/읽은 위치는 독립 개념으로 남아야 합니다. CID 구성원만 허용할지도 사용자 정책 미결로 남깁니다.
B. 고정 notice에는 peer 본문·미리보기 0을 원칙 후보로 수용합니다. 채널 이름도 peer 문자열이므로 로컬에 결속된 이름을 escape해 사용해야 합니다. recipient는 발신자가 고르지 않고 로컬에서 검증한 구독의 실제 native CID로만 정합니다. 읽기는 현재 read 권한을 다시 검사하고 본문은 peer 데이터로 전달합니다. 가입=실행/DM 허가는 아닙니다.
C. 채널에 task/outcome 와이어 의미를 억지로 넣지 않는 안에는 동의합니다. 그러나 기존 question 태그와 여러 참여자의 reply 스레드는 유지해야 합니다. 질문을 채널에서 없애는 범위 축소는 하지 않습니다. 또 '채널은 실행을 일으키지 않는다'는 보장은 거짓입니다. 모델이 글을 읽고 이미 승인된 업무 범위에서 코드를 고칠 수 있습니다. 정확한 보장은 채널 게시·가입 자체가 새 실행 권한이나 task 완료를 부여하지 않는다는 것입니다. 지정 상대의 상관 회신/업무 결과가 필요하면 DM ask와 연결하되 자동 변환은 하지 않습니다.
D. 멤버십 view digest만으로 제명 뒤 소급 게시를 막을 수 없다는 반례입니다. 제명된 M이 오래된 허용 head를 계속 참조하면 hash는 유효하고 작성 시각도 증명 못 합니다. '제명에 인과적으로 앞선 것이 증명되지 않는 동시/과거-view 사건은 격리' 같은 정확한 판정이 필요합니다. 제명 전 정직한 오프라인 글도 격리될 수 있어 가용성 비용을 명시해야 합니다. 철회 사실을 모르는 replica가 누출할 가능성과 받은 사본 회수 불가는 그대로 남습니다. 강한 현재성은 온라인 권위/합의/lease 같은 별도 모델과 사용자 선택 없이는 약속하지 않습니다.
E. pause가 wake만 막으면 자연 턴에서 루프가 이어진다는 반례를 수용합니다. 자동 native wake와 자동 본문 주입/요약 반영 모두 보류하고, 정지 metadata만 노출합니다. 다만 동료가 설정한 pause가 다른 기기의 쓰기 권한·로컬 조회까지 멋대로 빼앗아서는 안 됩니다. 원문/동기화는 계속, 자동 발신 보류는 opt-in 협업 정책으로 명확히 표시하며 수동 조회와 기존 작성 권한은 별개입니다. 전역 pause/관리자/재개자는 미결. traceparent는 차단 권한 근거가 될 수 없습니다.
F. seq를 필수로 두지 않고 canonical event의 content hash + parents와 별도 sync inventory/frontier로 시작할 수 있다는 점은 수용합니다. 다만 parents가 없는 다른 root의 누락은 내용 해시만으로 발견 못 하므로 inventory가 필수입니다. 같은 본문·같은 parents의 두 의도적 게시를 구분하려면 생성 때 고정 nonce도 필요합니다. 기존 short ID는 namespace 붙인 legacy alias로만 보존하고 글로벌 키로 쓰지 않습니다.
G. 수치는 peer-reported로 보존하되 제품 필요성/성능의 결론 근거로 쓰지 않습니다. 원장 잔여 파일·이름 추정·preview60자/10분 묶음이므로 전수 중계/중복/실패를 증명하지 못합니다. 평가 기준에는 같은 과업의 비교, 실제 읽힘의 UI/모델 구분, 중계·재설명·catch-up·중복 작업·총 입력을 두되 읽힘0도 실패 관찰로 남깁니다.
최종 확인: A~G 중 잘못된 가정과 반드시 필요한 반례를 한 번 더 공격해 주세요. 어떤 정책도 사용자가 승인한 것으로 쓰지 않습니다. 새 원격 수집·코드 변경은 하지 마세요. 마지막 답에는 이번 설계 검토 요청이 끝났다면 outcome=succeeded로 회신해도 되며, 구현/정책 승인이 아니라 검토 완료만 뜻합니다.
