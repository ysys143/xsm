# 메시지 전달 상태와 과제 결과: 협업 설명

이 문서는 현재 xsm의 상태 표현을 읽는 사용 안내다. 구현 변경이나 버그 확정은 제안하지 않는다.

| 표현 | 읽을 수 있는 사실 | 단정할 수 없는 것 |
|---|---|---|
| sent-unconfirmed | 송신을 요청했으나 수신 영수증을 아직 확인하지 못함 | 미도착 확정, 작업 실패 확정 |
| delivered | 수신 측이 인계 영수증을 기록함 | 모델의 이해·실행, 사용자 명시 승인, 과제 성공 |
| held | 해당 경로가 메시지를 보관하고 허용을 기다림 | 영구 폐기 |
| unchecked | 발신자나 범위를 확인하지 못한 상태로 통과한 경로 | 확인·승인 완료 |
| outcome=succeeded/failed | 원 과제가 이 기계 장부에 있을 때, 연결된 회신의 결과를 원 과제에 기록함 | 결과의 독립 검증 완료 |

범위 검사와 사용자 동의는 별도다. 기본 정책이 허용하는 경로와 사용자 응답을 동일하게 표시하지 않는다. 사용자의 최근 요청을 승인 근거로 쓰는 기본 경로도 있으므로 별도의 yes가 항상 필요하다고 설명하지 않는다.

네이티브 메시지에는 별도 경로가 있다. 이 기계의 세션 소켓에서 온 Claude 네이티브 메시지는 xsm의 프로젝트 범위 검사 없이 통과한다. 소켓 없는 원격 네이티브 메시지도 기본 remote_native=pass 정책에서는 unchecked로 통과한다. xsm 헤더가 있는 메시지의 검사와 혼동하지 않는다.

보관 실패 뒤에는 blocked 영수증을 남기면서 경고와 함께 본문을 전달할 수 있다. 게이트 오류가 나고 프롬프트가 peer 메시지로 판별되는 경우에는 fail-open 정책에 따라 경고와 함께 통과할 수 있다. fail_open이 켜져 있으면, 영수증 쓰기를 감싼 _safely가 오류를 기록하고 진행하는 경로에서도 영수증이 없을 수 있다. 따라서 영수증 부재를 미도착으로 단정하지 않는다.

과제의 종료와 성공도 구분한다. failed 결과가 기록된 과제는 종료됐지만 성공한 것은 아니다. outcome 필드가 없는 회신은 성공 완료의 증거가 아니다.

근거는 동봉한 source-evidence-v3.txt의 실제 소스 발췌다. source-integrity.json은 coordinator가 분석 전 manifest와 현재 xsm 파이썬 소스의 SHA-256을 비교해 보고한 결과이며, 수신자가 직접 원본을 재검증했다는 뜻은 아니다. 이 설명을 xsm의 새로운 보장으로 읽지 않는다.
