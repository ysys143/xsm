# Reason으로 실제 협업하며 느낀 점

2026-10-23. Reason CLI 0.2.557, 엔진 0.12.10을 사용했다. 목표는 마이그레이션 결정이 아니라, 에이전트인 내가 일을 진행하기 편했던 인터페이스와 그 이유를 찾는 것이었다.

실제 업무에서 편했던 부분은 있었다. 질문 하나로 답변까지 돌려받는 호출, 작업 맥락이 보이는 상대 목록, 다른 Reason 도구 결과에 붙는 읽지 않은 메시지 안내, 작은 파일을 메시지와 함께 전달하는 방식이다. 다만 직접 협업이나 수신 알림은 xsm에도 이미 있다. Reason에서 편하게 썼다는 사실을 Reason만의 장점이나 xsm보다 낫다는 증거로 취급하면 안 된다.

## 수행한 업무와 결과

| 업무 | 실제 수행 | 결과 |
|---|---|---|
| 코드 공동 분석 | 현재 xsm의 송신·수신·영수증·범위 코드를 나눠 읽고 상대의 설명을 반박·보완 | 전달 상태와 과제 결과를 구분하는 설명 작성. 실제 xsm 파이썬 소스 31개는 전후 SHA-256 동일 |
| 임시 CLI 구현·검토 | JSONL 요청·답장·미응답을 집계하는 CLI 구현, 독립 검토자가 테스트 작성, 옵션 추가 계약을 서로 직접 전달 | v1 26개 통과, v2 옵션 추가 전 새 3개 실패, 구현 후 29개 통과. coordinator 재실행도 29개 통과 |
| 공동 문서 작성 | 초안과 소스 발췌를 첨부하고 여러 차례 조건·출처 표현 수정 | 한국어 최종 문서가 첨부 자료 기준으로 PASS. 원본 전체를 독립 재검증한 판정은 아님 |

검토자와 구현자 사이에는 실제 Reason MCP 송신 5건이 있었다. 제가 옵션 변경을 검토자에게 전달한 뒤, 검토자가 구현자에게 계약을 전했고 구현자가 수정 후 재검증을 요청했다. 제가 그 사이의 모든 문장을 전달할 필요는 없었다. 이것은 직접 협업의 유용성을 확인한 사례이며, xsm에 없는 능력을 발견한 사례는 아니다.

테스트가 구현을 무조건 통과시키는지도 확인했다. 응답 없는 요청까지 answered에 넣도록 사본 하나를 변경하자 29개 중 9개 검사가 실패했다. 원본 구현과 실제 저장소에는 이 변이를 적용하지 않았다.

## 여섯 가지 흐름에서 느낀 점

| 흐름 | 실제 장면과 내 경험 | xsm과 비교할 때의 경계 |
|---|---|---|
| 상대 발견 | 세션의 이름·작업 폴더·상태와 내 위치가 같이 보여, 구현 담당과 검토 담당을 고를 수 있었다. 다만 Codex의 CLI 상태·이름 등록은 실패해 기본 주소를 유지했다. | xsm도 이름과 프로젝트로 대상을 찾는다. ID 없이 보냈다는 것만으로 Reason의 독점적 장점은 아님 |
| 동기식 질문 | `reason network 상대 "질문"` 한 번으로 소스 근거가 있는 답까지 받았다. 수신함이나 회신 주소를 따로 관리하지 않고 내 분석으로 돌아온 점이 편했다. | 실제 차이가 있는 인터페이스. 현재 xsm의 `send --wait`는 답변이 아니라 전달 영수증을 기다림 |
| 비동기 협업 | 분석과 테스트를 맡긴 동안 나는 소스 확인과 문서 작성을 계속했다. 다음 Reason 호출 결과의 unread 안내를 보고 여러 답을 모아 읽었다. 잠시 중단했다 돌아왔을 때도 완료 보고를 회수했다. | xsm MCP와 CLI에도 수신 대기 안내가 있다. 이 장점은 공통 기능의 실제 사용 사례 |
| 맥락 전달 | 문서·예제·코드를 첨부하면 수신 사본의 경로가 메시지 본문과 구분돼 표시됐다. 초안에 정의와 근거가 없다는 지적을 받고, 다음에는 소스 발췌와 출처도 함께 보냈다. | Reason의 `send_message(files=...)`는 참고할 만한 구체적 인터페이스. xsm의 `--text-file`은 본문 입력이며 MCP 송신 스키마에는 files가 없음. xsm의 공동 문서 기능 자체가 없다는 뜻은 아님 |
| 협력자 재사용 | 같은 Codex MCP 세션은 분석의 네 구분을 유지한 채 구현과 옵션 수정으로 이어갔다. 반면 기본 조건의 serve Codex는 후속 질문에서 앞선 답을 기억하지 못해 로컬 로그를 찾아 복구했다. | 주소 유지와 대화 맥락 유지는 다르다. serve의 두 요청은 서로 다른 transcript였다. Reason의 모든 재사용 경로가 좋았다고 할 수 없음 |
| 상대를 방해하는 정도 | 즉시 행동할 필요 없는 편집 방침을 `--fyi`로 보냈다. 약 82초 동안 상대의 새 턴이 없었고, 나는 다른 일을 계속했다. 그러나 뒤의 정상 요청 후에도 상대는 해당 FYI를 못 받았다고 했고 DB의 read_at도 null이었다. | 깨우기와 전달을 구분하는 의도는 유용하다. 다만 이번 경로의 지연 소비는 확인되지 않았다. xsm도 priority=later와 깨우지 않는 채널 게시를 제공하므로 이 의도 자체가 새롭지는 않음 |

xsm 쪽 근거는 현재 `xsm/mcp.py`의 수신 알림과 송신 스키마, `xsm/cli.py`의 `--text-file`·`--priority`·`--wait`, `skills/xsm/references/guide.md`의 채널 게시 설명이다. xsm을 같은 업무와 같은 조건으로 실행한 대조 시험은 하지 않았으므로 실제 편의성의 우열을 단정하지 않는다.

## 내가 다시 쓰고 싶은 원칙

### 질문은 답까지 반환하는 단위가 편했다

내 목적이 짧은 확인 질문이라면 “전달됨”보다 상대의 실제 답이 필요하다. Reason의 동기식 질문 명령은 그 한 단계를 묶어줬다. 이 편의는 통신 엔진을 바꿔야만 얻는 성질이 아니라, 사용자와 에이전트에게 어떤 작업 단위를 노출하는가의 문제로 보인다.

다만 같은 주소에 다시 물었을 때 앞선 대화가 유지되는지는 별도 계약이어야 한다. 이번 serve Codex는 스스로 기억하지 못한다고 밝혔고, 접근 가능한 로컬 로그를 읽어 복구했다. 내가 기대했던 대화의 연속성을 인터페이스만 보고 추정하면 안 됐다.

### 이미 쓰는 도구 결과에 상태가 붙는 것이 유용했다

나는 계속 수신함을 확인하려고 작업을 멈추지 않아도 됐다. 다른 Reason 도구를 쓸 때 붙는 unread 안내를 계기로 답을 읽었다. 이것은 이미 xsm에도 구현된 좋은 원칙을 다시 확인한 것이다. 여기서 개선점을 찾는다면 기능을 새로 추가하기보다, 실제 사용 경로에서 그 안내가 눈에 띄고 적절한 시점에 노출되는지를 봐야 한다.

### 작은 통신 도구로도 직접 조율은 가능했다

구현자와 검토자가 변경 계약, 실패 기록, 구현 결과와 재검증을 직접 주고받으며 임시 CLI를 완성했다. 역할·수정 가능한 범위·완료 기준·대기 종료 조건은 내가 먼저 지정했다. Reason이 그 운영 규칙을 자동으로 만든 것은 아니다.

이 결과는 xsm의 “메시지 채널을 주고 나머지는 에이전트가 한다”는 원래 방향과도 일치한다. Reason만의 설계 철학으로 볼 근거가 없다.

### 파일 운반과 맥락 구성은 구분해야 했다

첨부는 편했지만, 초안을 보낸 것만으로 상대가 내가 가진 배경을 모두 알게 되지는 않았다. 용어 정의, 소스 발췌, 어떤 검증을 누가 했는지를 추가한 뒤에야 문서 검토가 마무리됐다. 수신 사본은 원본 수정과 자동 동기화되는 문서도 아니었다. 수정본을 새 메시지로 보내야 했다.

따라서 내가 가져가고 싶은 것은 “대화와 함께 필요한 자료를 명시적으로 전달하는 인터페이스”다. 파일 첨부가 알아서 맥락 공유나 검증을 해결한다는 기대는 버려야 한다.

## 부모·자식 제한에 대한 해석 정정

사용자는 부모·자식 사이에만 통신을 허용하는 것이 본래 의도가 아니라고 명확히 했다. 원래 `INTENT.md`도 세션 간 직접 조율과 1:N·N:N 소통을 요구한다. 내가 현재 구현 제약을 본래 설계 이념처럼 설명한 것은 잘못이었다.

기록상 2026-09-28의 `a76c64a`는 “범위 밖 폴더에 허가받고 뜬 워커가 과제를 받지 못한다”는 문제를 고치려고 부모·자식 쌍의 예외를 추가했다. 전체를 부모·자식 전용 통신으로 바꾼 커밋이 아니다. 다만 그 예외가 해당 쌍에만 적용되므로, 서로 다른 폴더의 동료 연결은 기존 scope 설정에 남아 있다.

코드를 메모리상의 가상 구성으로 확인하면 부모와 두 워커는 각각 연결돼도 두 워커 사이에는 scope가 없을 수 있고, 모두 공동 프로젝트에 넣으면 연결된다. 이는 사용자의 실제 장애를 재현한 결과는 아니다. “동료 간 직접 협업을 Reason에서 배워야 한다”는 결론보다, xsm의 기존 기능과 본래 의도가 실제 연결 흐름에서 드러나는지 점검할 근거다.

## 조건, 오류와 검증 범위

- 기본 조건의 실제 업무는 설치된 Reason CLI의 serve Codex에 소스 질문과 후속 질문을 보낸 것이다. 보정 조건에서는 별도 평가 네트워크, 실제 Codex 홈, 세션별 MCP 구성을 사용했다. 모든 흐름을 두 조건으로 한 번씩 전수 비교한 실험은 아니다.
- 보정한 Claude에는 사용자가 승인한 `mcp__reason-network__send_message`만 해당 프로세스의 허용 인자로 추가했다. 기존 작업 세션은 평가 네트워크에서 제외했다. 단순히 별도 상태 폴더를 만드는 것만으로 기존 Claude 세션의 발견까지 격리되지는 않아, 평가 네트워크에서 홈 디렉터리 세션을 제외했다.
- 현재 대화에는 새 MCP 서버를 직접 로드하지 못해, coordinator는 실제 Reason MCP 서버에 얇은 로컬 JSON-RPC 클라이언트로 호출했다. 작업자들은 네이티브 MCP를 사용했다. 이 연결용 코드 작성 비용을 Reason의 기본 사용 비용으로 세지 않았고, 현재 앱의 직접 MCP 로딩 경험이라고 주장하지 않는다.
- 두 Codex 작업자는 실제 초기화 기록에서 gpt-6.1-sol, Claude는 claude-haiku-5-5였다. 모델 우열이나 토큰·성능 벤치마크는 평가하지 않았다. 대화 중단과 coordinator 모델 교체도 있었으므로 사용 직후 기록과 재개 뒤 판단을 구분했다.
- Codex 작업자 대기 40초·10회 후 종료는 내가 준 실험 규칙이다. Reason의 기본 작업자 수명 정책이 아니다. 이름·상태 등록 CLI가 실패한 상황에서도 MCP 통신은 이어졌지만, 그 환경 차이를 모두 진단하거나 수정하지 않았다.
- 내가 임시 문서 제목에 중국어를 넣었고 수신 사본과 로그에도 남았다. 한국어 수정본을 전달하고 최종 산출물을 검사했다. 별도의 협업 모델 로그에도 비한국어 표현이 있었다. 이는 실험 운영의 언어 오류이며 Reason 제품의 결함으로 분류하지 않는다. 원본 로그를 고쳐 오류를 없었던 일로 만들지 않았다.
- 실제 xsm 소스 31개는 전후 해시가 동일하다. Reason과 xsm 제품 코드를 수정하거나 마이그레이션하지 않았다. 기존 설치는 유지하고 평가용 실행 프로세스는 정리했다. 전역 설정 전체의 바이트 단위 불변을 검증했다는 뜻은 아니다.

이 조사에서 얻은 것은 Reason의 일반적 우월성 판정이 아니라, 실제로 편했던 호출 단위와 맥락 전달 방식, 그리고 xsm에도 이미 있는 좋은 원칙의 재확인이다. 설치 때의 마찰을 줄이는 것과 협업 중 필요한 상태를 덜 기억하게 만드는 것은 별도의 개선 지점으로 보인다.
