# Reason Network 실제 설치·연결 평가

평가일: 2026-10-23 KST. 대상: macOS arm64의 실제 사용 환경. Reason CLI `0.2.557`, 네트워크 엔진 `0.12.10`, Claude Code `2.1.309`, Codex CLI `0.163.0`.

## 요약

로그인·가입 뒤의 설치와 기본 연결은 에이전트가 명령으로 상당 부분 처리했다. 사용자에게 프로젝트 연결 명령이나 세션 ID 입력, 매뉴얼 읽기를 요구하지 않고 Claude와 Codex에 요청을 보내 응답을 받았다. Codex가 MCP로 Claude를 찾아 메시지를 보내고 답장을 받는 경로도 성공했다.

하지만 사용자 조작이 전혀 없는 설치로 판정할 수는 없다. 사용자가 브라우저 로그인·가입을 직접 진행했다. 새 Codex 대화형 세션의 Reason 훅 5개는 사용자의 채팅 승인 후 에이전트가 신뢰 처리했다. `reason network serve claude`에는 Reason MCP가 없었으며 CLI 대체도 승인 요구로 막혔다. 일반 Claude의 반복 회신과 일반 Codex의 유휴 수신에서도 추가 실패가 나왔다.

따라서 이 표본에서 확인한 것은 가입 후 기본 연결의 편의성과 현재 환경의 연결 한계다. 모든 프로필과 실행 경로가 자동으로 연결된다는 결론은 나오지 않았다. xsm 제거, 마이그레이션, xsm 기능 변경은 수행하지 않았다.

## 평가 조건과 증거

설치 전 `reason`·`reason-network` 실행 파일과 `~/.reason`이 없는 것을 확인했다. 기존 Claude·Codex·xsm은 설치돼 있었다. 새로운 OS 계정이나 VM에서 시작한 시험이 아니며, 에이전트는 앞선 문서·소스 조사 내용을 알고 있었다. 사용자가 매뉴얼을 읽지 않아도 되는지를 평가했으며, 에이전트 자신은 설치 페이지와 CLI 도움말을 읽었다.

설치 전 Claude에는 이미 `crossSessionInbound: accept`와 권한 기본 모드 `auto`가 설정돼 있었다. 성공한 경로도 이 기존 설정과 xsm이 남아 있는 공존 조건의 결과다. xsm을 제거한 뒤의 동작이나 신규 OS의 기본 권한 상태로 확대하지 않는다.

공식 시작 명령을 그대로 실행했다.

```sh
curl -fsSL https://reasonmachines.com/install.sh | bash -s -- network
```

설정 변경 전 사본은 비공개 임시 디렉터리에 보존했다. 원본 실행 로그에는 로그인 연결 정보와 초대 링크가 포함될 수 있으므로 공개 산출물에 넣지 않았다. 공유 가능한 결과는 [구조화 증거](reason-network-evaluation-2026-10-23/evidence.json)에 모았다. 아래 주소의 개인명은 `user`, 임시 작업 경로는 `<EVAL_ROOT>`로 치환했다.

이 실행은 실환경 탐색 평가다. 가상 인물·격리 OS·독립 이미지 판정을 포함한 정식 journey-qa 수용시험을 통과했다고 보고하지 않는다. 제품 문서나 공개 스크린샷도 수정·게시하지 않았다.

## 사용자에게 실제로 요구된 일

### 로그인·가입

설치 명령은 기본 브라우저에서 로그인 페이지를 열었다. 에이전트가 별도로 연 ego-browser에서는 Google 계정 선택 화면까지 도달했지만, 계정 선택이나 가입 동의는 실행하지 않았다. 그 사이 사용자가 기본 브라우저에서 로그인·가입을 완료했고, 원래 설치 명령이 이어서 완료됐다.

따라서 이 실행은 로그인 자동화 성공의 증거가 아니다. 브라우저에 저장된 계정만으로 에이전트가 최종 가입을 끝낼 수 있는지도 이번 표본에서는 검증되지 않았다. Reason에 생성된 사용자는 확인했지만, 사용자가 실제로 선택한 로그인 공급자와 이메일은 확인하지 않았다.

### Codex 훅 신뢰

새 대화형 Codex는 다음 5개 훅을 신뢰하기 전에는 실행하지 않는다고 표시했다.

- SessionStart
- SessionEnd
- UserPromptSubmit
- PostToolUse
- Stop

모두 설치된 Reason 엔진의 `hook codex ...` 명령이다. 기존 훅은 그대로 남아 있었다. 화면에는 훅이 신뢰된 뒤 샌드박스 밖에서 실행될 수 있다는 안내가 있었다. AGENTS.md의 권한 규칙 변경 승인 경계에 따라 사용자에게 물었고, 사용자가 “Reason 훅 5개 신뢰 허용”이라고 답한 뒤 에이전트가 평가 터미널에서 승인했다. 사용자가 직접 터미널 UI를 조작하지는 않았다.

신뢰 후 일반 대화형 Codex는 MCP 호출과 엔진 등록까지 성공했다. 그러나 그 세션의 유휴 수신은 J22에서 실패했다. `codex exec`·serve Codex의 성공과 일반 대화형 Codex의 실패는 구분했다.

### 매뉴얼·명령 입력

평가 중 에이전트가 사용자에게 매뉴얼 읽기나 셸 명령 입력을 넘긴 횟수는 0이다. 프로젝트 연결과 세션 ID 입력도 사용자에게 요구하지 않았다. 확인된 사용자 직접 UI 조작 구간은 로그인·가입 1구간이다. 별도로 Codex 훅 신뢰에 대한 채팅 승인 1회가 있었고, 실제 터미널 조작은 에이전트가 수행했다. 클릭 수는 측정하지 않았다.

## 성공한 연결에서 편했던 점

`reason network serve claude --cwd <frontend>`와 `reason network serve codex --cwd <backend>`는 `user/claude`, `user/codex`라는 수신 별칭을 제공했다. 이 두 작업 폴더 사이에 프로젝트 연결 규칙을 만들지 않았다. 에이전트가 목록을 보고 이름으로 대상을 골랐고, 사용자에게 긴 식별자를 받지 않았다.

J09는 수신 모델의 완료 주장만으로 판정하지 않았다. Codex 실행 기록에서 MCP 세 도구의 실제 호출과 결과를 추출했고, Claude 측 로그의 수신·응답과 대조했다. 받은 표식 `EVAL_CROSS_ACK_7319`와 요청에 대한 `reply_to`가 확인됐다.

일반 Claude는 스트리밍 입력을 열어 둔 정상 세션으로 실행했다. 준비 응답 뒤 유휴 상태에서 CLI 메시지를 넣자 세션이 다시 처리했고, MCP `send_message`로 표식 `EVAL_NATIVE_WAKE_2759`를 회신했다. 별도 사용자 입력이나 xsm을 통한 전달은 없었다. 다만 같은 세션의 두 번째 회신은 J21에서 거부됐으므로, 이 첫 성공을 반복 송신의 안정성으로 확대하지 않는다.

데몬 재시작 직후 디렉터리에서 별칭이 잠시 사라졌지만 serve 프로세스는 재연결했다. 추가 로그인·설정 없이 뒤의 Codex 요청이 성공했다. 이 결과는 한 번의 재시작 표본이며 장기 운영 안정성의 증거로 확대하지 않는다.

## 마찰과 실패의 범위

### serve Claude와 일반 Claude는 결과가 달랐다

`reason network serve claude`가 시작한 세션의 ToolSearch는 Reason 도구를 찾지 못했다. 이 세션에 CLI를 사용하라고 요청해도 첫 `reason network who`가 승인 요구로 거부됐다. 이 경로에서는 원래 사용하려던 MCP도, CLI 대체도 자동으로 이어지지 않았다.

반면 새로 실행한 일반 Claude는 Reason MCP 서버를 connected로 로드했고 `list_team`도 성공했다. 따라서 “Claude 연동 전체 실패”로 판정하지 않는다. 실패는 CLI `0.2.557`의 serve Claude 경로에서 관찰한 결과다. 권한을 넓히거나 제품 설정을 고쳐 통과시키지 않았다.

### 여러 Codex 홈은 한 번에 설정되지 않았다

현재 세션의 `CODEX_HOME`인 `.codex-3`에는 Reason MCP와 훅이 추가됐다. 다른 두 홈에서 `codex mcp get reason-network`를 실행하면 `No MCP server named 'reason-network' found`로 끝났다. 여러 프로필을 쓰는 이 환경에서는 한 번의 설치로 모든 홈이 연결된다고 볼 수 없다.

### 일반 Claude의 자동 승인에 반복 회신이 막혔다

첫 회신이 성공한 같은 세션에서 두 번째 메시지를 보냈다. 수신 세션은 실제 `send_message`를 호출했지만 Claude Code 자동 모드 분류기가 `External System Writes`로 거부했다. 모델의 완료 문구가 아니라 실제 `permission_denied` 이벤트를 확인했다. 요청한 CLI는 답을 받지 못해 시간 초과했다.

이는 네트워크 수신 실패와 다르다. 메시지는 모델에 도달했고 송신 권한에서 막혔다. Reason 설치가 이 환경의 반복 메시징 권한까지 해결하지는 못했다. 권한을 넓히거나 다른 도구로 우회해 재전송하지 않았다.

### 일반 Codex의 유휴 수신은 홈 라우팅에서 실패했다

훅 신뢰 후 평가 TUI는 엔진에 idle·push로 등록됐다. 정확한 세션에 메시지를 보내자 데몬 로그에 `no rollout found for thread id`와 `falling back to hooks`가 남았다. 90초 동안 추가 사용자 입력 없이 답하지 못했다.

그 뒤 같은 스레드에 `codex queue`를 직접 대조했다. `CODEX_HOME`을 지정하지 않은 기본 홈 경로는 같은 오류로 실패했고, 실제 `.codex-3`를 지정한 경로는 큐 등록에 성공했다. 설치된 launchd 서비스에는 `CODEX_HOME`이 없었다. 이 표본에서는 네트워크가 알고 있는 스레드와 실제 Codex 홈 사이의 라우팅 문제가 확인됐다. Reason 서비스나 설정을 수정해 해결했다고 주장하지 않는다.

직접 큐 진단은 원래 실패한 Reason 요청이 시간 초과한 뒤 수행했다. 이후 진단 입력으로 세션이 움직여도 원래의 무인 유휴 수신 성공으로 합치지 않았다. 이 Codex TUI는 로컬 백그라운드 서버 모드였고 세션 메타데이터의 source는 vscode였다. 다른 Codex 버전·실행 모드의 결과로 일반화하지 않는다.

### CLI 디렉터리와 엔진 디렉터리가 달랐다

같은 시점의 `reason network who --all --json`에는 일반 Codex 세션이 없었고, 공개 엔진의 `who --all --json`에는 live Codex 세션 2개가 있었다. 평가 TUI의 상태 화면과 엔진 등록을 읽기 전용으로 대조해 정확한 대상을 골랐다. 이 내부 조사는 사용자가 한 일이 아니지만, 기본 CLI 목록만으로 연결하기에는 추가 마찰이 있었다. 필터링의 정확한 구현 원인은 확인하지 않았다.

### 수신 별칭의 저장소 표시가 실제 작업과 달랐다

두 serve 명령에는 서로 다른 임시 저장소를 `--cwd`로 지정했다. 실제 모델에 작업 디렉터리를 확인하게 하자 각각 지정한 폴더가 맞았다. 그러나 네트워크의 `claude`·`codex` 별칭에는 두 명령을 실행한 xsm 저장소가 표시됐다.

이 표본에서 이름으로 연락하는 일은 성공했지만, 저장소를 보고 수신자를 찾는 판단에는 이 불일치가 영향을 줄 수 있다. 실제 작업 폴더가 잘못됐다고 판정한 것이 아니라 디렉터리 표시의 불일치를 확인한 것이다.

### 기존 세션은 자동으로 모든 도구를 얻지 않았다

설치 완료 메시지는 현재 세션과 다른 열린 세션을 재시작해야 새 MCP 도구가 생긴다고 명시했다. 재시작 전에는 CLI로 조회·요청할 수 있다는 대안도 안내했다. 일반 세션의 MCP 검증은 새 프로세스에서 수행한 결과이며, 설치 전부터 열린 모든 세션이 자동 전환됐다는 뜻은 아니다.

## 엔진 단독 경로

공개 엔진은 서로 다른 `REASON_NETWORK_HOME` 두 개를 사용해 같은 머신에서 격리했다. `init --no-setup`과 `join --no-setup`으로 설정 파일·서비스를 추가하지 않고 별도 평가 네트워크를 만들었다. 계정 가입이나 브라우저 없이 초대 링크를 얻어 상대 엔진을 가입시킬 수 있었다.

추가로 GitHub 공식 엔진 설치 스크립트를 새 설치 경로에 실행해 다운로드·체크섬 검증·바이너리 설치·팀 초기화까지 약 4.43초에 완료했다. 이 경로도 브라우저와 사용자 입력이 없었다. 단, `--no-setup`을 사용했으므로 이 별도 엔진을 실제 사용자의 모든 에이전트에 연결한 시험은 아니다.

이후 두 엔진 사이의 고유 표식 전송은 양방향으로 성공했고, 팀 상태는 상대를 direct 1ms로 표시했다. 다만 같은 호스트에서 실행한 두 엔진이다. 실제 별도 컴퓨터 가입, NAT 통과, 인터넷 릴레이, 다른 사람의 계정 초대 성공을 입증하지 않는다. 이 부분은 미검증이다.

## 평가 자체에서 분리한 문제

첫 일반 Claude 검사에서는 평가 모델이 요청과 달리 보조 스크립트를 만들고 중첩 검사를 실행했다. 원래 수집 파일도 다시 기록돼, 이 결과는 깨끗한 단일 실행 표본에서 제외했다. 원본 JSON에는 그 순서가 남아 있다. 다시 실행한 J04는 내장 도구를 ToolSearch로 제한했고, 실제 ToolSearch와 `list_team` 두 호출만 나온 것을 확인했다.

일반 Codex 실행에는 기존 로컬 공급자 경로의 WebSocket 426 오류가 있었지만 명령과 MCP 호출은 성공했다. 이 오류를 Reason의 연결 실패로 분류하지 않았다.

ego-browser는 업데이트 가능 알림을 표시했다. 평가 중 브라우저 버전을 변경하지 않았다. 정리 단계의 종료 호출에서는 작업 공간을 찾지 못했고, 목록에서도 해당 공간이 없음을 확인했다. 에이전트가 정상 종료시켰다고 기록하지는 않았다.

## xsm 비교에서 바뀐 판단

Reason은 사용자에게 프로젝트 연결과 세션 ID를 다루게 하지 않고 기본 연결을 성립시키는 흐름을 실제로 제공했다. 이 점은 문서상 지원만 확인한 앞선 조사보다 강한 근거다.

앞선 비교에서 “Reason 공개 엔진에 동등한 워커 생성 기능을 확인하지 못했다”고 한 범위도 보완해야 한다. 공개 엔진과 별개인 Reason CLI에는 `network serve`가 있고, 로컬 Claude·Codex 수신 에이전트를 실제로 띄웠다. 따라서 단순한 워커 실행 자체를 xsm만의 차별점으로 두기 어렵다. xsm의 응답 후 종료·실패 계보·공유 기록과 동등한지는 이 평가로 판정하지 않았다.

사용자는 이 결과를 바탕으로 마이그레이션과 xsm 개선을 검토할 수 있다. 이번 실행은 그 선택을 대신 내리지 않았다. 특히 다중 홈 누락과 유휴 수신 실패, Claude 자동 승인에 따른 회신 거부, serve Claude 실패, 디렉터리 표시를 기본 연결 성공과 함께 평가해야 한다. Reason의 설치 흐름이 더 간단하다는 관찰과 현재 환경의 모든 세션을 대체할 수 있다는 판단은 별개다.

## 설치 변경과 복구 준비

공식 설치로 Reason CLI, 네트워크 엔진, 사용자 로그인 서비스 `com.reasonmachines.network.plist`, 에이전트별 MCP·훅·확장 설정이 추가됐다. 현재 Reason 설치와 사용자 네트워크는 남아 있다.

설치 전 추적한 경로 10개 중 8개가 변경 또는 생성됐다. 이 10개는 전체 설치 파일 목록이 아니다. opencode 플러그인, pi 확장, DeepSeek 설정 등도 doctor와 setup 출력에서 확인했다. `.codex-3/config.toml`에는 Reason 서버의 `default_tools_approval_mode = "approve"`가, Claude 설정에는 Reason `ask_user` 허용 항목이 추가됐다.

비교한 `.codex-3/config.toml`, `.claude/settings.json`, `.claude.json`의 기존 xsm 관련 항목은 총 79개이며 전후 동일했다. 다른 프로세스가 바꿀 수 있는 전체 설정 파일이 바이트 단위로 불변이라는 뜻은 아니다. xsm 코드·설치·세션을 제거하거나 마이그레이션하지 않았다.

복구 시에는 공식 `reason network leave`와 엔진의 `setup --remove`로 네트워크 연결·에이전트 연동을 제거한 다음, 설치 전 사본과 현재 설정을 비교해 남은 변경을 복원할 수 있다. Reason CLI 제거와 데이터 삭제는 별도 작업이다. 사용자 승인 없이 삭제·탈퇴·설정 복원을 실행하지 않았다.

평가용 serve 프로세스 2개, 일반 Claude 스트리밍 프로세스 1개, 격리 엔진 데몬 3개는 중지했고 해당 PID가 더 이상 실행 중이지 않음을 확인했다. 평가 Codex 대화형 클라이언트도 종료했다. Codex 공유 백그라운드 서버와 대화 이력은 유지했다. 기존 세션은 종료하지 않았다.

Reason의 실제 설치·경로별 동작 평가와 실패 기록은 수행했다. 이것은 실패 경로가 고쳐졌다는 선언이 아니다. 별도 물리 머신·NAT·인터넷 릴레이·8종 전체 런타임·xsm 제거 후 단독 실행은 이 표본에서 미검증으로 남는다.

평가 실행 기록용 `.journey-qa/`는 로컬 `.git/info/exclude`에 추가했다. 공유 제외 규칙이며 저장소의 추적 파일이나 공용 `.gitignore`를 변경하지 않았다.

## 독립 검토

별도의 읽기 전용 Codex 실행이 보고서와 증거를 대조했다. 첫 검토에서 4개 항목의 증거 부족이 나와 doctor 실제 출력, Codex MCP 이벤트, Claude 준비·회신·거부 이벤트, 재연결 로그, 전체 10개 경로 비교를 보완했다. 재검토는 관찰 24건의 분류와 결론이 증거에 부합하고 성공 과장·실패 누락이 없다는 PASS 판정을 냈다. [검토 결과](reason-network-evaluation-2026-10-23/independent-review.json)
