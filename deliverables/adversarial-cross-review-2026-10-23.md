# xsm과 Reason의 양방향 적대적 비평

두 비평가를 서로 다른 새 문맥에서 실행했다. 한 명은 Reason 관점에서 xsm을, 다른 한 명은 xsm 관점에서 Reason을 공격했다. 같은 Codex 모델과 읽기 전용 설정을 사용했으며 서로의 답변과 coordinator의 결론을 제공하지 않았다. 이는 서로 다른 모델 두 종류의 합의가 아니라, 같은 모델을 독립적인 두 문맥과 반대 관점으로 실행한 결과다.

원문: [Reason 관점의 xsm 비평](adversarial-cross-review-2026-10-23/reason-on-xsm.md), [xsm 관점의 Reason 비평](adversarial-cross-review-2026-10-23/xsm-on-reason.md).

## 가장 강한 공격

**Reason 관점:** 사용자는 이미 자신의 의사를 표현했는데, xsm이 별도의 승인 기록·범위·재실행·전송 경로를 에이전트에게 관리하게 한다. 실제 승인을 놓친 뒤에도 동일한 기록만을 요구하는 복구 경로는 “나머지는 에이전트가 한다”는 약속을 깨뜨린다.

**xsm 관점:** Reason의 친숙한 주소와 송신 결과가 실제 런타임 도달을 보장하지 않는다. 같은 Codex 스레드에서 큐 등록은 실패했는데 최초 응답은 등록된 것처럼 표현됐다. 데몬과 신원 체계를 더해도 대상 홈·스레드·훅의 정확한 바인딩은 여전히 필요하다.

두 공격은 상쇄되지 않는다. 첫째는 작업을 성립시키는 부담을 누가 지는가의 문제이고, 둘째는 이미 성립했다고 보이는 작업을 어떤 증거로 믿을 수 있는가의 문제다.

## Reason 관점에서 xsm을 공격한 여섯 항목

| 공격 | coordinator 대조 결과 |
|---|---|
| 실제 승인을 놓치면 복구 수단도 같은 누락 기록에 종속됨 | 실제 실행과 순수 함수 대조로 확인. 기록이 전혀 없는 경우에는 원문을 받지만, 기록은 있고 해당 답만 없으면 거절한다. 설치된 consent 소스도 체크아웃과 같음을 추가 확인 |
| “한 번 검토해 줘”가 폴더 연결 범위와 수명 관리로 확대됨 | 제품 선택의 대가. 도구가 기본 연결 방식을 제안하므로 사용자가 매번 link·join·reach를 직접 고른다고 확대하지 않음 |
| 주소 식별에 비해 담당 업무로 상대를 고를 구조화 정보가 적음 | 목록 필드 차이는 확인. 이로 인한 실제 사용자 개입률은 미검증이며 런타임 이름에 업무 정보가 담길 수 있음 |
| CLI/MCP 경로 선택과 기능 차이를 에이전트가 알아야 함 | 실제 Codex의 CLI 거부 후 MCP 복구 확인. MCP 송신 스키마·호출에 priority가 없는 것도 확인. Reason MCP의 FYI 부재 역시 유지 |
| Codex 작업 도중 답을 읽는 시점을 호출자가 관리해야 함 | xsm 자체의 중간 수신 경로와 문서에서 확인. 모든 SDK 버전의 자동 전달을 부정하는 주장은 아님 |
| 답변 대기와 수신 영수증 대기를 혼동하게 함 | README의 “답장 기다림” 설명은 실제 --wait 계약과 불일치. 영수증 전용 대기 API 자체는 설계 선택이며 reply_to·outcome이 없는 것은 아님 |

가장 먼저 손댈 후보는 승인 수집과 복구다. 올바른 답이 기록된 대조 조건에서는 정상 인식되므로, 해결책을 임의의 --reply를 허용하는 것으로 단순화할 수 없다. 실제 사용자 응답이 해당 요청에 도달하는 경로를 복구해야 한다.

다음 후보는 실행 경로를 잘못 고르게 하는 답장 안내와 인터페이스 차이, 실제 답변까지 기다리는 명확한 호출 단위다. 기존 inbox나 링크 기능을 다른 이름으로 다시 소개하는 것은 해결이 아니다.

## xsm 관점에서 Reason을 공격한 여섯 항목

| 공격 | coordinator 대조 결과 |
|---|---|
| 주소·스레드는 알지만 대상 Codex 홈을 보존하지 못함 | 동일 스레드의 실제 전달 실패 확인. 공개 엔진의 queue 구성·실행에도 대상별 CODEX_HOME이 없다. 다만 실제 데몬 전체 환경을 수집하지 않아 단일 원인으로 확정하지 않음 |
| 실제 큐 등록 성공보다 먼저 성공을 전제하는 문구를 반환함 | pinned 소스에서 비동기 실행 시작 직후 반환하고, 뒤에 실패하면 등급을 낮추는 경로 확인. 데몬 저장·네이티브 큐 등록·모델 읽기는 구분해야 함 |
| 같은 형태의 주소가 대화·프로세스·우편함이라는 서로 다른 수명을 가리킴 | 문서·소스에 명시된 제품 비용. 오프라인 송신 문구에는 미독 만료 안내가 실제로 있으므로 완전히 숨긴다는 표현은 줄여야 함 |
| 작업별 협업 범위가 머신의 네트워크 참여와 폴더 제외 관리로 바뀜 | 기본값과 정책에서 확인. 정보 침해의 증거는 아니며, 바로 그 넓은 참여 범위가 새 저장소 연결을 쉽게 만든 반대 증거도 유지 |
| MCP와 CLI에서 표현할 수 있는 FYI·그룹 협업 의도가 다름 | MCP는 wake=true로 보내며 CLI FYI와 다르다. 에이전트의 그룹 송신 제한은 소음 방지라는 타당한 반론이 있고, N:N 자체는 두 도구 모두 성공 |
| 공유 MCP 프로세스의 첨부 루트가 호출별 작업 폴더와 달라질 수 있음 | 조건부 결함 후보. 호출별 세션 키와 별개로 agent_files가 프로세스 cwd를 사용함은 확인. 서로 다른 저장소가 실제 한 MCP 프로세스를 공유하는 구성과 오전송은 재현하지 않았음 |

가장 먼저 검증할 후보는 대상 홈을 포함한 런타임 바인딩과 송신 회신의 증거 강도다. 주소가 맞다는 것, 전달 명령이 실행됐다는 것, 런타임이 받아들였다는 것, 실제 답이 왔다는 것을 구분해야 한다.

공유 MCP의 첨부 루트 문제는 확정 결함 목록에 넣지 않았다. 문서가 상정하는 구성과 실제 하네스의 프로세스 공유 단위가 일치하는지 재현한 뒤 판정해야 한다. 이를 정보 유출이나 모든 첨부의 실패로 표현하지 않는다.

## 유지한 반대 증거와 보류

- xsm은 같은 저장소의 질문·후속·동료 간 직접 검토와 일반 Codex 수신에서 실제로 성공했다. 부모·자식 전용이라는 것이 사용자 원래 의도도 아니고 전체 구현의 의미도 아니다.
- Reason은 새 저장소 세션과 추가 폴더 연결 없이 실제 왕복했다. xsm의 연결 승인 수집 실패는 이 장점을 공격하면서도 숨길 수 없는 반대 증거다.
- Reason 엔진은 오픈소스이고 계정 없는 경로가 있다. 비공개 CLI에는 실제 network serve도 있다. 이 기능들이 없다고 주장한 공격은 채택하지 않았다.
- xsm delivered 역시 모델의 이해·실행·과제 성공을 증명하지 않는다. typed outcome은 수신자가 보고한 결과이지 독립 검증 그 자체가 아니다.
- Reason의 주소 수명에 대한 공격과 비공개 serve의 문맥 지속성은 별개다. 두 번째 비평가는 주어진 baseline 자료만으로 serve의 대화 단절을 확정하지 않았다. baseline은 시험 조건의 이름이므로, 실제 바인딩은 별도의 시작 로그로 판단해야 한다.
- 프로젝트 경계와 네트워크 참여의 어느 쪽이 맞는지는 이 비평이 대신 결정하지 않는다. 사용자에게 필요한 협업 범위와 권한을 표현하면서 어떤 부담을 남기는지가 설계 쟁점이다.

## 검증과 독립성

Reason은 태그 v0.12.10, 커밋 `72ca2b3fb36d6e3cbfa44aa82c68d27aafe5e690`의 공개 소스를 고정해 읽었다. 비공개 CLI는 실제 인터페이스와 실행 결과까지만 다뤘다.

두 실행은 source=exec, forked_from_id=null인 서로 다른 세션이었고 모델의 샌드박스는 read-only였다. 각각 16회의 도구 호출을 남겼으며 MCP·웹 호출이나 상대 비평 출력 읽기는 관찰되지 않았다. 설명 보고서 대신 지정한 원시 증거와 코드를 읽었다.

coordinator는 승인 복구 함수를 AST로 추출해 메모리상의 세 조건을 대조했다. “기록 없음”, “기록은 있지만 실제 승인 누락”, “실제 승인 기록 있음” 중 두 번째만 거절됐다. 실제 사용자 상태는 변경하지 않았다. ledger의 대기 함수도 답변이나 outcome 없는 delivered만으로 반환함을 별도로 확인했다.

원래 xsm 파이썬 소스 31개의 해시는 두 검토 후 동일했고 tracked diff도 없었다. 새로운 실통신·권한 변경·폴더 연결은 수행하지 않았다. 비교에서 미완이던 xsm 연결 후 구간은 그대로 미검증이다.

자세한 판정과 한계: [검증 기록](adversarial-cross-review-2026-10-23/verification.json). 별도 세션과 실제 실행 기록: [실행 메타데이터](adversarial-cross-review-2026-10-23/execution.json). 원문은 주장과 판정을 유지하고 링크 목적지만 정리했다. 원래 stdout과 입력 자료는 비공개 임시 경로에 보존했다.

실행 기록의 한계도 남긴다. 개별 비평 실행은 각각 약 560초와 588초에 종료 코드 0으로 끝났지만, 라우팅 원장의 900초는 실행과 사후 검증 기록 전체를 포함했다. 두 비평을 대조한 뒤 완료 기록을 제출해 이 기한을 넘겼고, 원장은 incomplete로 남았다. 기록을 바꾸거나 모델을 다시 실행하지 않았다. 실제 비평문·검증 결과의 존재와 라우팅 원장의 완료 여부를 구분한다.
